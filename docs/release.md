# 发版

什么时候走本页：一批修改做完（改代码、写测试、跑过相关测试、提交）之后，问仓库主人要不要打包发版；他说发版才走，不说不走（2026-10-17 用户定的）。一旦走，就要走完：全量回归通过、打包、从最近两版压缩包验收安装与自动更新、单独提交 `release` 并打版本标签，不能只走一半。提交和 push 到 GitHub 直接做（2026-10-18 用户定的）；发布到内网 GitLab 由仓库主人在维护的那台电脑上做。

## 版本号

- 格式 `年月日.时分`，取打包那一刻的本机时间，比如 `20261001.0303`。一天可以发好几版。
- **不能比实际时间晚**：自动更新按版本号比新旧，写晚了的版本号之后，按实际时间打的包反而"更旧"，会被当成退回旧版（2026-09-28 出过一次，重打了）。所以版本号等真要打包时才定。
- 包名带完整的版本号：`vibe-kit-<版本号>.zip`，打在仓库根目录。zip 不进 git。

## 平时：先写占位

改完一批东西，在 `vibe-kit/更新说明.md` 里改三处：

- 最上面加一节，标题写 `## @@VER@@（最新）`，原来那一节标题里的"（最新）"去掉。
- "先看你装的是哪一版"那张表最上面加一行（下面这样），原来写"最新版"的那一行改成说明是哪一版的包。
- 有新开关的，加进"配置页'套件开关'一览"那张表。

```
| 有 `VERSION` 文件，内容 `@@VER@@` | 最新版 |
```

`pack.js` 会查这两处（标题和表里都要有这个版本号），对不上不打包。

这一节写给用的人看：新加了什么、行为变了什么（他们会感觉到的）、修了什么、要他们做什么（比如开着的会话要敲什么）。内网导出的议题修了的，写"修了 #编号"，发布时脚本会在对应议题下面留一句是哪一版修的。

## 平时：改了提示的说法、默认值之后

20261018.0051 那一版全量回归 40 项不过、验收 1 项不过，全是过时的断言，一直到发版才暴露，修完补跑 23 分钟（见 [docs/release-timing.md](release-timing.md)）。所以改了钩子的提示、默认值、配置页说明这类"说法"之后，提交之前做两件事：

1. 找测试里的旧说法、旧默认值，找到的逐个看一眼、该改的改：

   ```bash
   node dev/stale-asserts.js
   ```

2. 跑改到的几套，加一个 Claude Code 版本的端到端、一份钩子对比（`e2e`、`diff` 是简写）：

   ```bash
   node dev/run-all.js --only test-1008.js,e2e,diff --claude <2.1.289 的 claude.exe> --old dev/baseline/<最新的基线>/vibe-kit
   ```

不用先跑一遍完整的基础回归：确定发版就直接全量（下面"打包前"），依赖旧默认值的那几套全量回归照样会发现。

## 打包前

1. 全量回归，盯着桌面跑（参数见 [dev/README.md](../dev/README.md)）：

   ```bash
   node dev/run-all.js --rt auto --claude <2.1.289 的 claude.exe> --claude <2.1.259 的 claude.exe> --claude <2.1.120 的 claude.exe> --old dev/baseline/<最新的基线>/vibe-kit --old dev/baseline/<再早一版>/vibe-kit
   ```

   要求：全过、桌面上没有多出窗口、临时目录没留下东西。默认分几路同时跑，2026-10-18 实测约 33 分钟（以前一个接一个 72 分钟，见 [docs/release-timing.md](release-timing.md)）。有失败、怀疑是同时跑引起的，用 `--lanes 1 --only <那几套>` 单独重跑确认。
2. `dev/diff-hooks.js` 里这一版有意改的用例，`since` 先写 `NEXT`。

## 升级自带的 OpenSpec（要升的时候）

安装包带一份 OpenSpec（`vibe-kit/kit/openspec/`，用户 2026-10-17 定的集成，打包时用当时的最新版）。升级在全量回归之前做，回归要用新的这份跑：

```bash
npm view @fission-ai/openspec version
```

```bash
npm install --prefix vibe-kit/kit/openspec @fission-ai/openspec@<版本号> --omit=dev --ignore-scripts --no-audit --no-fund
```

然后把 `vibe-kit/kit/openspec/package.json` 里的版本钉成确切的版本号（不留 `^`），核对三件事：
- 新版要求的 Node 版本（`node_modules/@fission-ai/openspec/package.json` 的 `engines`）。比以前高的，在《更新说明》里写明：Node 不够的电脑会退回用自己装的。
- 在临时目录里用新版建一个变更、写好四份产物，拿 1.2.0 跑 `list`、`status`、`validate`、`archive`，确认同事的旧版还认（做法见 2026-10-17 的记录：`.vibe/tmp/openspec-probe` 里的探测脚本思路）。
- 新版生成的命令里调用命令行的写法没变（`openspec <子命令>` 开头），`lib/openspec.js` 的改写还能认出来。

## 打包

```bash
node dev/stamp-and-pack.js
```

它把《更新说明.md》里的两处 `@@VER@@` 换成现在的时间，再跑 `pack.js`：检查（脚本语法、UTF-8、`.bat` 是 GBK + CRLF、源目录里没有运行时文件、必备文件都在、没有 jar）→ 写 `kit/VERSION` → 压缩 → 解压出来逐个文件核对 → 在 `dev/baseline/<版本号>/` 留一份这一版的代码（只留最近四份）。

只补了文档、要重打同一个版本：`node dev/pack.js --keep-version`。

## 打包后

1. `dev/diff-hooks.js` 里写成 `NEXT` 的用例改成刚打的版本号（加一个常量，比如 `const V1001 = '20261001.0303';`）。不改的话，下一版拿这一版当旧版对比时，这些用例会报"和旧版确实不同"不成立。
2. 验收：拿真的压缩包走一遍发布、安装、自动更新。从最近两三个版本各升一次：

   ```bash
   node dev/accept-packages.js vibe-kit-<上上版>.zip vibe-kit-<上一版>.zip vibe-kit-<这一版>.zip
   ```

   最后一个是这一版，前面的每个各升一次，几条升级路同时跑（端口各错开 10，从 18751 起）：2026-10-18 实测一个接一个 5 分 25 秒，同时跑 2 分 53 秒。只给两个包就只走一条路。

3. 提交到这个仓库，打标签 `v<版本号>`，push 到 GitHub（main 和标签，2026-10-18 起直接推，不用再问）。
4. 发给内网：维护的人（只有他那台电脑能发）解压新包，双击 `发布到 GitLab（双击我）.bat`。同事的电脑会自己发现、自己装上。手动装的同事直接给 zip。

## 内网的议题怎么进来

1. 同事那边记下的问题反馈自动建成内网 GitLab 的议题。维护的那台电脑在配置页"更新和上报"里导出开放中的议题（一个 `.md`，浏览器下载），导出后这一批关掉。导出文件最后附着各台电脑的使用情况汇总。
2. 把导出文件交给改套件的人（或 AI）。先分三类：真毛病、规矩和全自动模式打架、不是问题。议题后面附的钩子流水账要看，信息往往比议题本身多。
3. 能复现的先在旧版上复现（拿 `dev/baseline/` 里的上一版跑同样的输入），再改，再加测试。
4. 修了的在《更新说明.md》里写"修了 #编号"。
