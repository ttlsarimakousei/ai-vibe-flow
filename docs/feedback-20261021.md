## 1. 提问框/原话的审查、自测、提交许可认不出（#179、#182、#187）

### 现象

人工模式下跑测试、起服务、跑 review.js、调 ttls-reviewer 代理，钩子回"人工模式：先用 Ask 询问是否自测或复验及范围……"。模型已经问过、用户已经选了，还是拦；拦截不带编号，不能申请放行。用户只好在对话里把"自测""审查"再打一遍，有一次为了跑一次审查打了 3 遍。三台电脑都出现过。

议题里的原话：

- #179：提问框"是否要我先自测？范围选哪个？"选"全量自测（推荐）"，`mvn test` 被拦；用户在对话里打"全量自测"，还是拦。后来一次：提问框多选"自测（推荐）/审查（推荐）"，用户又在对话里打"自测"让起服务放行，接着跑 review.js 被拦。
- #182：提问框选"按 tasks.md 自测（推荐）"，`mvn test` 被拦；提问框选"use ttls-cross-review"，调技能被拦；用户说让 `git add/commit`，提交方式是"关"，被当成没要求提交拦下。
- #187：提问框选"用 ttls-reviewer 代理审查"，调代理被拦；单独再问一次、选"现在审查"才放行。

### 核实

假用户目录里用 `S.userSaid(会话记录, 话题)` 逐条试（脚本见文末"复现 1"）：

| 说法 | 话题 | 结果 |
|---|---|---|
| 提问框"是否要我先自测？范围选哪个？"＝"全量自测（推荐）" | test | 不认 |
| 对话里"全量自测" | test | 不认 |
| 提问框"人工模式下是否执行这些自测？"＝"按 tasks.md 自测（推荐）" | test | 不认 |
| 提问框"独立审查怎么做？"＝"用 ttls-cross-review" | review | 不认 |
| 提问框"独立审查怎么处理？"＝"用 ttls-reviewer 代理审查" | review | 不认 |
| 对话里"帮我 git commit 一下" | commit | 不认 |
| 提问框"现在执行本次代码的独立审查？"＝"现在审查" | review | 认 |
| 一个提问框三问："审查""自测""按日期" | review、test | 都认 |
| 提问框多选"自测（推荐）, 审查（推荐）" | review、test | 都认 |
| 对话里"把这两个变更 git add 然后 git commit" | commit | 认 |

### 根因

- 提问框的答案和用户打的字走同一套 `intent.explicit()`：动作词前面只能是"请、帮我、现在、直接……"这类前缀（`PREFIX`，`lib/intent.js:22`），而且要在句首或标点后（`lib/intent.js:36`）。提问框的选项是模型写的，常带"全量""按 tasks.md""用 ttls-reviewer 代理"这类修饰，就认不出。
- 提问框分支（`lib/session.js:251`）另有一条退路：问题里有动作词、答案是"好""可以"这类短肯定（`YES_SHORT`）。"全量自测（推荐）"不是短肯定，也走不通。
- "git commit"：`commit` 前面是 "git "，不在前缀里。
- 只看最后一句（`lastUserVoice`）：提问框里同时选了自测和审查，之后用户在对话里又打了一句"自测"，最后一句就只剩自测，审查的许可没了（#179 最后一次）。这是"归档、提交要他点头，只看最后一句"那条规矩（2026-10-07 用户定的）用到了审查、自测上。
- #187 第一次被拦时三问一框的选项原文不在议题里。按"审查"原样测是认的，现场多半是选项带了修饰（同上），没有原文不能定。

### 改法（仓库主人 2026-10-21 同意）

1. **提问框答案单独判断**：选项是用户点的，不要求动作词在句首。答案里含这个话题的动作词（审查：审查/审核/复审/审一下/cross-review/reviewer；自测：自测/测试/起服务/看页面……沿用 `SAID[topic].yes`），不含否定（不/先不/暂不/跳过/放弃/不用/取消，沿用 `intent.denied`），就算。提交、归档、推送也用这条，但仍然只看最后一句。
2. **对话原话放宽"范围词 + 动作词"**：只对 review、test 放宽，"全量自测""按 tasks.md 自测""用 ttls-reviewer 审查""单元测试跑一下"这类算。提交、归档、推送的认法只能收紧（intent.js 第 45 行注释的原则），只补"git commit""git add 然后 git commit"这种直接写命令的。
3. **审查、自测往回看本轮**：本轮（`turnStart()` 算的最后一条真人消息起）用户的原话和之后每个提问框答案里，有一处给了审查或自测许可、后面没有一处否定它，就算。提交、归档、推送不变，仍只看最后一句。许可照旧在 `permissions.allow()` 里绑会话、目标和版本，成功用过一次就消费掉，不能借到下一轮。
4. 拦截提示写清楚要什么：例如"人工模式：先用提问框问是否自测；选项写成'自测（范围）'或'不用'，用户选了自测就直接跑"。

### 要加的测试

- `dev/fixtures/intent-phrases.json` 的 review、test、commit 各加上表"不认"的原话（该算）；否定、问句、名词（"审查报告看一下"）保持不算。
- `dev/test-workflow-intent.js` 加提问框答案的用例：带修饰的选项算、"先不用审查""跳过自测"不算；多问一框只认对应的那一问。
- 往回看本轮：提问框选"自测、审查" → 用户打"自测" → review.js 放行；上一轮的许可不能带到这一轮；本轮后面说了"先不审"就不算。
- 提交、归档、推送：本轮前面说过、最后一句没说的，仍然不算（防止放宽带到这几类）。
- 按 AGENTS.md：拿 0051 的套件跑新用例，看要有几项不过。

## 2. 提案修订后，提问框选"开工"，改代码仍被拦（#187 补充）

### 现象

改完提案（范围回到提案阶段），模型用提问框问开工，用户选"开工"，接着 Edit 业务代码，被 `[vibe-kit 范围] 提案已修订，业务代码要重新明确开工` 拦下；再问、再选，还是拦。同一个项目的流水账里，`guard-ask block Skill opsx:apply（用户还没说开工）` 四分钟里出现 4 次。

### 根因

- 提问框的答案不触发用户开口钩子，开工许可要在用之前补读（`confirmApply()`，`lib/session.js:278`）。guard-ask（调 `/opsx:apply` 技能前，`hooks/guard-ask.js:34`）和 guard-spec（打勾前，`hooks/guard-spec.js:95`）都补读了，**改文件的 pre-edit 没有**：`hooks/pre-edit.js:47` 直接 `scope.check()`，状态还是 `stage=plan, waiting=scope`，就拦。
- 走 `/opsx:apply` 技能这条路也会失败：`confirmApply()` → `apply-scope.grant()` 在"有多个变更、答案里没点名"时返回 `有多个变更，请明确 apply 哪个变更`，但 guard-ask 只说"用户还没说开工"（`hooks/guard-ask.js:39`），原因丢了。出问题的项目当时正好有两个没归档的变更。

### 改法

1. pre-edit 在 `scope.check()` 之前先 `confirmApply(j)`，和 guard-spec 一样。
2. `confirmApply()` 把 `grant()` 的失败原因带出来；guard-ask 拦的时候把原因说出来，例如"有两个变更 a、b，提问框的选项要写明开工哪一个"。
3. 同一个答案修订后不能再授权（`applyVoice`）这条保留。

### 要加的测试

修订提案 → 提问框答"开工" → Edit 业务代码放行；同一个答案在再次修订后不放行；两个变更时提问框答"开工"不点名，拦截提示里说出两个变更名；答"开工 a"放行。

## 3. 审查模型只回思考、没有正文（#180、#186、#188、#175）

### 现象

review.js 提案模式、代码模式都有：每批 `stage=model-empty`、"未收到审查者正文，未记为完成"，`completedBatches=0`、`covered=[]`、`status=failed`。诊断片段里 `content` 只有 `thinking` 块，思考里其实有实质意见（模型自己看出了 design 前后不一致、并发风险），工具不采信。两台电脑、deepseek-flash 和 MiniMax-M3.1-Flash 两种模型都有，重跑一样。审查一直过不去，提案卡在不能 apply，代码审查点卡住。

### 根因（代码确认，现场缺停止原因）

- 审查请求写死 `max_tokens: 5000`，不带 `thinking` 参数（`lib/review-runner.js:176`）；路由只在配了 `model_override` 时换模型名，其余原样转发（`router/router.js:776`）。
- 这两个模型默认先思考。材料一批最多 40000 字，思考很容易把 5000 个输出 token 用完，停在 `max_tokens`，正文还没开始写。现象（只有思考块、换一轮还一样、和材料量无关）都对得上。
- 证实不了：诊断只截回复**开头** 1500 字（`lib/review-runner.js:158`），`stop_reason` 和 `usage` 在 JSON 末尾，没截到。Claude Code 自己跑同样的模型没事，它给的输出上限远大于 5000。

### 改法

1. 诊断里单独记 `stop_reason`、`usage.output_tokens`、实际模型名（`reply.model`），不再只靠片段。
2. 提高输出上限（建议 16000 起，或做成配置页"审查输出上限"；新开关要按 AGENTS.md 第 10 条同时改两份默认值、`cleanConfig`、配置页、README、更新说明）。
3. `stop_reason=max_tokens` 且只有思考块：同一批自动重试一次（上限翻倍），重试算同一次审查，不占用户的重开预算；还不行，结果里写明"模型只输出思考、到了输出上限"和模型名，给一句可操作的话（换审查模型、或用兼容代理方式）。
4. 可选：请求里关思考（`thinking: {type: "disabled"}`）。网关和这两个模型认不认没有把握，**改之前在内网用 deepseek-flash 实测一次**，不认就不加。
5. 不从思考块里抽结论：思考不是正式结论，抽出来也不能记完整审查。

### 要加的测试

假路由（`VIBE_KIT_REVIEW_PORT`）回"只有 thinking、stop_reason=max_tokens"：第一次失败自动重试，第二次回正文 → completed；两次都只有思考 → failed，诊断里有 stop_reason 和模型名；只回思考但 `stop_reason=end_turn` → 不重试，照旧 model-empty。请求体里的 max_tokens 是新值。

## 4. review.js 多仓基线、非 OpenSpec 改动怎么审（#189、#187）

### #189 现象

壳子（工作区仓库）带两个子仓库，页面变更跑代码审查：`--project <子仓库> --base <子仓库的提交>`，回 `审查基线不是本地提交`。`work-baselines.json` 里只有同一壳子另一个变更的三仓基线，没有这个页面变更的。

### #189 根因

- `--base` 只有一个值，却对变更涉及的每个仓库根都用它（`lib/review-runner.js:117`），在没有这个提交的仓库里 `rev-parse` 失败，整轮抛错（`:119`）。`--project` 指子仓库也一样：仓库根来自 `S.projectRootsOf(change.dir)`（`:114`），和 `--project` 无关。
- 基线只在开工许可登记成功时写（`apply-scope.js:23` → `review-runner.baseline()`）。页面变更是在另一个变更的开工范围里接着改的（范围按仓库根放行业务代码，`apply-scope.js:38`），从没走过自己的开工，就没有基线。

### #189 改法

1. `--base` 支持多值：`--base <仓库相对路径>=<提交>`，可以写多次；只给一个不带等号的值时，只用在 `--project` 所在的仓库，其余仓库用登记的基线，都没有的照旧跳过并说"缺开工基线"。
2. 缺基线的提示列出每个仓库要的写法，例如 `--base jssslt-gwjh=11325fd --base .=32171c4`。
3. 审查技能说明（`vibe-kit/claude/skills/ttls-cross-review/SKILL.md:12-16`）补多仓写法。

### #187 现象和根因

不走 OpenSpec 的小修复（没有变更目录），模型给 review.js 编了一个变更名，回"没找到当前变更"（`lib/review-runner.js:233`）。工具其实支持：代码模式不带 `--change`、带 `--base`，审 `--project` 所在仓库从基线到现在的改动（`:114`）。审查技能说明只写了带 `--change` 的用法，没写这个。

### #187 改法

审查技能说明补一条"不走 OpenSpec 的改动：`review.js run --mode code --project <项目> --base <改之前的提交>`，不带 --change"；`没找到当前变更` 的报错里也带上这句。

### 要加的测试

两个仓库各自的 `--base` 都能审；单值 `--base` 只用于 `--project` 的仓库、另一个仓库用登记基线；不带 `--change` 的代码审查能出结果。

## 5. 命令文字里有 `review.js run` 就当成要审查（#187 第 6 点）

### 现象和核实

模型用 `feedback.js add` 记问题，正文里引用了 review.js 的命令，被"人工模式：先用 Ask 询问是否审查"拦下（无编号）。假用户目录实测（脚本见"复现 2"）：

| 命令 | 结果 |
|---|---|
| `node ".../feedback.js" add --kind 误拦 --what "跑 node review.js run --change x 被人工模式拦下"` | 拦 |
| `git commit -m "fix: 修 review.js run 的参数"` | 拦 |
| `node ".../feedback.js" add --kind 误拦 --what "跑 mvn test 被拦"` | 不拦（自测按拆好的命令段判断） |

### 根因

`lib/flow-policy.js:222`：`review` 用 `/review\.js["']?\s+run\b/.test(cmd)` 对整条命令文字匹配；同一行里自测（`testCommand`）已经按拆好的命令段判断。同类的 #153（审查预算按命令文字匹配）当时只改了 `budgetIssue`（`lib/review-runner.js:196`），这里没跟上。

### 改法

用 guard-commit 的 `splitCommand` / `words` 拆命令，只认"第一个词是 node、第二个词解析后是套件的 `tools/review.js`、第三个词是 `run`"的段，做法照 `decisionIssue()`（`lib/review-runner.js:207`）。自动模式那一支（`:229` 起）用的同一个正则，一起改。

### 要加的测试

上表三条，加上：真跑 review.js run 仍要许可；`cd x && node review.js run` 这类串着的仍认出来。

## 6. 钩子 12 秒预算用完、git 超时（#147、#121、#181）

出错时钩子都放行（fail-open），用户看不到；但 after-tool 的"验证证据"没记上，后面可能被要求重跑自测。出问题的多是壳子带五六个子仓库的项目、偏慢的电脑。

### #147：核对文件指纹超时（实测出原因）

- 栈：`after-tool 验证证据` → `W.fingerprint()` → `fingerprintOne()` 的逐文件循环（阶段"核对文件指纹"）。触发命令是 `devserver.js start`。0051 上还在出。
- `lib/workspace.js:40-56`：对**每个已跟踪文件**都先 `pathStatus()`（`lstat` + 两次 `realish()` 即 `fs.realpathSync.native`），然后才看"没改过就用索引里的哈希"（`:49`）。壳子模式下每个子仓库各算一遍（`:62-67`）。
- 本机实测（"复现 3"）：本仓库 3925 个已跟踪文件，`pathStatus` 全跑一遍 2.6 秒（约 0.67 毫秒一个）；`fingerprint(all)` 去掉 node_modules 后 1494 个文件 2.3 秒。几个子仓库加起来上万个文件、在慢一些的电脑上，12 秒不够。
- 改法：没改过的已跟踪文件直接用 `ls-files -s` 的哈希，不做 `pathStatus`；链接用 `ls-files -s` 的模式 `120000` 认。只对改过的、未跟踪的文件做 `pathStatus` 和读内容。改完指纹值对没链接的仓库应保持不变（加测试比对改前改后的哈希），否则已有的许可和审查记录会全部失效。

### #121：`spawnSync git ETIMEDOUT`（同方向，没在现场量）

- `lib/workspace.js:9`：每条 git 最多等 `min(5 秒, 剩余预算)`。`fingerprintOne()` 每个仓库要跑约 7 条 git（`rev-parse` 两次、`ls-files -s`、`diff --name-only`、`ls-files --others`、`rev-parse --show-object-format`、`config --get`），大仓库在慢盘上 `diff --name-only`（要刷新索引）超过 5 秒就超时。1017 修了 #110（查库、缓存命令误触发），这次触发的是正常的自测命令。
- 改法：同上减少逐文件开销后再看；超时的诊断里记是哪个仓库、哪条 git、等了多久，不然下次还是看不出来。壳子模式下只算这次相关的仓库，要看调用方，改之前先 Grep 全 `fingerprint(` 的调用方。

### #181：guard-commit 卡在"开始"阶段（证据不足）

- 命令只是 `node devserver.js start --help | head -40`。阶段名还是"开始"，说明 12 秒在 `analyze()` 第一次登记阶段（`hooks/guard-commit.js:1461`）**之前**就花完了。

## 7. 产出位置记好了还被拦，提示误导（#196）

### 现象

会话在壳子里启动，模型要写 `<子项目>\1.txt`，被"代码之外的产出放哪"拦下。照提示用提问框问，用户选"子项目根目录"，模型把位置写进 `<子项目>\.vibe\project.md` 的"产出位置"一节，先后试了 `- 接口返回示例/测试样例：仓库根目录`、`- 文档：./`、`- 文档：<子项目>/` 三种写法，还是拦，提示仍说"项目说明的'产出位置'里没有，用户这次也没说过"。最后申请放行，没问用户就放了。

### 根因

- **有意的设计**：模型在本次会话里自己加进项目说明的条目不算确认过（`lib/outputs.js:230-250`，`snapshot()` 记会话里第一次见到时的内容）。要靠用户说过的话（`mentioned()`，`:267`）。
- 用户的答案"子项目根目录"里没有目录名。`mentioned()` 认根目录只认"根目录 + 文件名"（`:278`，#58 加的），目录名认的是 `<子项目>/` 这类写法。所以认不出。
- 提示（`hooks/guard-output.js:25`）说"产出位置里没有"，还让"用户选定后把它记进 project.md ……然后写到那里"。模型照做以后，项目说明里**有**了，钩子却不认，提示也没说为什么，模型就反复改写法。

### 改法

1. 提示区分两种情况：项目说明里确实没有；有，但是本次会话里加的、用户没在提问框里选过这个目录。后一种直说"你在这个会话里自己加的不算；提问框的选项要写实际目录（例：`<子项目>/`），用户选了再写"。
2. 提问框的要求写得更死：选项必须是目录路径，不写"子项目根目录""仓库根目录"这种说法；根目录写成 `<子项目>/`。
3. 不放宽"会话里加的不算"这条（防止模型自己给自己定位置）。

### 要加的测试

会话里自己加了条目再写 → 拦，提示里有"本次会话里加的不算"；提问框选 `<子项目>/` → 放行；选"子项目根目录" → 拦，提示里要求写目录。
