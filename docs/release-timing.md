# 发版耗时

发版一次要多久、慢在哪、怎么提速。下面的数分三种：**实测**（标了怎么量的）、**按实测推算**、**估计**（没量过）。

数据来源：`dev/run-all.js` 每一轮的日志（`.vibe/tmp/run-all-<时间>/`，每套一行"通过 N（S 秒）"）、会话记录里的时间戳、2026-10-18 凌晨补做的几个小实验（做法写在"慢在哪"各条里）。

## 慢在哪（提速之前的分析）

1. **测试一套接一套地跑，机器一大半闲着。** 实测：单独跑 test-1008 时整机 CPU 平均 42%（去掉空闲时的 17%，测试自己约用 2 个核）。拿 test-1008、test-feedback0930、test-workflow1014 三套实验：一个接一个 245 秒；同时跑 94 秒（快 2.6 倍），全部通过，整机 CPU 平均 68%、最高 94%。3 路已经接近吃满，4 路多半快不了多少。`run-all.js` 现在只有钩子对比是同时跑的，注释里说别的套件"机器忙时有的测试会因时序出问题"，但没写是哪几套。
2. **调一次钩子要起一个 node 进程。** 测试支架 `H.hook` 每次都起进程（`dev/lib/harness.js` 第 271 行）。实测（用 `node -r` 预加载给支架套计时）：test-1008 的 84 秒里，调钩子 82 次共 64 秒（76%），平均每次 780 毫秒。拆开看（同样的输入，起进程调 vs 在工作线程里调，各 12 次取平均）：

   | 钩子 | 起进程 | 工作线程 | 起进程多出来的 |
   |---|---|---|---|
   | guard-commit（git status） | 296 毫秒 | 12 毫秒 | 284 毫秒 |
   | pre-edit（改代码） | 309 毫秒 | 21 毫秒 | 288 毫秒 |
   | guard-commit（git commit，要查提交方式） | 938 毫秒 | 676 毫秒 | 262 毫秒 |
   | verify-gate（收工检查） | 1681 毫秒 | 1125 毫秒 | 556 毫秒 |

   所以每次固定多 0.3—0.6 秒是起进程、载模块；剩下的是钩子本身在跑 git 这些，用户真用的时候也要等这么久。按 test-1008 的 82 次推算，起进程约占整套的三到五成（看调的是哪几个钩子）。
3. **新旧钩子对比的时间大半花在建测试用的 git 仓库上。** 每个输入、新旧两版各建一个仓库（写文件、git init、add、commit）。实测建一个平均 1272 毫秒，把建好的仓库整个复制一份平均 196 毫秒，复制出来的状态一样（干净、有那一次提交）。按 151 个输入 × 2 推算，光建仓库约 384 秒，占每份 590 秒的六成多。
4. **两份旧版的对比不占墙上时间。** 两份是同时跑的，各 590 秒，和单独跑一份（这次开发中跑过，约 600 秒）差不多。少比一份只省 CPU，不省等待时间。
5. **失败发现得晚。** 全量回归里 40 项不过、验收 1 项不过，全是过时的断言（提交方式默认改成关、打勾不查验法、自带 OpenSpec 多了技能），代码没有毛病：
   - 钩子对比开发中跑过，但最后改默认值之后没再跑；
   - 端到端和验收在这一批开发中一次都没跑，10-17 下午提交的行为改动（打勾不查验法、集成 OpenSpec）一直到发版才暴露。
   修完补跑用了 23 分钟。
6. **端到端三个版本一个接一个跑。** 实验：e2e-0930 三个版本一个接一个 126 秒，同时跑 55 秒，但 3 个里 2 个各挂 2 项。原因是 `run-all.js` 给三个版本传的假 redis 端口一样（18765，第二个假 redis 用 18766），三个版本抢同一个端口，不是机器跑不动；e2e-update 的假 GitLab 也是三个版本同一个 18748。同时跑时剩余内存最低降到 0.24 GB（IDEA 开着），内存是另一个风险。
7. **查库（H2）一套 9 分钟：286 条 `db.py` 命令，一条约 2.1 秒。**（2026-10-18 量的：`node -r` 预加载给测试里的同步子进程计时，整套 563 秒里 552 秒是这 286 次调用；再拿 cProfile 和单独的小实验拆一条命令。）一条 `query` 2.1 秒大致是：
   - 起 Java、连 H2、查：约 0.95 秒（光 `java -version` 是 0.18 秒）。每条命令起一次 Java 是用户的默认方式（后台执行器默认关），测试照这个测，不能省。JVM 加快起参数（`-XX:TieredStopAtLevel=1` 等）实测没区别。
   - Python 载模块：约 0.75 秒，其中 **0.36 秒是每次重新编译源码**：技能自己设了 `sys.dont_write_bytecode = True`（不在技能目录里留 `__pycache__`，安装器逐个文件比对），Claude Code 起的命令行里又有 `PYTHONDONTWRITEBYTECODE=1`（见 [claude-code-facts.md](claude-code-facts.md)），测试用的 Python 也不带编好的标准库，所以标准库和技能的模块每条命令都编译一遍；另有约 0.2 秒是模块载入时编译正则。
   - 起 Python 0.12 秒，其余零碎（查 git 忽略等）。
   实验：把字节码缓存放到技能目录外面（`sys.pycache_prefix` 指一个临时目录、去掉不写字节码的设置），技能目录照样干净，`query` 2.21 秒降到 1.72 秒，`--help` 1.13 秒降到 0.71 秒；整套按 286 条算能省 2 分钟左右。这是改技能的行为（用户每条查库命令也快 0.2—0.4 秒），没做，见下面"优化建议"。
   "没动过就不测"：判断规则做在 `dev/lib/affected.js`（见下面）。这套用到的套件文件连同它们 require 到的有 81 个（技能读 guard-commit 写的 `state/tool-flow.json`、调套件的 `tools/onboard.js`、`tools/drivers.js`，这些又 require 到 `session.js`、`guard-commit.js`），而这两个文件差不多每版都改，按这个规则最近 11 版一次都跳不了。
8. **没量的可能原因：** Windows Defender 的实时扫描开着，可能拖慢起进程、git、建临时目录这些小文件操作；加排除目录是安全设置，要不要试由仓库主人定，效果没测过。

## 优化建议

按"省得多、风险小"排。"依据"一栏写是实测还是估计。前三项 2026-10-18 凌晨做了（结果见"提速之后"），其余的 2026-10-18 下午做了（结果见"后面几项"）：工作线程调钩子、两条流程、验收同时跑照做；"没动过的模块不测"做了 `run-all.js --since`，但按现在的规则跳不了，放不放宽待仓库主人定（见表下）。最后两行是这次分析查库那套时新找到的，没做。

| 办法 | 依据 | 预计省 | 前提和风险 |
|---|---|---|---|
| 钩子对比：不带额外文件的输入（151 个里绝大多数，带额外文件的按代码粗数十几个）共用一个建好的仓库模板，每次复制一份 | 实测建 1272 毫秒、复制 196 毫秒；按输入数推算 | 每份 590 秒降到约 300 秒（只让同一个输入的新旧两版共用，降到约 430 秒） | 改 `dev/diff-hooks.js` 的 `project()`；每个输入还是各用各的一份，测试意思不变，风险小 |
| 单元测试分 3 路同时跑，怕机器忙的单独一路排队 | 实测 3 套快 2.6 倍、全过 | 29 分降到约 11—12 分 | 要先找出哪些套怕机器忙（多跑几次找时序失败）。端口不是问题：14 套写死了默认端口（18733—18795），但每套各不相同。内存只剩 1 GB 左右，配置页那几套各开一个 Edge，不要排进同一时段。每套自带的"桌面上冒没冒窗口"检查，同时跑时会把别的套弹的窗口记到自己头上，出了要按时间对一下是谁 |
| 端到端三个版本同时跑 | 实测 2.3 倍（126 秒→55 秒）；同时跑挂的那 2 项是抢端口 | 16 分降到约 7—8 分 | `run-all.js` 现在给三个版本传同一个端口（e2e-0930 都是 18765，e2e-update 都是 18748），改成每个版本传不同的就行，两个脚本本来就从参数接端口；IDEA 开着时内存紧，可能只能开 2 路，或发版时关掉 IDEA |
| 测试支架调钩子改用套件现成的工作线程（`kit/lib/hook-worker.js`，路由的 HTTP 钩子就是用它在同一个进程里跑钩子，`test-http-hooks.js` 测过和命令方式结果一样） | 实测每次省 0.3—0.6 秒 | 调钩子多的套快三到四成 | 用户开口、会话开始两个钩子要起路由，不能这样调；工作线程的环境变量要指假用户目录（`Worker` 的 `env` 参数）；钩子里用 `process.cwd()` 的地方要核对 |
| 不先跑一遍完整的基础回归：改完跑相关的几套（`--only`），确定发版直接全量 | 按这次的时间推算 | 约 40 分（那 8 套依赖旧默认值的，全量回归照样会发现，修完补跑那 9 分钟省不掉） | 相关的几套选漏了，失败挪到全量回归里才暴露 |
| 改了默认值、提示的说法时，开发阶段就拿一个 Claude Code 版本跑端到端、跑一份钩子对比，再搜一遍测试里引用了旧说法的地方 | 估计 | 时间省得不多（开发中多跑约 15 分钟，发版少补跑约 23 分钟），主要是发版那天不再"失败→修→补跑" | 要写进 `docs/release.md` 的流程，靠自觉 |
| 验收两条升级路同时跑（不同端口） | 实测 5 分 25 秒→2 分 53 秒 | 约 2 分半 | 小 |
| 没动过的独立模块（查库、redis、看页面）不测，脚本按上一个版本标签以来改了哪些文件判断，结果里写明跳过了什么 | 估计 | 查库那套 9 分钟（能跳的版本才省） | 要先给每个模块列清依赖（技能目录、读的配置项、guard-commit 写的条子格式）；条子格式改了的版本不能跳。10-17 用户提过，方案还没给 |
| 查库技能的字节码缓存放到技能目录外面（`sys.pycache_prefix`，不再关掉字节码） | 实测一条 `query` 2.21 秒→1.72 秒 | 查库那套约 2 分钟（摊到 3 路上约 40 秒）；用户每条查库命令快 0.2—0.4 秒 | 改的是技能的行为，要写更新说明；缓存目录放哪、会不会被清要定；Claude Code 设的 `PYTHONDONTWRITEBYTECODE` 要在脚本里盖掉 |
| 测试用的 Python 预编译标准库（`python -m compileall`） | 按 cProfile 估计 | 查库那套约 1 分钟 | 只改这台电脑的测试环境；Python 装在 AppData 下，要在仓库主人自己的 PowerShell 里跑 |

"没动过的模块不测"的规则（`dev/lib/affected.js`）：一个模块用到的文件 = 测试脚本连同它 require 的测试支架、技能目录、测试和技能调到的套件脚本连同它们 require 到的。按这个规则查库用到 81 个文件，里面的 `session.js`、`guard-commit.js` 差不多每版都改，最近 11 版（20261007.1217 到 20261018.0051，每版和上一版比）四个模块一次都跳不了。放宽成"只看模块自己的目录、测试脚本、直接调到的套件脚本，不往下追 require"：测试支架改了也照测的话，查库、起服务、看页面各能跳 4 次、查 redis 2 次；测试支架不算的话，查库、起服务各 6 次。放宽的风险是共用的库改了、模块的行为跟着变了却没测到（比如 `session.js` 的默认值、`lib/onboard.js` 的扫描）。

不再建议"把旧版的输出缓存起来"：复制仓库省得差不多，缓存还要管什么时候失效（测试输入、测试支架、git 和 Node 的版本变了都要作废），容易让对比悄悄失真。

当时推算前四项做完全量回归能降到 35—45 分钟；实际只做了前三项就到了 32 分 43 秒。再加流程上的两条（不先跑完整的基础回归、开发中先跑一个版本的端到端），同样一次发版能从 3 小时左右降到 1 小时左右，前提是发版那天不再出现一批过时的断言。
