## 二、自动更新：三种做法

| | 做法 | 同事的电脑要什么 | 主要代价 |
|---|---|---|---|
| A | GitLab 仓库里放**解开的包**，同事的电脑用 git 拉 | 装了 git，能读这个仓库 | 仓库里带着看页面用的依赖（压缩后 4.7 MB，基本不变） |
| B | GitLab 的发布页或包仓库里放 zip，用接口下载 | 一个令牌 | 令牌要发到每台电脑上；接口跟 GitLab 版本有关 |
| C | 共享目录里放 zip | 能访问共享目录 | 不走 GitLab，权限和记录都没有 |

**我建议 A。** 理由：

- 不用发令牌。同事平时拉代码怎么登录，这里就怎么登录。
- 每次只下载变了的文件。实测改两个文件的一版，只多下载 17 KB。
- 仓库的提交记录就是版本记录，回退就是退回上一个提交。
- GitLab 页面自带"下载 zip"，新同事第一次装就从那里下。

## 三、做法 A 的整条路

```
你（外网）   打包 → 拷进内网
你（内网）   解压 → 双击"发布到 GitLab" → 推进仓库（一版一个提交、一个标签）

同事的电脑   开会话、发消息时顺带看一眼：离上次检查超过 2 小时才去问仓库
             └ 有新版：后台拉到暂存处
                 └ 等路由空闲（没有正在跑的请求）：跑包里的 install.js
                     └ 状态栏提示"套件已更新到 xxx"
```

- **不花 token**：全是本机脚本。
- **不拖慢会话**：检查和下载都在甩开的后台进程里做，钩子只负责把它叫起来。
- **安装和手动双击完全一样**：开关、模型和 key、问题反馈、经验规则都保留。
- **配置页**加一张"自动更新"卡片：现在的版本、仓库里的版本、上次检查的时间和结果；按钮"现在检查""现在更新"；更新源的地址和分支。

### 要讨论的几个点

| 要定什么 | 选项 | 我的建议 |
|---|---|---|
| 发现新版之后 | 自动装 / 只提醒，我点了才装 / 关 | 默认自动装，挑空闲的时候。配置页里每个人可以改 |
| 多久检查一次 | 1 到 24 小时 | 2 小时 |
| 版本怎么比 | 跟着仓库走：仓库里的和装着的不一样就装 / 只升不降 | 跟着仓库走。这样你退回一版，大家自动跟着退 |
| 要不要试用通道 | 一个分支 / 两个分支：试用、稳定 | 两个。你一天发好几版，先推试用，你自己用过再转正 |
| 装坏了怎么办 | 不管 / 自动装回上一版 | 装完自检，不过就装回上一版，并记一条问题反馈 |
| 谁能发布 | 谁都能推 / 保护分支 | 保护分支，只有你能推 |

### 风险和边界

- **自动更新等于自动执行仓库里的代码。** 所以仓库必须只有你能推。模型不能触发更新，也不能改更新源：更新程序放在它跑不了的位置，更新源只能在配置页里改。
- **路由重启会断请求。** 安装时路由要重启一两秒，这时正在发的请求会断，走路由的检查会被跳过。所以要挑空闲的时候装。
- **手动装了测试版的人会被装回去。** 选了"跟着仓库走"就是这样。这种情况把自动更新改成"只提醒"。
- **连不上、没权限时安静失败。** 不弹登录框，不卡住，配置页上写清原因。
- **比这一版更老的套件没有自动更新。** 每个同事要先手动装一次带自动更新的版本。

### 实测过的

拿本机的空仓库代替 GitLab 测的，网络上的耗时会比这里长。

| 事实 | 结果 |
|---|---|
| 包推进仓库之后的大小 | 解开 32.0 MB，仓库里 4.7 MB |
| 第一次拉到暂存处 | 1.1 秒 |
| 问一次仓库有没有新版 | 0.13 秒 |
| 再发一版（改两个文件）之后拉取 | 0.34 秒，多下载 17 KB |
| 拉下来的文件和原包逐字节一样 | 是，换行和 GBK 的 bat 都没被改 |
| 直接跑暂存处里的 install.js 能从旧版升上来 | 能 |
| 整个更新放在后台进程里跑，桌面上有没有冒出窗口 | 没有 |
| 仓库要登录、电脑没登录过 | 5 秒左右失败，不弹登录框，不卡住 |
| 暂存处最长的路径 | 约 181 个字符，没超过 Windows 的限制 |

## 四、问题反馈也走 GitLab

可以。现在反馈存在每台电脑的本地，你要一台一台去配置页导出。走 GitLab 之后，同事的反馈自动集中到一处，你一次收走。

从内网拷出来交给我这一步省不掉，但只用拷一份汇总。

| | 做法 | 同事的电脑要什么 | 你得到什么 |
|---|---|---|---|
| F1 | 用 git 推进一个**反馈仓库**，每台电脑一个分支 | 对反馈仓库有推的权限 | 所有人的反馈文件集中在一个仓库里 |
| F2 | 每条反馈建成一个 GitLab 议题 | 一个令牌 | 议题：有通知、能讨论、能标"已在某版修复" |

**我建议 F1，和自动更新用同一套办法。**

- **反馈仓库和更新仓库分开。** 更新仓库大家只读，反馈仓库大家可写。
- **每台电脑推自己的分支。** 互相不冲突，不用合并。
- **什么时候传**：记了新问题之后，下一次开会话或发消息时在后台传。传不上去就下次再传。
- **传什么**：本地那份已经遮过密码、token、内网地址的记录，和现在导出的内容一样。
- **你怎么收**：双击"收反馈"，它拉下所有分支，合成一份汇总，格式和现在配置页导出的一样。收过的记下来，下次只出新的。
- **开关**：配置页里每个人可以关掉上传。

想要议题的跟踪能力，可以只在你这边加：收反馈时把汇总后的条目建成议题。这样只有你一个人需要令牌。

### 要讨论的点

- **同事之间能互相看到反馈。** GitLab 里能推就能读。反馈里有项目路径、被拦的命令、钩子日志的片段。不能接受的话，要换成每人一个仓库，或者用议题的"机密"选项。
- **这是从同事电脑上自动往仓库里推东西。** 推的只是反馈文件，推到专门的仓库，和代码无关。但要让同事知道有这件事。

### 不用告诉我的

**仓库地址和分支名不用给我。** 我这台机器连不到内网，知道了也用不上。它们在内网第一次双击"发布"时填一次，记在你的电脑上，并且跟着发布的包带给同事。

你要在 GitLab 上做的准备：

1. 建两个仓库，一个放更新，一个放反馈。
2. 更新仓库：同事能读，保护分支只有你能推。
3. 反馈仓库：同事能推。
