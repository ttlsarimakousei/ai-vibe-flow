### 实施时改了的

| 方案里写的 | 实际做的 | 为什么 |
|---|---|---|
| 项目级规则先只在本机 | 跟着仓库提交。规则文件更新后收工检查催一次提交（`docs: 更新经验规则`） | 你定的 |
| 规则编号用流水号（L12） | 用文字的指纹（L916d46） | 规则文件要进仓库：几个人各自加规则再合并，流水号会撞 |
| 会话开始时每天查一次过时的规则 | 改成写规则文件的那一刻顺手查，另有 `lesson.js tidy` | 规则文件进仓库了，会话一开始就自动改它，会平白多出没提交的改动 |
| 升成用户级之后，项目里那一条去掉 | 留着 | 项目规则是全团队共用的，不能因为你一个人升了用户级就从同事那里拿走 |
| 可选：第一版只收候选 | 做成了一档开关"只收集"，默认是"开" | 门槛是两次、项目规则你能直接改，风险不大；想稳一点就在配置页切到"只收集" |

测试结果：9 套 392 项全过，其中端到端在 Claude Code 2.1.120 和 2.1.259 上各跑一遍；和上一版的钩子对比了 81 个输入，75 个没动的地方输出一字不差。

## 一、现在的情况：不会

套件 20260925.1411 里，审查发现的问题走到"改掉、记一笔"就结束了，没有下一步。

| 审查结果去了哪 | 之后有没有人再读它 |
|---|---|
| 会话记录里（审查代理的回复） | 没有，会话结束就没了 |
| 这个变更的 `revisions.md`（起因写"审查"） | 没有，跟着变更归档 |
| 修复提交的信息（`fix: …（源自 <变更名> <任务号>）`） | 只有 `tools/trace.js` 溯源时读 |

套件里现有的三样东西都不是干这个的：

- **问题反馈**（`feedback/`）记的是套件自己的毛病，收给改套件的人。
- **提示规则**（配置页里填的）是你手写的，不是从审查里来的。
- **规范**（`~/.claude/vibe-kit/rules/`）也是手写的，而且每个请求都带着。

所以同一类问题，下一个变更里模型照样会犯，审查照样再抓一次，每次都花一个子代理的钱。

## 二、Claude CLI 里这类机制叫什么

官方统称 **Memory（记忆）**，下面分三样。2.1.120、2.1.259、2.1.283 三个版本我都用假模型实测过，行为一致（细节见第八节）。

| 名字 | 放哪 | 什么时候进上下文 | 谁写 |
|---|---|---|---|
| **CLAUDE.md** | 用户级 `~/.claude/CLAUDE.md`；项目级 `项目/CLAUDE.md`；本机私有 `项目/CLAUDE.local.md` | 会话开始就全带上，每个请求都带 | 人 |
| **Rules（规则目录）** | 用户级 `~/.claude/rules/*.md`；项目级 `项目/.claude/rules/*.md` | 没写 `paths` 的：会话开始就带上。写了 `paths` 的：**读到匹配的文件才带上，一个会话只带一次** | 人 |
| **Auto memory（自动记忆）** | `~/.claude/projects/<项目>/memory/`，只有项目这一层 | 索引 `MEMORY.md` 会话开始就带上（前 200 行或 25KB） | 模型自己 |

和你要的东西最接近的是"自动记忆"，但它不合用：

- 只有项目一层，没有用户级。
- 记不记、记什么全看模型自觉，和审查没有关系。
- 它默认是开着的，套件也没关它，所以内网多半一直开着（我看不到内网，这一条是按模拟内网的实测推的）。它的说明每个请求都占系统提示：2.1.259 占 2,317 字符，**2.1.120 占 12,762 字符，差不多是系统提示的一半**。
- 索引文件最多能长到 25KB，全是每个请求都带的。这正是你担心的"越攒越多"。

真正合用的是**带 `paths` 的规则目录**：项目级、用户级都有，按文件类型按需加载，平时不占上下文。缺的只是"谁来往里写、写多少、什么时候删"，这部分套件来做。

## 三、怎么判断项目级还是用户级

一句话：**跟着代码库走的是项目级，跟着人和技术栈走的是用户级。** 逐条问下面五句，先中哪句算哪句。

| 先问 | 是的话 | 例子 |
|---|---|---|
| 只是这一次的疏忽吗（笔误、漏看一个字段）？ | 不记 | "字段名打错了一个字母" |
| 能用脚本查出来吗？ | 不写规则，做成检查 | "提交信息格式不对" |
| 里面有这个项目特有的名字吗（表、类、接口、模块、业务词）？ | **项目级** | "sys_user 没有 dept_name 字段，部门名要联 sys_dept 查" |
| 换一个同样技术栈的项目，这条还成立吗？ | **用户级** | "MyBatis 的 foreach 传空列表会拼出 `in ()`，调用前先判空" |
| 和技术栈无关，是做事的方式？ | 交给你决定要不要写进全局约定 | "改了接口返回结构，全局搜一遍调用方" |

模型（尤其是内网模型）判断这个不可靠，所以方案里**不让模型定级**，由脚本按证据定：

1. 一律先当项目级。
2. 脚本在规则文字里找项目特有的名字（在项目里真的搜得到的类名、文件名、表名）。找到了，就永远留在项目级。
3. 同一条经验在**两个不同的项目**里都成了规则，而且不含项目特有的名字，才列为"可以升用户级"，等你在配置页点一下。

另外还有一个和级别无关的选择：项目级规则是**跟着仓库提交**（同事的 Claude 也能看到）还是**只在本机**。这个要你定，见第六节。

## 四、方案

### 4.1 整条路

```
审查代理报问题
  └ 主模型逐条核实（现有流程）
      ├ 不成立：revisions.md 记理由（现有）
      └ 成立：改掉、提交（现有）
          └【新】这条换个任务还会再犯吗？会，就记一条经验（一句话）
                └ 脚本收进候选（不进上下文）
                    └ 同一条第二次出现：升成规则，写进规则文件
                        └ 以后读到这类文件时，Claude CLI 自动带上
```

花 token 的只有两处：记经验那一轮，和规则被带上的那一次。其余都是本机脚本。

### 4.2 记经验

- **谁记**：主模型，在处理完审查意见的同一轮里记。不另开子代理。
- **怎么记**：调套件的工具，一条一句话。

```
node "$HOME/.claude/vibe-kit/tools/lesson.js" add --file <出问题的文件> --when "<什么情况下>" --do "<要怎么做>" --from "<变更名> <任务号>"
```

- **不靠自觉**：收工检查加一条。这个会话里有一次审查报了问题、模型也改了，却既没调过这个工具、也没说"没有需要沉淀的经验"，就拦一次让它补。每次审查只拦一次。
- **模型怎么知道有这个工具**：写在 `/cross-review` 技能里（调用技能时才加载）和收工检查的那句话里。全局约定不加字。
- **工具会拒收的**：超过 120 字的；带"视情况、尽量"这类含糊词的；和全局约定、项目 CLAUDE.md 里已有的话基本重复的。

### 4.3 候选和规则分开放

| | 放哪 | 进上下文吗 | 进仓库吗 |
|---|---|---|---|
| 候选（只出现过一次的） | 项目的 `.vibe/lessons/candidates.jsonl` | 不进 | 不进 |
| 项目级规则 | 出问题的文件所在仓库的 `.claude/rules/vibe-lessons-<类型>.md` | 读到这类文件时 | 你定 |
| 跨项目的记录 | `~/.claude/vibe-kit/lessons/` | 不进 | 不进 |
| 用户级规则 | `~/.claude/rules/vibe-lessons-<类型>.md` | 读到这类文件时 | 不进 |

规则文件长这样。次数、出处写在单独一行的注释里，实测注释不进上下文，模型只看到正文：

```markdown
---
paths: "**/*.java"
---
# 这个项目里写 Java 要注意（审查里反复出现过的）

<!-- L12 次数=3 最近=2026-09-28 出处=add-export 2.3、fix-order 1.2 -->
- 调 OrderMapper.selectByIds 之前先判空列表：传空列表会拼出 in ()，SQL 报错
```

规则文件本身就是"生效规则"的唯一来源，人可以直接改、直接删行。没有注释的行当作你手写的，脚本不动它。

壳子结构下，规则写进**子项目自己的仓库**。实测在壳子里启动时，读到那个子项目里的文件才会带上它的规则；在子项目里启动也一样生效。

### 4.4 什么时候升成规则

- **门槛**：同一条经验在两个不同的变更里出现过。只出现一次的留在候选里，不进上下文。
- **怎么算"同一条"**：脚本先按文字相似度找出最像的几条，列给模型看，模型说"就是这条"才合并。模型只需要读三句话。
- **升用户级**：见第三节，要两个项目的证据，再加你点头。

### 4.5 钩子和保护

- 模型不能直接改 `vibe-lessons-*.md`（用户级和项目级都拦），只能通过工具。否则它可以绕过条数上限。你手改不受限。
- 用户级规则文件、跨项目记录纳入"禁止改套件"的保护范围。
- 卸载、装新版不删候选和规则。

### 4.6 配置页

加一张"经验规则"卡片：各项目和用户级现在生效的规则、候选、等你确认的用户级规则、被标成"没管住"的规则；能删、能改字、能点升级；门槛和上限可调。

## 五、上下文怎么控制

| 手段 | 做法 |
|---|---|
| **平时不占** | 所有经验规则都带 `paths`，没读到这类文件就不加载。每个请求都带的内容一个字不加 |
| **进门有门槛** | 出现两次才成规则 |
| **每条限长** | 一句话，最多 120 字。原因和出处放注释里，不进上下文 |
| **每组限量** | 一种文件类型一个文件，最多 10 条、1,200 字。满了挤掉最久没再出现的那条，退回候选 |
| **过时自动退** | 规则里提到的类、文件、表在项目里搜不到了，自动退役（每天最多查一次） |
| **没用的不留** | 规则生效之后同样的问题又被审出来两次，标成"没管住"，建议改成脚本检查或者重写 |
| **能脚本查的不写规则** | 转成一条套件问题反馈（类型"建议"），由改套件的人做成检查 |
| **全局约定不自动加** | 和文件类型无关的经验只列在配置页，要不要写进约定由你定 |

分组固定为：Java、SQL 和 Mapper、前端、提案文档、其他（按扩展名）。

最坏情况的开销：

| 项目 | 什么时候 | 大约 |
|---|---|---|
| 记经验 | 审查确认了问题的那一轮 | 多一到三次工具调用，每次输出约 100 token |
| 项目级规则 | 一个会话里第一次读到这类文件 | 每组最多 1,200 字，一个会话一次 |
| 用户级规则 | 同上 | 每组最多 1,000 字，一个会话一次 |
| 每个请求都带的 | 不变 | 0 |

对照：现在全局约定每个请求带约 5,900 字；自动记忆的说明在 2.1.120 上每个请求带 12,762 字符。

## 九、边界和还没验证的

- **只有读文件才触发规则**。模型没读过任何同类文件就直接新建一个，规则不会带上。改已有文件不受影响，因为改之前必须先读。
- **内网模型听不听、写得好不好，没验证过**。规则送到了不等于照做；它记的经验可能太泛。这要内网用过才知道，所以建议第一版可以先只收候选。
- **压缩之后**按需加载的规则会丢，要等再读到同类文件才重新带上（官方文档的说法，没实测）。
- **团队共享时**多人各自升级规则，规则文件会有合并冲突。文件是一行一条，冲突好解，但要人来解。
- **公司规定**"不许用 Claude Code 的各种新特性"。规则目录是 2025 年 12 月就有的稳定功能，而且比写进 CLAUDE.md 省 token。公司要是不认，可以改成走套件现有的"读到文件时提醒"那条路（同样按需、同样在 2.1.120 上验证过），只是规则没法跟着仓库共享。
