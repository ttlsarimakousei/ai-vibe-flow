## 一、严重（会直接出事故或者测错）

### 1-1 push 确认、公司红线、提交规范在条件块、子 shell、循环里全部漏掉【已复核】
- 位置：`kit/hooks/guard-commit.js` 拆命令（44-70）、找命令名（136-141）、认 git 子命令（183-203）
- 问题：拆命令时不认 `( ) { }`，也不认 `if / for / do / try / ForEach-Object / xargs` 这些开头，命令名被当成 `if`、`{`、`do`，里面的 git 命令整条没查。
- 什么情况下出事：Claude Code 的 PowerShell 工具说明里教模型用 `A; if ($?) { B }` 串联（PS 5.1 没有 `&&`），所以 `git commit -m "feat: x"; if ($?) { git push }` 是模型的标准写法。套件没给 PowerShell 配权限规则，这一路只靠这个钩子。
- 证据（实测，都放行）：PS 的 `…; if ($?) { git push }`、`try { git push } catch {…}`、`'a','b' | ForEach-Object { git -C $_ push }`；Bash 的 `(cd frontend && git push)`、`for d in a b; do git -C "$d" push; done`、`ls -d */ | xargs -I{} git -C {} push`、`bash push-all.sh`（脚本里写的 push）。同样的写法下，壳子里的 `git add -A`、`git add 子项目`（gitlink）、不合规的提交信息也全部放行。
- 改法：push 加一道保守兜底——去掉 heredoc 正文后，同一段命令里出现 `git … push` 就要确认；要执行的脚本文件（.sh/.ps1/.bat，64KB 以内）里有 `git push` 也要确认。拆命令时把 `( ) { }` 当分隔、控制关键字当前缀去掉。这些写法都加进测试。

### 1-2 模型能绕过套件的保护：关掉禁改、打开自动放行、清空问题反馈【已复核】
- 位置：`guard-commit.js:373-379`（调路由 /api 的检查）；`router/router.js:925-931、952-959`；`kit/lib/feedback.js:247-264、301-305`
- 问题：
  - 调路由接口的检查只认命令里字面写出的 `127.0.0.1|localhost:<端口>/api`。端口前面加 0、用变量拼地址、写个 node 脚本去调，都拦不住；路由那边只认一个固定请求头，任何本机程序都能带。实测用 `http://127.0.0.1:015730/api/kit/config` 把 kitBypass 改成 auto、kitLock 改成 false，路由照收。
  - config.json、state/bypass.json 是明文，程序运行时拼出路径再写，钩子看不到；事后也没有任何地方会发现。
  - 通行证：用的时候看的是通行证文件里自带的"免确认"字段，不按当前配置重判；也不核对会话（A 会话申请的，B 会话做同样的操作能用掉）。
  - `/vibe-kit/hook/*` 对本机调用不设防，能拿伪造的输入调钩子（没实测）。
- 改法：命令里出现 `x-vibe-router`、`/vibe-kit/hook/`、路由端口（按数值比较）就拦；路由把每次 /api 写操作记进日志和问题反馈；配置页写 config.json 时另记一份哈希，会话开始、用户开口时比对，不一致就提醒用户并按默认值处理 kitLock、kitBypass；通行证按当前配置重判、核对会话，并在会话记录里核对确实跑过 `feedback.js bypass <编号>`；安装时给 hooks/、lib/ 记哈希，会话开始时校验。

### 1-3 问题反馈会把 token、密码、内网地址原样记下来（我这两天的代码）
- 位置：`kit/lib/feedback.js:58-65`（redact）、`223-234`（blocks.json 原样存命令）
- 问题：`Authorization: Bearer <jwt>` 被第一条规则只把 "Bearer" 换成 ***，token 本身留着；24 种常见写法里 19 种能看到原文：Basic 认证头、`curl -u admin:pw`、JSON 里的 "password"/"token"、`mysqldump -p…`、`redis-cli -a`、`sqlplus scott/tiger@…`、`jdbc:oracle:thin:scott/tiger@…`、`secret_key=`、`DB_PASS=`、中文"密码是 xxx"、Cookie 里的 JSESSIONID；内网 IP 完全不遮。这些记录是要被收走、交给别人看的。
- 改法：Bearer/Basic 规则放最前；键名按子串匹配（passw、pwd、secret、token、apikey、private_key），允许带引号；补上面那些写法；遮私网 IP 和内网域名；写进 blocks.json 之前也遮一遍。

### 1-4 壳子里用 `--cwd 子项目` 起服务，改了代码也发现不了，一直测旧代码
- 位置：`kit/tools/devserver.js:36、129-141、216`
- 问题：判断"起服务之后代码改没改过"时，是在当前目录（壳子）跑 git status；子项目在壳子的 git 看来只是一个目录，里面改了什么看不到。复用判断也不比较 `--cwd`，同名同端口换一个子项目会复用另一个子项目的服务。
- 证据（实测）：壳子是仓库时，改完 order-api 的代码再 start，输出"已经在跑，启动之后代码没改过，直接用"，服务返回的还是旧的。
- 改法：按实际运行目录往上找它的 git 根去查；记录里存 cwd，参与复用判断。

### 1-5 多轮审查的记录全机器共用：别的项目没审完，这里每轮都被催复审（只在开了多轮审查时）
- 位置：`kit/hooks/verify-gate.js:392-401、395、370`
- 证据（实测）：项目 X 的审查报了 2 条还没复审，7 天内在项目 Y 改任何文件，每轮收工都被拦"再让 vibe-reviewer 审一遍改动点"，而且不说是哪个变更——模型只能猜着开子代理，烧额度。
- 改法：只看当前目录能看到的、这份会话记录里出现过的审查；话里写上变更名。

### 1-6 审查意见全部驳回会卡死：永远审不完，打勾、归档一直被拦（只在开了多轮审查时）
- 位置：`verify-gate.js:369、392-400`；`guard-spec.js:83-89`；`guard-commit.js:318-321`
- 证据（实测）：审查报了 2 条，模型核实都不成立、只在 revisions.md 记了理由（技能允许这么做）→ 打勾被拦"多轮审查还没审完"→ 复审照旧报同样的问题，轮数涨到 4（上限 3）也不问用户。全自动模式下这一类不给放行，直接停摆。
- 改法：审查之后只动了 revisions.md 也算处理完；到上限就直接走"问用户 / 全自动按原则定"。

## 二、中

### 会被错误拦住、流程走不下去
- **2-1 前台审完代码、同一轮里紧接着归档，被错拦成"还没审过"**（`guard-commit.js:301-324`）：归档检查前没有先把会话里的审查同步进记录（打勾检查做了）。实测复现；模型会以为套件错了去申请放行或者再审一次。改法：归档检查里先同步一次。
- **2-2 审查提示里提到第二个变更名，这次审查就不算**（`kit/lib/session.js:917-923`）：第二行"变更：…"写的相对路径对不上，退回全文找变更名，材料里写了"参照 add-import 的写法"就命中两个。实测复现。改法：优先解析第二行（相对、绝对路径、名字都认）。
- **2-3 打勾前的验法判断两头不准**（`session.js:712、727-729、594`；`guard-spec.js:103-107`）：错拦——验法写 `.vibe/qc.bat src/main/java/…/OrderService.java`，路径里的 `java` 被当成要跑 java 命令，照原样跑了还是被拦；放水——验法写成一句话时跑个 `openspec status` 就能打勾，收工的"改了代码没验证"也把 `openspec status`、`devserver.js status` 当成验证过。实测四条都复现。改法：只看命令开头那个词；写了 .vibe 脚本就要求跑那个脚本；验证命令里去掉 openspec 和套件自己的工具。
- **2-4 产出位置检查把代码资源当成"文档、表格"**（`kit/lib/outputs.js:23-36、70-84`）：新建 `src/main/resources/banner.txt`、`src/test/resources/data/orders.csv`（测试数据）、`public/robots.txt`、`i18n/messages.md` 都被拦；全自动下还把测试 csv 放到 `.vibe/pending/`，测试读不到。改法：代码目录（resources、src/test、public、static、assets）里的所有类型都不管，不只 .sql。
- **2-5 devserver 的 status、再次 start 会把还在启动中的服务结束掉**（`devserver.js:222-226、260-263`）：进程活着、端口没通就当"没在跑"。大型 Spring Boot 起得慢，模型顺手 status 一下就被结束，可能永远起不来。实测复现。改法：进程活着、端口没通 = 还在启动，status 只报告，start 接着等。
- **2-6 后台审查发出后退出了 Claude Code，再 `claude --continue`，打勾永远被拦**（`session.js:949-960`；我这两天的代码）：子代理随进程没了，通知永远不来，一直算"还在后台跑"。实测 20 小时后还拦。改法：发出超过 30 分钟、或之后有过会话恢复，就不算还在跑，提示重审。

### 提醒错了、催错了
- **2-7 壳子里 git pull 下来的同事的变更，被当成"进行中的变更"**（`task-anchor.js:185-202`；`verify-gate.js:416`）：每条消息都带"进行中的变更：zhang-add-print…这个提案还没审过"；全自动下还被催"li-refund 还有 3 项没做完，接着做"。实测复现。改法：只提、只推进这个会话动过的变更。
- **2-8 全自动模式下，收工检查不管交接线和网关上限**（`verify-gate.js:331、413-414`；`task-anchor.js:217-222`）：上下文到 76% 收工只催"接着做"；离网关上限只差 10% 时什么都不说就停下，没有交接记录；过线后每个后台通知都叫它再写一遍交接记录。实测复现。
- **2-9 用户按 Esc 叫停后，后台通知一到，提醒让它回去接着 apply**（`task-anchor.js:237-241`；我这两天的代码没处理这一处）。实测复现。改法：后台通知那一轮不出打断提醒。
- **2-10 Git Bash 的 `taskkill //F //IM node.exe` 能把路由一起结束**（`guard-commit.js:401-403、166`）：Git Bash 里为了不被转换路径，惯用 `//F`；`cmd //c "taskkill /F /IM node.exe"` 也放行。改法：Windows 原生命令先把参数开头的 `//` 归成 `/`。
- **2-11 "起服务要走 devserver"漏掉常见写法**：`nohup mvn spring-boot:run &`、`env X=1 mvn spring-boot:run`、`npx cross-env … vite`、`cmd //c start /b npm run dev`、PS 的 `Start-Process npm.cmd -ArgumentList 'run','dev'`、`npm --prefix frontend run dev`、`pnpm -C`、`yarn --cwd`；而且整条命令里只要出现 devserver.js 就整条不查。改法：跳过 nohup/env/cross-env/start 前缀，拆 Start-Process 参数，认目录参数，只对调 devserver.js 的那一段免检。

### 能被轻易跳过的
- **2-12 OpenSpec 链上的空子**（`guard-spec.js:55、34-43、164`；`verify-gate.js:262`）：会话里更早读过任何文件，提需求这一轮探索完就能直接写提案；目录里一天内有过 handover.md 也放行（公司 70% 就交接，这条规矩大多时候等于关着）；tasks.md 第一次写入就全是 `[x]`，审没审、验没验都不查。

### 慢
- **2-13 壳子里每次收工要等 2～3 秒，哪怕只回答了一个问题**（`verify-gate.js:148-170`）：每次都对所有子项目跑 `git status -uall`；6 个子项目各 1500 个文件就 3.2 秒；单个 git 超过 8 秒会被悄悄结束，这一项等于没查。改法：这一轮没有写文件、跑命令就跳过；只查这一轮碰过的仓库。
- **2-14 壳子里写 design.md、tasks.md 要 12～14 秒**（`session.js:450-484`；`guard-spec.js:145-163`）：每个只写了文件名的路径，要在每个根目录各走 2 万个目录项，壳子根目录走完每个子项目又走一遍。HTTP 方式超过 25 秒就当放行。改法：每次调用只建一次文件名索引（git ls-files），不重复走子仓库，设总时间上限。

### 安装和卸载
- **2-15 点过"接上"再卸载，Claude Code 就连不上了**（`install.js:383-419`）：卸载停了路由，但 settings.json 里的 ANTHROPIC_BASE_URL 和占位 token 还在，原来的网关地址（记在 claude-link.json 里）没恢复。实测复现。改法：卸载时先自动做一次"断开"。
- **2-16 安装做到一半出错，只打出英文堆栈，套件新旧混杂**（`install.js:421-481`）：实测把 settings.json 设成只读后升级，钩子已是新的、登记还是旧的、旧路由还在跑。改法：主流程包 try/catch，中文说明原因和怎么办；bat 先检查 install.js 在不在（常见：在压缩包里直接双击）。

## 四、每个请求带给模型的字数（实测，默认开关）
- 全局约定每个请求都带：7,299 字（中文 4,715），约 3,200～4,400 token。构成：基础约定约 2,700 字，OpenSpec 规范约 3,000 字，Git 提交 1,395 字。开全自动 + 多轮审查时 8,044 字。

## 五、体系层面欠缺什么

按对你们的价值排。先写结论，再写依据。

1. **后端改动的"验证"基本等于"能编译"**。看页面的场景执行器只有页面动作，没有直接调后端接口、断言返回值的步骤，也没有"等某个接口返回并检查"的步骤。OpenSpec 的每条规格都有 WHEN/THEN 场景，却没有东西把它变成能跑的检查。建议加"接口场景"：和页面场景同一个执行器，写 JSON（请求 → 状态码、返回字段、必要时查库），devserver 起服务后脚本执行，结果进"验：…"。
2. **项目知识不能在团队里共享**。`.vibe/project.md`（快检命令、编码情况、产出位置、踩过的坑）只在本机、不进仓库，同一个项目每个同事各自 /onboard，写出来的不一样，别人踩过的坑你还得再踩。建议分两层：团队共享的一份提交进壳子仓库，本机的一份只放本机路径和账号；会话开始两份都带上。
3. **做完一个变更，没有交给人的东西**。人工测试发现问题 → 溯源 → fix（源自…）这条回路前面缺一环：给测试同事的测试清单（从规格的 WHEN/THEN 生成）和改动摘要。建议归档前自动生成，放到产出位置。
4. **分发与版本**：包里没有更新日志（你刚才让我列两个版本改了什么，就是这个缺口）；同事装的是哪版、有没有新版都看不到；问题反馈要你一台台去收。建议包里带更新日志、配置页显示版本和更新内容；可选配一个内网共享目录当"更新源 + 问题收集箱"。
5. **没有效果数据**：路由有按天按模型的用量，钩子有拦截计数，问题反馈有记录，"（源自…）"让返工能统计，但没有按需求（变更）合起来——一个需求花了多少 token、多少次请求、被拦几次、申请放行几次、归档后返工几次。没有这个，判断不了这套流程是在省事还是添乱，也不好向上交代。
6. **提交前不查敏感信息**：提交检查管格式、管整仓 add、管过程文件，不看内容。模型把数据库密码、key、内网地址写进配置文件再提交，没人拦。建议提交前扫一遍这次 add 的内容，命中常见模式就要用户确认。
7. **没 Node 的机器装不上**：安装脚本要求 Node 18+（`node -v` 不过就退出），每个检查也是 `node "…"` 跑的。立项时记过"后端机器不一定有 Node"。建议随包带便携版 node（约 30 MB），或者至少给离线安装包——先看同事机器的情况再定。
8. **每天 4000 次请求的提醒只在配置页**：平时不开配置页就看不到。建议接近时在状态栏显示。
9. **给使用者的一页纸**：README 是给维护者的长文档（几百行）。同事需要一页：装了会看到什么（拦截、确认框、收工检查）、被拦了怎么办、怎么反馈问题、怎么升级。
10. **套件的自我保护是尽力而为**（见 1-2）：真正可靠的是"改了能发现"，而不是"改不了"——篡改检测比继续加拦截规则划算。
