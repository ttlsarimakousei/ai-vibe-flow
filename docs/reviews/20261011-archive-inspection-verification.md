# 归档临时查看的修复与验证

用户反馈模型查看 JAR 时把解包条目留在项目根。此次修复适用于临时检查，不以文件是否被 Git 忽略、是否准备提交作为例外。

## 原因与改动

原来的整理检查能判断备份、日志和直接写文件，却没有判断解包命令的落盘目录。补查发现 Windows 完整程序路径经包装命令重建后会丢失反斜杠，带空格的程序路径也可能丢失引号，导致漏判或误拦。

| 入口 | 本次处理 |
|---|---|
| JAR、ZIP、WAR、TAR、7z、PowerShell 和 Python 的直接解包命令 | 项目内临时解包要求 `.vibe/tmp/<事由>/`，不接受项目根、源码目录或 tmp 根 |
| 目录列表或条目读取结果落盘 | 重定向、`tee` 和 `Out-File` 同样检查事由目录 |
| 工作目录与路径 | 跟踪常见包装命令的工作目录；目录联接核对实际位置；保留 Windows 完整路径与引号边界 |
| IDEA 与全自动 | 共用命令检查；关闭套件文件保护不跳过整理检查；重复坏命令不会自动放行 |
| 审查 | 审查代理只读查看归档，主会话负责在事由目录准备必要材料 |
| 提示与配置 | 复用现有整理开关；全局约定只在已有一句中补充“和解包样本” |

正式导入项目资源遇到误拦时，可以说明用途并使用现有问题反馈放行机制。需要交付给其他协作者的提案材料仍按提案材料规则放进变更目录。

## 适用边界

- 优先使用只读目录列表或流式读取条目，避免产生临时文件。任意脚本内部写文件、动态路径和构建工具自己的行为无法由这道静态检查完整判断，模型仍须遵守目录约定。
- 本机 JDK 17 的 `jar xf <归档> -C <目录>` 报错，不能把它当成兼容旧 JDK 的解包方案。兼容写法是指定工具工作目录，再用归档完整路径解包；支持 `--dir` 的 JDK 才使用该选项。
- 常规构建产物和项目外的正式安装保留原行为。此次没有检查归档内部恶意条目，也没有把目录检查当成归档内容安全校验。
- 没有接触真实模型网关、业务数据库、用户的 IDEA 项目或真实凭据，也没有执行真实推送。
