**值得保留的设计**

- 把编号、Git 状态、任务打勾和归档前置条件交给脚本，减少模型自行猜流程。
- 命令钩子和 HTTP 钩子共用 `handle()`，比两套实现各自修补容易维护。
- Windows 后台进程隐藏窗口，编码和用户配置归属有专门规则，适合内网同事的实际环境。
- 经验规则带路径限制和数量、长度上限，避免无条件扩充所有请求的上下文。
- 合并 push 限定未推送的线性提交，独立 index 重建后核对最终 tree，保留备份引用并拒绝强推。源码见 [merge-push.js](../../vibe-kit/kit/lib/merge-push.js)。本次没有发现这段逻辑的已确认缺陷，也没有把它当成完整验收过。
- IDEA MCP 安装使用独占锁，并在写客户端配置前检查变化；既有保护入口测试通过。它体现了用户配置归属和并发保护的意识。

## 已确认问题

P1 表示应优先修复的授权或敏感信息风险，P2 表示会影响可靠性的缺陷。等级依据触发条件和后果，不代表已发生真实数据事故。

| 编号 | 等级 | 问题 | 证据 |
|---|---|---|---|
| R1 | P1 | 明确否定 apply，仍进入全自动实现阶段 | 三种否定说法均复现 |
| R2 | P1 | 讨论提交、归档机制，被当成允许执行 | 用户确认函数和实际钩子均放行 |
| R3 | P1 | 已纳入的连接转为非开发环境后仍可选用 | 探索器判非开发，解析器仍加载且非只读 |

| R5 | P2 | 并发读改写覆盖另一条已成功写入的状态 | 两个正常退出的进程最终只保留一条 |

**R1：否定开工被当成开工**

位置：[session.js](../../vibe-kit/kit/lib/session.js) 的 `APPLY_HARD` 和 `applyIntent()`，第 119、128 行；[task-anchor.js](../../vibe-kit/kit/hooks/task-anchor.js) 的阶段判断；[guard-ask.js](../../vibe-kit/kit/hooks/guard-ask.js) 的提问拦截。

`APPLY_HARD` 只要匹配到“开工”或 `apply` 就返回肯定，先于提案修改判断。用户明确说“不做 apply”时，也能把 `plan` 改成 `apply`。随后钩子按照全自动阶段禁止提问，并允许调 apply 技能。

复现前提：打开套件全自动开关，会话已经进入提案阶段，存在未归档变更。分别提交以下用户消息，再检查阶段、提问和 apply 的钩子结果。

| 用户消息 | 实际阶段 | 提问是否被拦 | apply 是否被拦 |
|---|---|---|---|
| 先不要执行 apply，提案还没确认，请先修改提案 | apply | 是 | 否 |
| apply 先缓一缓，需求还要调整 | apply | 是 | 否 |
| 不要开工，先整理需求 | apply | 是 | 否 |

钩子还会输出“开始 apply：全自动模式开着”。本次只检查钩子输出，没有让模型实际实施任务。

影响：用户要求继续沟通时，套件反而允许自动实现并阻止提问。这直接违背“用户明确同意开工后才全自动”的约定。

修复方向：先处理否定、取消和延后，再判断肯定执行；把明确开工许可与对话阶段推断分开。自然语言、斜杠命令、提问框答案和 IDEA/CLI 入口应共同遵守同一许可状态。补充“不要执行 apply”“apply 先缓缓”“还没确认”等反例。

**R2：话题词被当成提交或归档许可**

位置：[session.js](../../vibe-kit/kit/lib/session.js) 的 `SAID`、`userSaid()`，第 225、231 行；[guard-commit.js](../../vibe-kit/kit/hooks/guard-commit.js) 的 `archiveIssue()`、`consentIssue()`，第 556、1405 行。

提交和归档的肯定规则是宽泛的词匹配。否定和问句过滤没有排除“提交机制有问题”“归档逻辑有问题”这样的讨论。push 已有较严格的执行意图判断，这两处没有同步。

| 用户最后一句 | 确认函数结果 | 被检查的操作 | 实际钩子结果 |
|---|---|---|---|
| 提交机制有点乱，先解释一下目前的策略 | 同意提交 | `git commit` | 放行 |
| 归档逻辑有问题，先帮我检查一下 | 同意归档 | `openspec archive demo --yes` | 放行 |

归档复现准备了已完成任务和有效审查记录，以隔离用户确认这道检查。只向钩子提交待检查命令，没有真正执行提交或归档。

影响：普通讨论可能解除需要用户确认的操作门槛。提案、普通长任务和全自动收尾都依赖这个公共判断，因此应查全部调用方。

修复方向：为提交和归档要求明确执行意图，排除解释、讨论、引用和问题描述。许可应记清操作、对象和对应用户消息，并支持撤销；不能只因为最近一句出现了操作名就授权。

**R3：连接退出开发环境后没有退出可用列表**

位置：[onboard.js](../../vibe-kit/kit/lib/onboard.js) 的开发连接筛选，第 731 行；`mergeDb()` 处理旧连接，第 589 行；`mergeRedis()` 标记 `gone`，第 650 行；[dbconf.py](../../vibe-kit/claude/skills/ttls-db-crud/scripts/dbconf.py) 的 `_parse()`，第 213、233 行；[redis.js](../../vibe-kit/claude/skills/ttls-redis/scripts/redis.js) 的连接加载，第 152 行。

新增连接会筛开发环境，但旧连接不再匹配时只写提醒。数据库解析器仍加载该段，默认 `readonly` 为 `false`。Redis 的 `gone` 也没有参与可用连接筛选。

复现：在临时项目中先用 `spring.profiles.active=dev` 生成数据库和 Redis 配置，再把同一配置改为 `prod`，按探索流程重新筛选并合并。

| 检查项 | 实际结果 |
|---|---|
| 最初识别出的开发数据库 | 1 |
| 改为 prod 后识别出的开发数据库 | 0 |
| 改为 prod 后识别出的非开发数据库 | 1 |
| INI 中旧连接 | 保留，只增加提醒注释 |
| Python 解析器加载旧连接 | 1 |
| 解析后的 readonly | false |
| Redis 中旧连接 | 保留，并标记 gone |

本次没有连接数据库，也没有证明真实生产库已被写入；确认的是执行器仍将已判非开发的旧配置作为可用、非只读连接加载。

影响：用户或模型后续选连接时仍可能选到不符合“只自动纳入开发环境”的条目，存在误选、误写风险。

修复方向：明确判为非开发的自动管理连接，应停止参与执行选择并移入隔离记录；人工维护的连接保留用户控制。来源暂时读失败与明确转为非开发要分开处理，避免误删。列表、执行器、后台进程和 Redis 共用可用性判断。

**R4：错误正文没有在日志和接口出口统一脱敏**

位置：[router.js](../../vibe-kit/router/router.js) 的 `snippet`，第 433 行；失败日志和 `record()`，第 578、579 行；普通错误透传，第 669、672 行；`/api/usage` 和 `/stats`，第 1005、1077 行。

上游错误正文只缩短、折叠空白，没有清除敏感值。不能假设公司网关或第三方兼容接口永远不会回显 key。

复现：假路由使用明确标为假的测试 key，假网关返回 401，并在错误正文中回显同一个假 key。检查请求响应、本机诊断接口和日志。

| 检查项 | 假 key 是否出现 |
|---|---|
| 本次模型请求最终响应 | 否，最终返回合成的 429 错误 |
| `/stats` | 是 |
| `/api/usage` | 是 |
| `router.log` | 是 |

本次全部凭据是测试字符串。本次客户端响应没有泄漏；源码中的非切换错误分支还会原样透传错误正文，这条分支需要补验证。

影响：凭据可能进入持久日志和用量诊断接口，违反“不打印、不记录 key”的约定，并扩大支持排障时的泄漏面。

修复方向：在所有落盘、诊断接口和客户端错误出口统一脱敏。既要识别敏感字段，也要替换已配置凭据的精确值，不能只依赖某种 key 前缀。JSON 错误、纯文本错误和流内错误都应有反例测试。

**R5：单次文件完整不等于并发更新不丢失**

位置：[session.js](../../vibe-kit/kit/lib/session.js) 的 `writeState()`、`updateState()`，第 638、657 行。相关调用包括审查记录、任务打勾记录、使用次数和拦截统计。

临时文件加 rename 保证单次写入不会留下半截 JSON，但两次更新仍可能读到同一旧值，再各自覆盖整个文件。

复现使用两个临时 Node 进程，同时向 `reviewed.json` 写不同的键。回调中用屏障让两者都完成读取后再写，稳定制造同一读写窗口。

| 检查项 | 结果 |
|---|---|
| 子进程退出码 | 0、0 |
| 应保留的独立记录 | 2 |
| 最终保留的独立记录 | 1 |

这是人为控制时序的并发探针，证明该更新方法存在丢失窗口，不代表每次日常运行都会发生。

影响：多个会话、命令钩子和 HTTP 工作线程并行时，可能丢审查记录、任务时间或统计。表现为明明审过却被催、计数不准，或后续判断依据不完整。

修复方向：采用跨进程排他更新、集中单写服务，或将互不相关的记录拆分；同时处理锁回收和崩溃恢复。不能只再增加读文件重试。`updater.js` 的锁也有“先检查再写”的同类窗口，本次没有复现双重安装，应单独验证。

**性能和上下文实测**

安装到假用户目录后测量生成的全局约定；耗时测量使用本机 Node `v24.21.0`、同一小型临时仓库和 `guard-commit` 的 `git status --short` 输入。

| 指标 | 本次测量 |
|---|---|
| 默认安装生成的全局约定长度 | 7133 个 JavaScript 字符单元 |
| 默认安装生成的全局约定 UTF-8 大小 | 16496 字节 |
| 原模板长度 | 2497 个 JavaScript 字符单元 |
| 每种暖态方式样本数 | 12 |
| 命令钩子中位耗时 | 132 毫秒 |
| 命令钩子最大耗时 | 216 毫秒 |
| 常驻工作线程中位耗时 | 3 毫秒 |
| 常驻工作线程最大耗时 | 5 毫秒 |
| 工作线程首次调用耗时 | 155 毫秒 |

工作线程数据测的是宿主直接调用计算，未包含 HTTP 传输和 Claude 的处理。不能据此宣称 HTTP 全链路只有 3 毫秒，也不能推及大型会话、慢磁盘和网络目录。

字符和字节不是 token。没有使用实际模型的 tokenizer 和计费记录，因此本次不提供 token 或费用降幅。

效率建议按证据排序：

1. 保留工作线程复用和规则按需加载，避免退回每次启动 Node 或把全部经验放进全局提示。
2. apply 时自动记录审查基线和各子项目的改动清单，减少审查者找提交、读错范围和漏审后返工。
3. 对真实大变更统计审查耗时、所读文件、模型请求和重复审查次数，再判断慢在工具、材料还是模型。
4. 固定约定的进一步压缩需做任务成功率对照，避免删掉少量文字后增加一次阻断或返工。把低频说明放到相应钩子时机，优先保留短而明确的全局底线。
