# 修改指导：用户说法测试表

2026-10-17 由 Claude 写。

## 为什么要做

套件的许可几乎都靠认用户原话：审查、自测、提交、推送、归档、开工、跳过审查、接受问题、交接、验收、重开审查预算，共 11 类，定义在 `kit/lib/intent.js` 的 `TOPIC`，问答框的回答另走 `session.js` 的 `SAID`。认漏了，人工模式会把用户明说的要求当成"先问"；认多了，就是越权（提交、推送、归档都在里面）。

10-16 的端到端发现"审一下"没被认出（`c3ee650` 修）。现在只有开工、提交、归档、推送 4 类在 `dev/test-workflow-intent.js` 里有成表的正反例，另外 7 类没有。

## 要做的

1. 把说法表从测试代码里拿出来，放成数据文件，例如 `dev/fixtures/intent-phrases.json`：

   ```json
   { "review": { "yes": ["审一下", "..."], "no": ["要不要审一下？", "..."] }, "test": { ... } }
   ```

   `test-workflow-intent.js` 读这个文件，逐条用真实的 `intent.explicit` 判断，并用 `session.userSaid` 走一遍会话记录的入口；以后加说法只改数据文件。
2. 补齐 7 类的正反例。第一版按下面的起点写，再从内网导出的议题、钩子流水账里能找到的真实说法补充：

   | 类 | 应该算（yes） | 不该算（no） |
   |---|---|---|
   | review | 审一下、审查一下、帮我审审、复审、再审一次、审核一下代码、修完审一下 | 要不要审一下？、审查机制有问题、审查太慢了、不用审了、先别审、他说要审查 |
   | test | 跑一下测试、自测一下、编译看看、把服务起起来、启动项目看看、看一下页面、验证一下、跑起来 | 测试怎么写？、测试失败了、不用测了、先别跑测试、测试用例在哪 |
   | reviewSkip | 这次不审了、跳过审查、不做代码审查 | 跳过审查会怎样？、审查能跳过吗 |
   | reviewAccept | 接受这条问题、这条不改 | 这条要改吗？ |
   | handover | 交接、写一份交接记录 | 交接记录在哪？、交接机制 |
   | accept | 自测通过、验收没问题 | 自测通过了吗？、验收怎么做 |
   | reviewBudget | 重开审查预算、重新审查 | 预算还剩多少？ |

   表里的说法先按"人会怎么说"写，再跑现在的代码看哪些认错了。认错的逐条判断：是改 `TOPIC`、`PREFIX`、`NOUN`，还是这句话本来就有歧义、应该保持"先问"。有歧义的放进 no，并写明原因。
3. 跨类的组合要测：
   - "审一下然后提交"：审查和提交都算；
   - "提交并推送"：提交和推送都算；
   - "先审查，不要提交"：审查算，提交不算。
4. 问答框的回答单独一组：问题里有"审查"，回答"好""可以"算；回答"先不用"不算。还要覆盖两种问答格式（`Your questions have been answered:` 和 `User has answered your questions:`），以及结构化的 `answers` 字段。

## 改代码时的规矩

- 推送、归档、提交的认法只能收紧，放宽要先问主人：这三类认错了就是越权。
- 审查、自测认漏了的后果是"多问一次"，可以放宽，但必须同时补 no 例，防止认多。
- 每加一条认法，都要有一条在改之前的代码上失败的 yes，和至少一条防误认的 no。
