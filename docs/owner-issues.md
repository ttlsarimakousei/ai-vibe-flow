## 1. IDEA 的 MCP 不要再拦

原话："vibe不要再拦截任何idea的MCP相关，现在版本连调用MCP都拦截"。

线索（记录时顺手看到的，没验证）：`lib/idea-tools.js` 的 `handle()`（guard-commit 对 `mcp__.*` 调它）：没写 `projectPath`、没适配的工具（末尾兜底"尚未适配套件检查"）、查库类、`get_run_configurations`、运行参数覆盖都直接拦；`lib/flow-policy.js` 的 `actionIssue()` 对 `execute_run_configuration` 按自测要人工许可；`hooks/after-tool.js` 会把 IDEA 工具的返回脱敏改写。

## 2. 用 IDEA 起项目，已经在跑的要先管

原话："用idea的MCP启动项目的时候，要是已经有在启动着的项目了你就告诉我一声，或者你直接重启，重启的时候不是重新打开一个，而是将原来的关了，或者直接将原来的重新启动，现在一启动，之前的你就不管了，搞的能启动好多个，各种端口占用，然后你再来解决问题，这个逻辑就不对"。

要的行为：起之前先看同一个项目、运行配置有没有在跑；有的话说一声，或者关掉原来的再起、或者直接重启原来那个。不能再多起一份。

线索（没验证）：`devserver.js start --idea` 已有"调试方式起、改过就停掉重起"的逻辑；模型直接调 MCP 的 `execute_run_configuration`（普通 Run）时没这层，IDEA 的 MCP 停不了 Run 起的进程，再调一次就多起一份（`lib/idea-run.js` 开头的实测说明）。和第 1 条一起看：不拦 MCP 之后，这条要换成不拦的做法。

## 3. 不再拦"密码明文"这类

原话："这个vibe套件不用在乎什么密码明文之类的，不要在这方面进行拦截了"。

修之前先找全哪些地方在拦或在改写，并跟仓库主人确认范围：AGENTS.md 硬规矩第 6 条（套件令牌、模型 key 的保护"只能收紧"）和第 7 条（库、redis 口令不经过模型、不上命令行）跟这条冲突，这两条放不放宽由仓库主人定。

线索（没验证）：IDEA 那边拿"可能带口令"当理由拦 `get_run_configurations` 和运行参数覆盖；查库、redis 技能写着"口令不经你的手"；`claude/rules/20-git-commit.md` 还写着"提交时查到了会弹确认"，而 guard-commit 开头说 2026-10-17 起提交已经不查像密码的内容（文档和代码可能对不上）。

## 4. 让连 IDEA 的 MCP、也连上了，套件不主动检查，照样拦

原话："之前idea的MCP被拦截，可能是因为这个IDEA工具尚未适配套件检查，如果说首次没检查到，我都描述的idea的mcp连一下，你连上了都不主动检查一下，而是选择被vibe套件拦下来，这是不是反逻辑"。

要的行为：用户已经说了连 IDEA 的 MCP、也连上了，首次没检查到的要主动检查一遍再用，不能连上了还按"这个 IDEA 工具尚未适配套件检查"拦下。
