## 最终讨论结论

| 话题 | 最终要求 |
|---|---|
| 配置分类 | 区分全局配置、OpenSpec 需求自动、Apply 自动；两自动开关独立 |
| 本次默认值 | 本次安装及从旧版升级都关闭两个自动模式；保留任务进度；之后使用者重新开启的选择不应反复重置 |
| 需求自动资格 | 用户已有一定描述，先实际探索。目标、边界、业务规则、验收不清楚就沟通，不能仅因开关开启而自动猜需求 |
| 简单与复杂修改 | 从聊天和探索判断。简单修改直接实施；复杂修改逐步完善 OpenSpec 变更，审查和自测仍服从当前模式 |
| 逐步产出 | proposal、specs、design、tasks 分步完成，各产物审修结束再继续；人工是否审查由用户选择 |
| 审查次数 | 每个文档产物、每个完成的整组 1.x 独立计数；材料分片数不是轮次，不跨点共用上限 |
| 自动审修 | 自动核验、修改、复验；整组审修结束再下一组；到上限仍有问题不能算通过，需沟通 |
| 主动审查 | 用户明确要求审查就执行，不能因自动审查上限拒绝 |
| 人工模式 | 审查、自测、复验先 Ask，已有明确要求直接执行；列完整问题，再逐条选推荐修改、不改或自行输入 |
| 人工放弃 | 放弃就继续，不记录未审查、未测试或待办，不反复催，也不能把放弃登记为通过 |
| 需求提交 | 需求与 OpenSpec 变更是同一套文档，敲定后提交一次，不拆成两套或两次阶段提交 |
| 衔接 Apply | 两模式均自动且当前范围允许实施时，需求定稿提交后自动 Apply；否则 Ask 提供 Apply、继续修改、暂不执行 |
| 提交提醒 | 关闭自动提交仍允许提醒；人工实施根据情况或用户明确要求提交，不能把提醒等同自动提交许可；自动提交档位只管 Apply |

### 交接第 2—4 项的核实结论

| 风险 | 结论 |
|---|---|
| 主动审查超过自动上限 | 代码路径对：自动模式到限后 `actionIssue` 要求当前用户明确要求，`review.js run` 本身不按上限拒绝。**没有专门测试**"自动模式到限 + 用户明确要求"这一组合，建议补 |
| IDEA `execute_tool` 转发 | 确认是缺陷，已修 |
| 部分失败不能登记为通过 | `run` 只在 completed 时写审查记录；`settled` 要 completed 且 0 条，或 resolved。`resolve` 的漏洞已修 |
| 人工放弃后不反复催 | 同一输入只提示一次（按会话 + 指纹）。代码再改会再问一次，见"待主人确认" 2 |
| 每轮只计一次 | `begin` 计一轮，`noteResult` 对同一次不再加，已有测试 |
| `syncReviewRounds` 仅凭 revisions 判完成 | 属实：审查报了问题后只改了该变更的 revisions.md，就记成 done（不看写了什么）。影响面小：它只在自动模式的旧多轮记录里起作用，而自动模式已不许启动兼容代理。建议退役兼容多轮时改为只认 `review.js resolve` 的逐条处理，不急 |
| `resolve` 验证材料仍有效 | 逐点：输入变了且没有 fixed 就拒绝，`settled` 还核对 `resolvedFingerprint` 和 `materialInputs`；非逐点：指纹不符拒绝。现在另要求 completed |
| `autoReport` 在用户验收阶段漏报告 | 确认是缺陷，已修 |
| 自动逐组约束 | 打勾 2.x 时硬检查 1.x 已完成并审修；写下一组代码不硬拦，靠收工提示（有未收尾的点时不催下一项）。下一组的文件可能和上一组重叠，硬拦写代码容易误伤，建议保持现状 |

## 待主人确认（2026-10-16 已答复并实现）

仓库主人 10-16 答复了下面 4 个问题，另补一项"快检在对话里问"，记在 [decisions.md](decisions.md)；实现和测试见 [修改指导](guide-20261016.md) 末尾的完成情况。下面保留当时的问题原文：

1. **编译、快检算不算"自测"**。现在人工模式下 `mvn compile`、`npm run build`、`node --check` 都按自测处理，用户最近一句话没要求测试就先 Ask。好处是严格照"自测先 Ask"；代价是人工模式下模型每改一次都要问能不能编译。另一种做法：编译、类型检查、静态检查算实现的一部分，跑测试、起服务、看页面才算自测。
2. **人工模式每次改了代码都问一次审查、自测**（按代码指纹去重：同一份代码不再问，代码一变再问）。用户说过"放弃就继续，不反复催"，这算不算反复催需要确认。
3. **人工模式打勾不再检查验法**（"人工放弃自测不阻止完成任务"的直接结果）。tasks 里的"验："在人工模式只是说明。
4. **人工模式归档不要求代码审查**（`guard-commit.archiveIssue` 里 `cfg.autoMode ? codeReviewIssue(...) : ''`），但提示文字没跟上：拦截时仍写"任务全部打勾 → /ttls-cross-review 审代码 → 修掉成立的问题并验证 → 再归档"；任务都勾了、等用户说归档时写"任务都打了勾、代码也审过了"，没审过也这么说。要么按模式改说法（建议：人工模式写"审查与否由你决定"，并如实说审过没有），要么人工模式也要求审查，取决于主人。

## 给接手 AI 的工作方法

这个仓库之前一直由 Claude 维护。下面是维护时一直在用的做法，10-16 的核对也照这个来，供接手的 AI 照着做：

1. **先跑全量，再动手**。交接里的失败数、"已修待复验"都可能过时。先拿到这台电脑上真实的失败清单，再排顺序。跑的时候不改被测文件，这段时间读代码、写文档。
2. **每个失败先归类，写下依据**：
   - 真缺陷：改代码，补一条能在旧代码上失败的测试。
   - 用户新决定替代的旧预期：改测试，并在测试旁注释是哪一天、哪条决定。不能为了过而放宽成一个更宽的正则；改完的断言要和原来检查同一层意思（例：1008 的"打勾不攒"改成核对新约定里"实现任务做完就打勾，提交按档位"，不是删掉）。
   - 测试环境问题（状态在用例之间串、输入已不现实）：修输入，让结果确定（例：diff-hooks 给收工用例独立会话号；提案提交用例先暂存产物）。
   - 拿不准的：列进"待主人确认"，不要选一个最容易过的解释。
3. **看完整输出，别只看第一行**。`run-all.js` 每个失败只打印原因的第一行。1007 那一项第一行只有"复审"，完整输出里还有一句"接着提交"，这才发现两句提示互相矛盾。单独跑那一套，或者看 `diff-hooks` 日志里的新旧全文。
4. **一个失败常常牵出旁边的真问题**。改断言之前问一句：新输出在用户眼里对不对？10-16 修的 8 个缺陷里有 3 个是这样顺带找到的（execute_tool 绕过、复审和提交同时催、只改页面什么都不问）。
5. **同一件事的两处判断要同一口径**。收工检查（verify-gate）和提交检查（guard-commit）都判断"审查收尾了没有"，只改一处就会出现一边催提交、一边拦提交。改任何判断前先 Grep 同义的地方。
6. **新测试必须证明不是空转**：`git archive HEAD vibe-kit | tar -x -C <临时目录>`，把这份修改前的套件当旧版目录传给测试，确认只有新断言失败。测试不收旧版参数的，用一个预加载脚本换掉 `makeHome` 的来源：

   ```js
   const H = require('<仓库>/dev/lib/harness');
   const orig = H.makeHome;
   H.makeHome = (name, from, config) => orig(name, from || process.env.OLD_KIT, config);
   ```

   然后 `OLD_KIT=<临时目录>/vibe-kit node -r <预加载脚本> dev/test-1007.js`。
7. **行为改了，文字同一次改**：约定模板、钩子提示、配置页、README、更新说明。改完 Grep 旧说法（例："一律拦""全自动模式下直接拦下""各一次"）。提示要写"看到什么才算过"，内网模型只被告知"不对"会原地打转。
8. **区分用户原话和自己的推导**。decisions.md 标"用户定的"不能改回去；实现时自己补的取舍（例：编译算自测）要在交接里写成"实现选择，待确认"，不要写成用户要求。
9. **不确定就少改**。宁可留一条写清楚的待办，也不要为了"做完"而改一处没把握的行为。10-16 没动的几处都列在上面，附了理由。
10. **提交按问题分**：一个缺陷一笔，测试跟着实现；措辞类测试更新、文档、发版生成物各自分开。只 add 自己改的文件。
