## 最终讨论结论

| 话题 | 最终要求 |
|---|---|
| 配置分类 | 区分全局配置、OpenSpec 需求自动、Apply 自动；两自动开关独立 |
| 本次默认值 | 本次安装及从旧版升级都关闭两个自动模式；保留任务进度；之后使用者重新开启的选择不应反复重置 |
| 需求自动资格 | 用户已有一定描述，先实际探索。目标、边界、业务规则、验收不清楚就沟通，不能仅因开关开启而自动猜需求 |
| 简单与复杂修改 | 从聊天和探索判断。简单修改直接实施；复杂修改逐步完善 OpenSpec 变更，审查和自测仍服从当前模式 |
| 逐步产出 | proposal、specs、design、tasks 分步完成，各产物审修结束再继续；人工是否审查由用户选择 |
| 审查次数 | 每个文档产物、每个完成的整组 1.x 独立计数；材料分片数不是轮次，不跨点共用上限 |
| 自动审修 | 自动核验、修改、复验；整组审修结束再下一组；到上限仍有问题不能算通过，需沟通 |
| 主动审查 | 用户明确要求审查就执行，不能因自动审查上限拒绝 |
| 人工模式 | 审查、自测、复验先 Ask，已有明确要求直接执行；列完整问题，再逐条选推荐修改、不改或自行输入 |
| 人工放弃 | 放弃就继续，不记录未审查、未测试或待办，不反复催，也不能把放弃登记为通过 |
| 需求提交 | 需求与 OpenSpec 变更是同一套文档，敲定后提交一次，不拆成两套或两次阶段提交 |
| 衔接 Apply | 两模式均自动且当前范围允许实施时，需求定稿提交后自动 Apply；否则 Ask 提供 Apply、继续修改、暂不执行 |
| 提交提醒 | 关闭自动提交仍允许提醒；人工实施根据情况或用户明确要求提交，不能把提醒等同自动提交许可；自动提交档位只管 Apply |
| 需求修订 | 任一阶段发生变化，同步受影响的需求、设计、任务、代码、用例、图；添加批注及业务修订理由；相关旧结果失效 |
| 文档长度和图 | 取消 250 行硬上限；复杂需求、设计必要时画图帮助分析 |
| tasks 的内容 | 放项目交付任务，不放套件起服务、审查安排、自测调度和内部诊断；实际测试代码仍是交付内容 |
| 需求回归 | 需求阶段准备验收场景，设计阶段补完整用例，修订时核对受影响场景；自测围绕这些用例，最终交付清单、用例和实际结果供用户验收 |
| vibe-kit 与 Agent | Agent 理解需求、编写代码和核验意见；vibe-kit 提供配置、确定性检查、证据、审查执行和流程节点；OpenSpec 保存需求、设计和任务 |
| 合并推送 | 使用者项目按具体任务或独立修复归组，保留定稿、验收、归档节点；只整理未推送历史，无可靠归属不合并。本开发仓库保留细分提交直接推送 |
| 图文同步 | 以后修改流程或机制，要同步对应流程图和说明 |
| OpenSpec | 最终决定：不集成、不自动安装或升级、不在打包前检查最新版。低版本不支持指令时提示使用者自己升级 |
| 数据库和 MiniMax | 本轮不修数据库反馈和 MiniMax 请求问题。日常专项只测受影响部分；仓库发版规程仍要求隔离环境的全量测试，包括临时 H2 |

前面的“集成 OpenSpec 1.2.0、主动升级、打包前查新版”“需求和提案各提交一次”“放弃后记录未审/未测”“整套产物写完再审”“一个通用审查次数”均已被后续决定替代。

目前实现选择每点默认 3 轮、可配置 1—20；这是当前实现值，不是用户原话。具体接口和状态见源码。

上述人工 Ask 约束是套件在使用者项目中的产品行为。本开发仓库按用户和 AGENTS.md 的授权直接开发、测试、本地提交，真实 push 要主人确认。用户已在 2026-10-15 明确要求推送本次开发交接；该次授权不自动覆盖接手后的新批次或内网安装包发布。
