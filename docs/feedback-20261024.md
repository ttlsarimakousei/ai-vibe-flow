另外查出三处：

- 选项后面的"（推荐）"：模型写的推荐项都带它，短肯定（`YES_SHORT`，`lib/session.js:230`）带上它就认不出，"可以（推荐）"不算同意。
- 自己打字回答的提问框（2.1.299 实测），结果文字是 `The user answered: …`，不是 `User has answered your questions: …`。`lastUserVoice` 靠结构化的 `toolUseResult.answers` 认得出，但 `ANSWERED`（`:174`）认不出，需求自动的"最近一次提问框还没回答"（`lib/flow-policy.js:111`）会一直成立。
- 一句"提交""推送"只能用在一个仓库上（`lib/permissions.js:35`，"这次许可已经用于另一个目标"）：壳子里两个子项目都改了，提交第二个就被拦。用户说"改完提交""修好再提交"时，许可在用户开口时就按当时的代码版本登记（`:48`），模型改完再提交就是"确认后输入发生变化，需要重新确认当前版本"（#215 的第一句拦截）。

改法（在 feedback-20261021.md 第 1 类的基础上）：

1. 提问框答案：去掉"（推荐）"再判断；含这个话题的动作词、不含否定就算；问题里有动作词、答案是短肯定或这个话题的执行词（自测：跑、执行、重跑、再跑、重试；审查：审、重试、再审；提交：提、提交；推送：推）也算。"就这样定稿""直接写下一份"不含动作词，照旧不算审查许可。
2. 原话：自测、审查放宽"跑 / 做 / 来 / 再 + 动作词"（"跑复验""做次复验""来一遍审查"）和"范围词 + 动作词"；审查认"复验 + 文档名"（复验 specs / 提案 / 设计）、"ttls-reviewer""cross-review"。提交只补直接写命令的（"git commit""git add/commit""git add 然后 git commit"），归档、推送不放宽。
3. 自测、审查往回看本轮（决定已定）；提交、归档、推送仍只看最后一句。
4. `ANSWERED` 认 `The user answered:`。
5. 提交、推送：同一句许可可以用在几个仓库上，每个仓库一次；话里点了子项目名的只用在点了名的那几个。"改完提交"这类先改后提的说法，开口时不登记版本，到真正提交时再登记。
6. 拦截提示写清用户怎么答才算：例"选项写成'自测（范围）'和'不用'，用户选了自测就直接跑"。

## 2. 开工许可（#214）

现象：用户在对话里打"开工"，打勾被"我还没说开工"拦；调 openspec-apply-change 技能也拦；用户自己敲了 /opsx:apply，打勾还是拦。项目里当时有两个没归档的变更（feat-019、opt-group-survey-list，都是这个会话动过的）。

根因：`grant()`（`lib/apply-scope.js:16`）在"话里没点名、有多个变更、会话动过的也不止一个"时失败，返回"有多个变更，请明确 apply 哪个变更"，但用户开口钩子只把阶段留在 plan（`hooks/task-anchor.js:111`），打勾、调技能的提示都只说"我还没说开工"，原因丢了。模型看不到原因，用户看不懂为什么说了开工还不行。另外 pre-edit 没有先补读提问框里的开工答案（旧第 2 类）。

改法：

1. 认开工目标时多看两处：模型在用户这句话之前最后说的那段话里只点了一个变更名的，用它（和提问框的问题一样当上下文）；打勾、改产物时，要改的就是哪个变更，用那个。都定不了才失败。
2. 失败原因带到拦截提示里："有两个变更 a、b，你说开工时没点名：让用户说'开工 a'，或者在提问框的选项里写明变更名"。
3. pre-edit 在 `scope.check()` 之前先 `confirmApply(j)`（旧第 2 类的改法）。

## 3. 收工检查（#219、#220）

#219：会话在新建 smart-material-distribution，只 `cat` 了旧变更 university-contact-… 的 proposal.md、tasks.md 参考格式，收工时被要求"当前 university-… 的 tasks 写完了……用 Ask 问"。假用户目录复现：一条 `cat openspec/changes/old-ref/proposal.md` 就让 old-ref 出现在收工提示里。根因：`hooks/verify-gate.js:723` 把命令文字里带 `openspec` 的 Bash 都当成在做这个变更（本意是 `openspec status --change x`），`cat`、`grep` 这种只读的也算了，`flowTouch` 之后它就成了"这个会话在做的变更"。

改法：只认真的 openspec 命令里点名的（`openspec status/instructions/new/archive/apply … <名字>`），读文件、搜索不算。

#220：提问框选了"就这样定稿"，收工检查又原样问一遍。同一轮里（提问框答案不开新一轮）复现不出来；按代码看，用户在对话里回一句"就这样定稿"（新一轮），之后模型又动过这几份文档（指纹变了），就会再问（`lib/flow-policy.js:185`）。这违反 2026-10-16 定的"用户说不用之后，这个要求里后面的小改动不再问"。

改法：用户最近一次开口（原话或提问框）是不审这一份（"就这样定稿""直接写下一份""不用审"），这一份不再问，直到用户提了别的要求。

- #189（旧第 4 类）：`--base` 支持 `仓库=提交` 多值，改法照旧。

## 7. 钩子预算用完、git 超时

0051 上的 #208（收工检查"核对文件指纹"）和旧 #147 同一个原因：`lib/workspace.js:40-56` 对每个已跟踪文件都先做 `pathStatus`（一次 lstat、两次 realpath），壳子带五六个子项目时上万个文件，慢电脑上 12 秒不够。1453 上的 #198、#200—#205、#216、#217 阶段名各不相同（Git config、Git rev-parse、Git ls-files、核对文件指纹、读取会话记录），报错的阶段是"预算用完前最后进的那一段"，都是同一次调用里指纹和 git 把时间花完了；#203 是 git 等不到结果（被剩下的预算截断）、读不出仓库状态。after-tool 对 `curl`、`python`、`node` 这类命令也算一次整个壳子的指纹（`lib/evidence.js:40`）。

改法：

1. 没改过的已跟踪文件直接用 `ls-files -s` 里的哈希，不做 `pathStatus`；链接按 `ls-files -s` 的模式 `120000` 认，只对它们和改过的、未跟踪的做 `pathStatus`。没有链接的仓库，指纹和改前完全一样（加测试比对），已有的许可、审查记录不失效。
2. 阶段名带上是哪个仓库（"Git diff（jssslt-oa）"），下次再出能看出慢在哪个子项目。
3. 工作线程第一次载入钩子模块不算在 12 秒里；guard-commit 前面几段补阶段名（旧 #181）。

## 12. IDEA 起项目查重（反馈表第 2 条）

|---|---|
| 推送、push | 直接 `git push`，几笔提交都一样，不出推送计划；壳子里几个子项目都有没推的，各推一次。强推、删分支、推到别的分支照旧要确认 |
| 合并推送、合并 push | 照旧：先出推送计划给用户看，用户确认后按计划推 |
| 合并成1条推送、合并成一条 push | 不问：新加 `merge-push.js squash --dir <仓库> --push`，把这个分支所有没推的提交合成一条（文件内容和原来完全一样、旧提交留备份 ref、不强推），然后推 |

远端还没有这个分支（第一次推）时不合成：那会把整个历史压成一条，提示先普通推送。
