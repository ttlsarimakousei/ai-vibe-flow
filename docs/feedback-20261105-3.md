### 手段实测

`dev/probes/cc-reviewer-opts.js`，假网关，2.1.120、2.1.259、2.1.289（见 [claude-code-facts.md](claude-code-facts.md) 最后一节）：代理文件的 `effort` 发得出去，只影响子代理；SubagentStart 的 additionalContext 进子代理第一个请求；代理文件里的 hooks 只对这个子代理生效，Read 拦得到，deny 的理由和 additionalContext 都送得到模型。

## 要定的

1. 审查子代理的命令要不要硬限制：只放 `git diff/show/log`、`unzip -l/-p`、`jar tf`，别的拒绝。建议限（可能漏掉要 Bash 才查得到的问题，看审查记录里问题数有没有掉）。
2. 收尾线：工具用到一定次数提醒交结论。提醒不拒绝，第 64 条否掉的"限调用次数"是拒绝。建议 30 次提醒。
3. effort：第 63 条定的不设。等 `review-effort.js` 的结果，有用再问。
4. 压缩窗口：73.3 万改小。输入大致成比例下降，代价是压缩更勤、每次压缩丢上下文。要先知道公司额度算不算缓存的 token。

## 修改计划

审查（按顺序）：

1. 第一轮材料直接给：`review-runner` 已经读出的 diff 和文档用 SubagentStart 注入，放在第一个请求里，不用子代理一个个读。脚本再算改动函数的调用方、被删名字的引用。注入不了的（超大）照旧写范围文件。
2. 代理专属钩子：`vk-reviewer.md` 里写 hooks，查命令白名单，数工具次数，到线提醒（要定的 1、2）。Read、Grep 范围外先只记数，不拒绝，看新报告。
3. 删脚本查过的检查项：含糊词、有没有 WHEN/THEN、任务里混测试（`vk-reviewer.md:36,38`，`session-proposal.js` 查过）。角度数按改动大小算，不算整个文件（`review-runner.js:168`、`:366`）。
4. 审查记录加请求数、输出 token：改完拿报告比。

第 1 点"能用脚本的"（按报告排）：

1. 读代码 42.7%：看新报告里 grep、sed、cat 的比例，再定做代码地图还是一次取多段的工具。
2. 审查脚本 4.8%：钩子在最后一个角度回来时带上结论，不用跑 status；`resolve` 和 `prepare` 合成一条。
3. 拦下和收工催 4.3%：cd 这类 98 次，提示里的写法是确定的，钩子直接改写（`git -C`、`mvn -f`、`npm --prefix`，只改认识的，不碰权限）；别的看新报告。
4. `openspec validate` 168 次：写完规格钩子自己跑，错了才说。
