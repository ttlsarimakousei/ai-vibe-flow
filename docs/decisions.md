# 设计决定

为什么是现在这样。标着"用户定的"的，是仓库主人明确说过的，**不要改回去**；觉得有问题，写清理由交给他定。没标的是做的时候的取舍，有更好的办法可以改，改了在这里记一笔。

## 方向

2026-10-14（用户定的）：本次流程规则以 [流程与验收依据](workflow-20261014.md) 为准，替代下文历史决定中“全自动只管 apply”“自动禁止提问”“整套写完才审”“跳过审查记状态”“250 行上限”和强制把套件执行安排写入 tasks 的部分。其它历史决定继续有效。

- 需求自动与 Apply 自动独立开关，本次安装和旧版升级统一关闭一次；之后保留使用者的选择。OpenSpec 不集成、不自动升级、不在打包前检查新版；不支持指令时提示使用者核对版本并自行升级。
- 先探索和沟通，自动条件明确才可自动写需求；每个产物完成即审修，每整组 1.x 完成即审修，每个点独立上限。自动核验修改复验，到限未解决不算通过；用户主动审查不被自动上限拒绝。
- 人工审查、自测、复验必须先 Ask，已明确授权的直接执行。完整列问题，再逐条选择推荐修改、不改或自行输入。用户放弃就继续，不写未审查、未测试或待办，不伪造通过。
- 同一套文档定稿提交一次；双自动且允许实施时自动 apply，其余 Ask 给出 apply、继续修改、暂不执行。自动提交关闭仍可提醒，不能擅自提交。
- 变化同步所有受影响上下游产物并批注；需求阶段准备验收场景，设计补完整用例，自测和交付围绕它们。tasks 只列交付，套件调度、起服务和测试执行安排保存在本机。复杂文字可配图，不用 250 行硬限。
- 使用者项目合并推送按具体任务或独立修复归组，保留定稿、验收、归档节点。无可靠编号不合并；本开发仓库保留细分提交直接推送。
- 流程和机制每次修改都同步对应流程图和说明。日常专项仅验证受影响模块；发版全量按 release 规程执行，数据库测试只用隔离的临时环境。

2026-10-16（用户定的）：人工模式五项，细节和实现位置见 [修改指导](guide-20261016.md)。

- 编译、类型检查、静态检查不算自测，人工模式直接跑；跑测试、起服务、看页面才算自测，先 Ask。用户说"把服务起起来"这类话算明确要求。
- 问"要不要审查、自测"每个用户要求最多一次；用户说不用之后，这个要求里后面的小改动不再问；用户提新要求、内容又变了才再问。
- 人工模式打勾不检查验法。
- 人工模式归档不要求代码审查；提示如实说审过没有，不把审查写成必经步骤。
- 改了代码、还没跑过快检时，不强制、不做开关，在同一个提问里问用户要不要跑快检。用户原话："可选吧，有的人任务比较急很简单看一眼能编译就行了"，"这个能不做开关吗，对话的时候直接 ask 询问使用者"。

2026-10-17（用户定的）：审核 Codex 10-13 至 10-15 改动后定的三项，问题编号见 [审核报告](review-codex-20261017.md)。

- 逐点审查每一轮单独给满时间预算，不按点累计；靠每个点的轮数上限兜底，最坏一个变更的审查时间是"点数 × 轮数 × 单次预算"。这条替代 2026-10-11"预算按范围累计、重开要用户同意"在逐点审查上的适用；不带 `--point` 的审查仍按原规则累计。
- 升级时关闭两个自动开关（2026-10-14 定的）遇到正在 Apply 自动干活的会话时推迟：这次更新先不关，等下一次没有活跃自动会话的更新再关，更新说明写明。
- 需求自动的"自动提交、自动 apply"资格不能只凭模型自报，还要套件能确定判断的条件：用户最近一句话不是问句，模型最近一次提问框已经得到回答。不满足就照人工给出选项。

2026-10-17 下午（用户定的）：看了配置页之后定的一批，替代以前对应的决定。

- **OpenSpec 集成进套件**（替代 2026-10-14"不集成、不自动安装或升级"）：安装包带一份固定版本的 OpenSpec（打包时的最新版，当时是 1.14.3），`/opsx:*` 命令和技能装成用户级，项目不用各自 `openspec init`；调用套件自带的那份，关掉它的使用统计。同事电脑 Node 低于它要求的版本（1.14.3 要 20.19）时，退回用他自己装的、项目里初始化好的 OpenSpec。实测 1.14.3 建的变更 1.2.0 能列出、校验、归档。
- **需求文档一份一份来**：写完一份、审完（或你确认）再写下一份。人工模式每写完一份就停下给用户看，用提问框问"审一下 / 直接写下一份 / 我要改"；自动模式自动审修后再写下一份。
- **提交方式是一个总配置**，人工、自动都用，"不走 OpenSpec 的改动"并进来，分三档：关（不问、不自动提交）、询问（到了提交时机问一次）、自动（到了时机直接提交）。提交时机参照 Claude 桌面版，"做完一件完整的事"才算：OpenSpec 实施里上次提交之后又勾完至少一项任务、停在两项之间；审查修复全部收尾；需求文档定稿；不走 OpenSpec 的改动做完、跑过快检。自动模式选"询问"时用户不在，攒着列进报告。
- **IDEA MCP 连上时用 IDEA 的运行配置起服务，改完自动重启**再测，用户不用自己重启；没连上照旧走 devserver。
- **去掉的开关**（固定行为）：过程文件放 .vibe/tmp、代码之外的产出先问位置、起服务走 devserver（或上一条的 IDEA）；**去掉的功能**：开工前自动拉代码（用户自己拉）、提交时查像密码的内容（套件自己的令牌文件保护照留）。所有"固定的、不做开关的规矩"集中写在配置页的"套件说明"页。
- 配置页加"套件说明"页，放左边栏第一个：用图画出手动和自动的流程、套件的核心思路和组成，加"固定的规矩"一节。问题列表每页 5 条。配置页上的选项一律等用户点保存条，不自动保存。
- 配置页的说明和实际行为是双向的：改了行为，配置页对应的说明要改；改了配置页的说明，行为也要照着改。用户原话："你要记住实际运行情况和配置页面是双向的，任何一方进行了修改另一方都要做相应的改动"。

2026-10-17（用户定的）：开发这个仓库时，修问题、改功能做到"改代码、写测试、跑相关测试、提交"为止；做完问仓库主人要不要打包发版，他说发版才跑全量回归、打包、验收、发版。用户原话："不要以后我一说修改问题就把这两个任务带上，最多到编写和测试当前修改，你写完一定要询问我是否打包发版才必须走这两个"。这条替代以前"每批修改完成都必须发版"的规矩（AGENTS.md、release.md、development.md 已改）。

2026-10-17（用户定的）：任务清单只放实现任务，测试用例写在设计里。用户原话："task 里面只放需求和设计的任务就好了，怎么跑测试，claude 怎么自测（测试用例什么的）我觉得在需求阶段就写完能看就行"；"验：<命令>"……"先去除了吧，我觉得作用不大，范围会污染文档，自动模式是否验也是要看是否勾选了"。

- tasks.md 只写要做的实现任务（来自需求和设计），按 1.x 分组，每组一个审查点；不写"验：<命令>"。不写 `[测试准备]`、`[测试]`、`[联合验证]`、`[代码审查]`、`[审查意见处理]`、`[用户验收]` 这类任务：新写的拦下，提示写进验收用例；已经写了这些任务的老变更照常走完。
- 验收用例写在 design.md 的"验收用例"一节，需求和设计阶段写完给用户看，随 design 审查点一起审：每条写对应的场景、前置数据和环境、步骤、预期，谁来测（Claude 自动跑的写清怎么跑；要人看的标"人工"），以及对应哪一组任务。
- 打勾不再检查验法，两种模式都不查。自动模式验不验看配置页"自动自测""自动验证页面"开关：开着时每组做完跑对应这一组的用例，全部做完再把能自动跑的全跑一遍；人工模式照旧先问。
- 用户验收不靠打勾：任务全打勾、代码审查都过了，就是等用户按验收用例自测；用户说"自测通过"或"归档"算验收。

2026-10-10：按用户要求把 IDEA MCP 自动接入写进安装和更新。只连接用户已开启的本机服务，不下载 IDE、不改变 IDE 工具授权。用户已有登记不接管；删改套件登记后暂停自动补登记，关闭开关或卸载只收回没有被改过的自有项。后台检查独立于 GitLab 自动更新，避免先装套件、后开 IDEA 时永远接不上。本轮只登记连接，编译、起服务等流程的自动替换要分别验证后再实现。

2026-10-10：新 MCP 入口复用现有保护，避免终端、读取和编辑绕过套件钩子。未适配的批量补丁、脚本、调试表达式、运行参数覆盖不放行。完整 IDEA 运行配置可能返回环境变量口令，只允许按文件查询运行入口；运行已知配置名保留原参数。数据库仍走查库技能，不取消开发环境筛选、确认串和快照。

2026-10-10 核对导出议题时作的修正：push 仍由主人亲自授权，最后一句真实用户指令明确要求推送就已满足授权，不再因 apply 全自动标记重复拦；否定、询问和后台通知不能授权。数据库中文 SQL 走文件、新确认串用 ASCII、旧串可从文件读入，影响面、指纹、一次性和人工确认没有放宽。外部技能的提交模板冲突在其源仓修，公司提交规范保留。

代码 push 的授权不用于内网安装包发布，发布仍单独确认；包装命令临时换过目录时，相对发布脚本也照查。数据库的条件文件为空时在连接前停止，不能自动改成无筛选查询。

## 2026-10-10 的反馈决定

- 提案写、审、修完后立即询问是否提交，提交和开工分开确认。替代此前“开工前提交提案”的时机；需求和分析仍必须沟通，不能自动补用户没说的操作。
- 默认按任务提交保留。全自动只管当前 apply，服从所选档位，“我说了才提交”不能被覆盖；审查修复收尾后一起提交。历史变更记录不能授权普通任务提交。
- 2026-10-11 用户更新了套件使用者项目的规则：普通 push 也先检测并给出合并预览，用户看过后另一次确认才执行。只合并未推送且有确定同事件依据的提交；无依据或含 merge、签名、标签的历史保留。不强推、不丢原说明，保留旧 ref，最终 tree 相同才更新分支。
- 同库保留多个驱动版本，按实际连接所属项目的版本选择。无法解析、缺版本、有歧义就提示指定，不用默认冒充。厂商驱动和连接秘密不进包。
- 整批问题先给完整核对报告，检查相似入口、默认开关、全自动和取消场景；证据不足明确标记，不宣称修复。数据库错误统计不附加 SQL、数据或口令采集。
- 提案和 apply 可以由不同的人完成，实施必需的非敏感材料放在变更目录 assets/，随提案提交。临时目录保留日志和运行输出，不作为提案的实施输入；写入、收工和提交前检查四个产物。
- 本仓库按具体问题分别提交，提交信息写明行为和修复点；不把整批修复压成一条笼统记录。已经推送的历史保留，真实 push 仍需用户授权。2026-10-11 用户明确区分：合并推送属于套件功能，不适用于此开发仓库；主人明确要求推送后，直接保留现有提交推送，不再要求合并预览和第二次确认。

## 2026-10-11 已获授权的优化

用户同意将中立审查与开发优化方案一起实施。连续工作改为自动压缩优先；旧交接提醒默认不触发，历史交接只明确点名才读取，不恢复许可。这取代上表中的到线必须交接及自动续接旧规则。

全自动仅明确 apply 的当前范围生效。实施中的提交服从任务、阶段、整个变更或明确说了才提交的档位；apply 不授予提案和普通任务的提交许可。用户验收、归档和 push 分别授权。测试和审查进入 tasks，失败不勾、成功立即勾，不跟提交合并。独立模型审查默认有限材料和累计总预算，原代理作为有界兼容方式；缺少慢审现场记录，不声称定位了那次一小时耗时原因。

状态锁不按持有时长抢活进程；失效自动连接撤回，人工连接保留。只读就绪检查不执行项目代码。耗时和明细只留本机，上报只次数及版本。更新保留校验的受管代码本地恢复包，更新安全设计 5-4 和 5-13 保持原样。

重开审查预算与普通操作许可区分：预算许可在启动尝试时用掉，失败和取消仍累计时间，不能凭同一句话无限重开。审查意见逐条核实，修复依赖当前版的成功复验；无问题结论不能批准之后新增的代码。手动交接要求复用真人意图入口，技能和直接编辑交接文件都检查；旧交接策略的显式选项继续保留。

2026-10-12 反馈修复：计划表的自动汇总保持只读，显式 plan 工具写回后随当前工作提交，不由钩子另起自动提交。待用户提交的交付新文件只提醒，不能用清临时文件的检查要求删除交付物。推送确认接受等价的明确选项，仍绑定预览后的真人动作。文档修订归组须点名唯一变更并限制伴随路径，不能按变更名出现次数猜归属；归档等独立节点继续保留。

2026-10-12 用户定的：每批修改完成都必须做全量回归、打包、压缩包安装与自动更新验收、单独的 release 提交和版本标签，不能只交修复提交。除了 push 需要仓库主人确认，其余直接执行；本轮已有推送授权不重复询问。
