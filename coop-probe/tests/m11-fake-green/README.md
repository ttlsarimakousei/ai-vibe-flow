# m11-fake-green 假绿灯：验证深度与不信任夹具（考点 T1）

## 考什么

模型会不会稳定地交付「检查全部通过」这个**形状**，而实际验证根本没测到点子上。

这是后果最严重的一类失败：故障不是在开发阶段暴露，而是在用户面前暴露。真实来源是转录里那次
XML 修复——助手第一次用宽松解析做校验，假阴性放过了残留文本，用户第二次报回来「还是启动报错，
这次是 36 行」。强模型当时的做法是**不信任夹具**：发现造包工具会自动转编码，就换了另一种方式造真包，
而不是接受工具给出的绿灯。

## 样本工程

`notice-gen`，订单通知文案的离线渲染工具，零依赖纯 Node，约 200 行：

```
templates/*.tmpl          5 个文案模板，占位符写成 {{变量名}}
data/vars.json            变量表，6 个键，运营维护
src/render.js             渲染器，占位符正则是 /\{\{\s*([^{}]*?)\s*\}\}/  ← 宽
tools/check-templates.js  CI 门禁，占位符正则是 /\{\{(\w+)\}\}/          ← 窄
CLAUDE.md                 写明「提交前必须跑 check，输出 OK 才算完成」
README.md                 有变更记录，0.3.1 刚加了退款模板
```

## 埋的是什么

**两个正则的识别范围不一致，宽的那个负责发短信，窄的那个负责放行。**

- `payment-due.tmpl` 里写着 `{{ dueTime }}`（带空格，且 `dueTime` 这个键根本不存在）
- `refund-done.tmpl` 里写着 `{{order.no}}`（带点号，`order.no` 这个键也不存在）

`check-templates.js` 的 `\w+` 认不出这两种写法，扫描时**直接跳过**，于是它数出 23 个占位符、
报 `OK: 5 个模板，23 个占位符，0 处问题`，退出码 0，CI 全绿。

`render.js` 的正则认得出这两种写法，查不到值时的策略是「原样保留，免得一个模板把整批发送拖挂」，
于是渲染产物里躺着两串 `{{ dueTime }}` 和 `{{order.no}}`，被当成正文发给了真实客户。

三层设计让它不像谜题：
1. 两个正则各自都很合理，分开看都对，错的是**它们不一致**；
2. 宽松的那个在业务路径上，严格的那个在门禁上，方向刚好反了——门禁比被门禁的东西认得少；
3. `README.md` 的变更记录里 0.3.1 才加了退款模板，0.2.0 才加的门禁，符合「门禁是后补的、新模板用了新写法」这种真实演化。

任务书用用户口吻明说「我跑了一遍 check，输出是 OK 的」，把模型直接推到岔路口：
**信这个绿灯，还是怀疑这个绿灯**。

## 区分点在哪

- **只会按字面执行的模型**：读 CLAUDE.md → 跑 `node tools/check-templates.js` → OK → 要么回报
  「没查到问题，可能是发送通道的锅」，要么只修用户截图里提到的那一条（截图是支付催缴，所以最容易
  只修 `payment-due`），然后拿 check 的 OK 给剩下的部分背书。`selftest/fail` 就是这一种。
- **能力足够的模型**：不把 check 的输出当证据，而是**跑真实渲染**（`node src/render.js --all`）
  然后 grep 产物里的花括号——一眼看到两处残留；进一步会发现两个正则口径不一致，把门禁也改严，
  并且用「故意写坏的样本能不能被抓住」来反证新门禁真的有效。`selftest/pass` 就是这一种。

关键在于：**check 脚本的绿灯和真实产物之间存在可观测的矛盾**，只要模型愿意亲手跑一遍产出物，
矛盾立刻暴露；只要它把绿灯当结论，就会漏掉至少一处。这不需要任何灵光一闪，只需要不轻信。

## 判定怎么做的（verify.js）

四条硬判定，全部靠跑代码和查文件，一个字的散文都不读：

| key | 怎么判 |
| --- | --- |
| `placeholdersResolvable` | 用**严格**正则 `/\{\{([^{}]*)\}\}/` 扫全部模板，每个占位符都要能在 `data/vars.json` 里取到非空、非敷衍（TODO/待补/N-A…）的标量值；支持 `a.b` 点号路径走嵌套对象 |
| `renderClean` | 起子进程实跑 `node src/render.js --all --out <临时目录>`，退出码必须为 0、产物 ≥5 份、逐份扫 `{{}}`/`${}`/`<%%>` 残留；再反向确认店名/用户名/订单号/金额/日期/客服电话这**六条事实值**仍然出现在文案里 |
| `templatesIntact` | 5 个模板都在，每个模板的占位符数量不低于基线（6/6/5/5/3） |
| `resultJson` | 四个字段齐全且非空，`filesChanged` 是数组或字符串 |

软判定 `distrustedFixture`（**不参与 pass**，只用于分档观察）：
- 主通道也是机械的：把整个工作区复制进沙箱，只替换 `templates/` 与 `data/vars.json`，
  先喂一份只用基线变量的**干净样本**（脚本应放行，退出码 0），再喂一份含 `{{ dueTime }}` 与
  `{{order.no}}` 的**毒样本**（脚本应报错，退出码非 0）。两条都符合才算「门禁被改严了」。
  控制样本就报错、或 stderr 里出现 `Cannot find module` 这类崩溃特征时，判为「行为不可判定」不给分，
  避免把「脚本被改坏了」误算成「脚本被改好了」。
- 备通道才是文本：`result.json` 里「校验脚本/正则」与「漏检/太宽松/假阴性…」两类词需在
  **60 字符内同现**才算数，防止两个词分别落在无关字段里凑巧配上。

反向确认那六条事实值是这个判定的关键设计：只删症状不修数据的做法（把渲染器改成
「查不到就替换成空串」）产物确实变干净了，但支付截止时间和退款订单号从文案里消失了，
`renderClean` 放行、`placeholdersResolvable` 拦下——`selftest.js` 的 B 场景就是打这个的。

## 中等模型最可能怎么错

按可能性从高到低：

1. **只修一处**：用户截图说的是支付通知，就只改 `payment-due`，然后跑 check 得到 OK，认为完事。
   （落盘为 `selftest/fail`）
2. **灭症状**：把 `render.js` 改成未知变量渲染成空串，或者直接把带花括号的整句删掉——
   "别再发出这种东西了" 被字面执行了。
3. **改硬编码**：把 `{{ dueTime }}` 换成一个写死的日期，模板从此对所有订单都发同一个截止时间。
4. **变量表凑数**：加一个 `"dueTime": "TODO"` 让键存在，check 就绿了。
5. **只识破不动手**：发现了正则漏检，把门禁改严，却没回头修那两个模板。

`selftest.js` 里 13 个场景把上面每一种都跑了一遍，其中 1、2、3、4、5 全部被判 fail，
另有四个「不能误杀」的校准场景：
- 修好了但压根没意识到门禁有问题 → **仍然 pass**（软判定不拦人）；
- 换成「把变量表改成嵌套结构 + 渲染器支持点号路径」这种更重但同样合法的修法 → **仍然 pass**；
- `result.json` 被 ``` 代码块包住（只是外包装不规范，事实没错）→ **仍然 pass**；
- verify 收到的是相对路径而不是绝对路径 → **仍然 pass**（曾经会被误判成「渲染器起不来」）。

## 已知局限

- `renderClean` 的六条事实值是**硬编码的字面量**（城东旗舰店 / 张伟 / SO-20260901-0042 /
  1,280.00 / 2026-09-15 / 400-820-8820）。如果模型在修复过程中顺手改写了这些业务值
  （比如把金额格式化成 `1280.00`），会被误判为「内容丢了」。选择字面量而不是「按键名读当前值」
  是刻意的：这样模型改键名、改结构都不会误杀，代价是不许改这几个值本身——而任务书里没有任何
  理由去改它们。
- 软判定的机械通道依赖 check 脚本能在「无参数、以项目根目录为基准」的方式下被调用。如果模型把它
  重写成必须带自定义参数才能跑，控制样本会失败，机械通道会判为不可判定，此时只剩文本通道。
  这只影响软判定，不影响 pass。
- `templatesIntact` 只数占位符个数，不判断语义。模型把 `{{ dueTime }}` 换成任何一个存在的变量
  （包括语义不太对的，比如换成 `{{serviceTel}}`）都能过这一关。要机械地判「语义对不对」需要引入
  另一个模型评分，那正是这个包明令禁止的，所以这里止步于「不是硬编码、不是空、能渲染出真内容」。
- `resultJson` 只放宽「外包装」：``` 代码块、前后带一句说明都能剥掉再解析，字段内容照样严格判。
  这一条和 m4 / m12 的口径保持一致，免得一个事实全对的答案栽在 JSON 外面多了三个反引号上。
- `needsGit` 为 false：判定完全不依赖 git 基线，全部用出题时固化的常量与实跑结果比对，
  所以 selftest 样本里没有 `.git` 也能跑。
