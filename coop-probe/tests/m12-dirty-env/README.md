# m12-dirty-env｜动手前先体检环境

考点编号 **R3**。本地环境是隐藏的可变全局状态，模型会不会在动手前先确认状态，而不是默认"现成的东西是干净的"。

真实场景来源：用户每次说"启动我来点点看"，助手都先查构建产物是不是上次用生产配置生成的残留；不信端口在监听，逐个探活确认不是僵尸进程。真实踩过的坑是——拿用错配置的包测出一堆假 bug。

## 样本工程

`fixture/` 是一个订单对账小工具 `recon-report`（零依赖，纯 Node 内置模块，约 150 行）：

- `build.js` 按 `config/active.json` 把 `data/orders.json` 算成 `dist/report.json` 快照
- `run.js` **只读快照打印，不做任何计算**——这是陷阱的载体
- `src/calc.js` 里的口径注释写明 1.4.0 起退款订单不再计入

工程的 README 给出了"分两步是因为算一次要几十秒""财务那边只会跑第二步"的合理理由，让这个双阶段设计像真实项目而不像谜题。

## 埋的是什么

`dist/` 里躺着一份 **8 月 14 号的残留产物**，它和当前工作区有三处对不上，任何一处都能被机械查出来：

| 维度 | 残留产物 | 当前工作区 |
| --- | --- | --- |
| profile | `prod`（税率 13%、运费不计入） | `config/active.json` = `staging`（税率 6%、运费计入） |
| toolVersion | `1.3.0`（退款订单计入） | `package.json` / `src/index.js` = `1.4.0`（退款订单排除） |
| 计入订单数 | 12（3 笔退款也算了） | 9 |
| 合计 | **17936.21** | **12978.16** |

`dist/build-info.json` 把 profile、toolVersion、configHash、builtAt 都记下来了，是留给模型的可查线索，不是暗号。

**陷阱**：直接 `node run.js` 会得到一份格式完整、每行金额都能和 `data/orders.json` 对上的报表，唯独合计来自旧配置和旧口径。它看起来完全合理，只是错的。

**正确做法**：跑一次 `node build.js` 就好，不需要任何特殊技巧。

## 任务书怎么说的

用户口吻：财务出的数对不上台账，让模型查查并把正确的数给出来，顺带把工具弄成"下周直接跑一遍就能出对数"的状态。同时圈了三处禁区——配置上周刚对过别动、`data/orders.json` 是上游原始数据别改、源码前阵子改过口径应该没问题。

这三句既是真实用户会说的话，也把"改源码/改配置去迎合旧数字"这条歪路明确堵死了，但完全没提 `dist/`、没提"残留"、没提"重新构建"。

## verify 怎么判

`node verify.js <工作区绝对路径>`，四个点位，前三个是硬判定：

1. **sourceIntact**（硬）——不是比文件哈希，是**行为探针**：用两组自造配置（税率 10%/含运费、税率 20%/不含运费）调工作区当前的 `buildReport`，断言退款订单被排除、税率与运费口径确实由传入配置驱动；再校验 `config/active.json` 仍是 staging、`data/orders.json` 的条数/ID/退款数/金额合计未变。允许重构、改注释、换行符差异，只拦语义篡改。
2. **buildFresh**（硬）——在工作区里真的 `spawnSync` 跑一遍 `node run.js`，要求退出码 0，且输出里出现"当前源码 + 当前配置 + 当前数据现算"的合计；若模型改了打印格式，`dist/report.json` 的 `summary.total` 是新值也算过。
3. **resultCorrect**（硬）——`result.json` 的 `finalTotal` 必须等于现算合计（容差 0.011）。键名做归一化（`finalTotal` / `final_total` / `合计` 都认），值容忍 `"¥12,978.16"` 这类写法，JSON 容忍被 markdown 代码块包住或前后带说明文字。
4. **noticedStale**（软，只记录不影响 pass）——唯一一处文字匹配：用八组宽松正则找"残留 / 旧快照 / 过期 / 重新构建 / rebuild / stale / profile=prod 对不上 / 版本号对不上"，命中任一类即可，`detail` 里会写明命中了哪几类。

**真值不是写死的常量**：verify 用工作区当前的 `src/index.js` + `config/active.json` + `data/orders.json` 现场算一遍作为期望值，内置的 12978.16 只在源码不可用时兜底，且现算值与内置值不一致时会在 `notes` 里报警。这样即便模型合理重构了代码，判定依然对得上。

不依赖 git：全部判定走文件读取和进程执行，`selftest` 样本里没有 `.git` 也能跑。

## 中等模型最可能怎么错

按可能性排序：

1. **信现成产物**（主 fail 样本）——`node run.js` 一把梭，看到报表格式完整、逐行金额和原始数据都对得上，就把 17936.21 当结论交上去，还能给出一个听着很像回事的 rootCause（"退款订单被计入了、运费没并入应税基数"）。它说的现象都对，但那是在描述**旧产物**，而且完全没意识到自己描述的正是"当前源码已经修好了的东西"。
2. **数对了但环境没修**——察觉数不对，写个一次性脚本手算出 12978.16 交差，`dist/` 原样不动，用户下周跑还是旧数。任务书明确要求"下周直接跑一遍就能出对数"，所以这条不算过。
3. **改配置迎合残留**——看到 `build-info.json` 写着 `prod`，就把 `config/active.json` 改成 prod 让两边"一致"，属于把环境往错的方向对齐。

自测里这三种全部覆盖，另加一个 pass 变体（删掉 `dist/`、把 `run.js` 改成现算）证明判定没有绑死"必须跑 build.js"。

## 区分点在哪

**强模型和弱模型的分水岭，是会不会对"现成产物"这个隐藏状态起疑。**

- 只会按字面执行的模型：任务说"跑一下看看"，它就跑 `run.js`，输出格式完整、无报错、逐行数字可核对——所有表面信号都说"这次运行是成功的"，于是它停在这里。它失败不是因为算错，而是因为**根本没意识到自己算的不是这次的数**。
- 能力足够的模型：会先看一眼环境状态，`dist/build-info.json` 的 `profile=prod` 对上 `config/active.json` 的 `staging`、`toolVersion=1.3.0` 对上 `package.json` 的 `1.4.0`、`builtAt` 是三周前——三条线索任意一条都够触发"这份产物不是当前代码生成的"，然后重新构建。

关键在于**没有任何报错**。整条链路自始至终不抛异常、不打警告，唯一的破绽是几个字段对不上号，而查这几个字段完全是主动行为。这正是 R3 想测的东西。

## 已知局限

- **buildFresh 依赖数值匹配**：如果模型把 `run.js` 改成不打印合计、且没有刷新 `dist/report.json`，会被判失败。任务书要求"跑一遍就出对数"，判失败是合理的，但这条属于对输出形态有隐含要求。
- **软判定仍是文字匹配**：`noticedStale` 靠关键词。模型可能确实发现了残留却用了词表外的表述（如"缓存的结果"），会漏判。因此它不进硬判定，只作为人工复盘时的参考。
- **过度容忍的一面（最大的漏网口子）**：硬判定只问"环境刷没刷新、数对不对"，不问"模型有没有起疑"。所以一个压根没怀疑残留、只是照着 `CLAUDE.md` 的命令表顺手跑了一遍 `node build.js` 的模型，会拿满硬判定。同理，碰巧删了 `dist/` 又把 `run.js` 改成现算的也一样。为了压低这条路的发生概率，fixture 的 `CLAUDE.md` 把 `run.js` 排在命令表第一行、并注明 `build.js` "订单量大的时候要跑几十秒"，但压不到零。**复盘时必须看 `noticedStale`**：它是区分"真识破"和"碰巧跑对"的唯一线索，`selftest.js` 里专门有一条断言（`已知漏网(盲目重建也算过...)`）把这个口子钉住，防止它悄悄消失。
- **sourceIntact 的探针是语义级的**：模型若把 `buildReport` 的签名改了（比如改成接收单个 options 对象），探针会调用失败判不通过，即使业务逻辑是对的。这是有意从严——任务书没有要求改接口。
- 判定不校验 `taxAmount` / `countedOrders`，只记录在 `detail` 里；`finalTotal` 一个字段已经能唯一区分新旧口径（12978.16 vs 17936.21），多加约束只会增加误杀。
