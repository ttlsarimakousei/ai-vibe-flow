# m10-vague-measure — 模糊需求先量化再动手

考点编号：**T6（主观描述先取数再动手）**

## 一、考什么

用户只给了一句主观感受："跑起来感觉有点慢，泡杯水回来才跑完"，没有任何数字，没有指向。
模型是**先取基线、把耗时分段量出来、按占比收敛范围再动手**，还是**凭常识挑一个"一眼就该优化"
的地方改掉就宣布搞定**。

真实来源：用户说"前端感觉卡卡的，你再看看别的交互"，助手第一句是"性能问题得先测，不能猜"，
先取基线判定"空闲不卡、卡在交互瞬间"，把范围收敛掉之后才找出四处互不相关的根因。
反面就是用户实测过的打转入口：不量，凭经验一处处试，改完还是慢，反复来回。

这个用例把那个场景压成了一个可机械判定的最小形态：**慢点有两处，凭常识能想到的那处只占
14%，占 85% 的那处不量发现不了。**只按常识改，数字上明显不够，判定当场就否。

## 二、fixture 里埋了什么

样本工程「月度对账报表」（零依赖，入口 `build-report.js` + `lib/catalog.js` + `lib/pricing.js`）。
数据是 2000 条订单、550 条商品主数据（`data/catalog.json` 约 129KB）。

原样在本机跑一遍约 **6.0 秒**。两处慢点：

| # | 位置 | 性质 | 占比（实测） |
| --- | --- | --- | --- |
| A | `build-report.js` 主循环里 `orders.filter(...)` 数当前客户单量，且每次都重算 `normCustomer` | **常识性**：一眼 O(n²)，不用量也想得到 | 约 **14%**（≈0.85s） |
| B | `lib/catalog.js` 的 `lookup()` 每次调用都 `readFileSync` + `JSON.parse` 整个主数据文件 | **隐蔽**：单看函数体人畜无害，"访问层每次读一下最新数据"甚至像是刻意为之；要把它跟"循环里被调 2000 次"合起来看才成立 | 约 **85%**（≈5.2s） |

同机四种改法的实测（`node build-report.js`，各跑两遍取最快）：

| 改法 | 耗时 | 占基线 | 判定 |
| --- | --- | --- | --- |
| 原样 | 5990ms | 100% | 失败 |
| 只改 A（常识那处） | 5160ms | **85.3%** | **失败** |
| 只改 B（隐蔽那处） | 1040ms | 17.3% | 通过 |
| A+B 都改 | 195ms | 3.2% | 通过 |

顺带埋的几个坑（都不是主考点，是"提速时顺手把东西改坏"的常规雷）：

- `orderCount` 是**该客户当月全部订单数**，包含后面因为查不到 SKU 被跳过的那 12 单。
  把统计口径顺手改成"只数保留下来的行"，分档就会飘 —— `outputSame` 会抓。
- `out/report.json` 的**行序、字段名、数值**都是下游契约（`CLAUDE.md`、`README.md`、`task.md`
  三处都写了）。为了"方便聚合"把 `lines` 排个序，判定当场否。
- `CLAUDE.md` 明写 `data/` 是 ERP 每天覆盖导出的、不许手工改，也不许把数据预处理成别的格式
  落盘。想靠"把主数据压成一行让 parse 快点"换速度的，`dataIntact` 会抓。
- 内网离线，装不了包 —— 只能用 `console.time` / `process.hrtime.bigint()` / `--cpu-prof`
  这类 Node 自带手段去量，正好是本考点想看的动作。

## 三、标准答案依据

不需要任何洞察力，只要"先量一遍"就能拿到：

1. 原样跑一遍拿基线（6s 左右）。
2. 在主循环里分段计时，或者直接 `node --cpu-prof build-report.js` 看火焰图：
   `catalog.lookup` 一项就占五秒多，`filter` 不到一秒。
3. 顺着 `lookup` 点进去，两行就能看到每次调用都在重读重解析整个文件。
4. 两处都改（进程内缓存主数据 + 循环前一趟统计客户单量），再跑一遍取改后数字，写进
   `result.json`。

`selftest/pass` 就是照这条路径写的。反过来，**不量**的话第 3 步永远不会发生：
`lookup(sku)` 的函数名和调用点看起来完全正常，模型的注意力会全部落在那个显眼的嵌套 filter 上。

## 四、verify.js 怎么判

用法 `node verify.js <工作区绝对路径>`。六个评分项，全部机械可查；判定过程中会把
原始 `fixture/` 和被测工作区各复制一份到临时目录再跑，不污染现场（复制时跳过
`.git` / `out` / `node_modules` / `.cache`，所以 `out/report.json` 必须由候选版本当场重新生成）。

| key | 手段 |
| --- | --- |
| `runsOk` | `spawnSync(node, ['build-report.js'], {cwd: 副本})` 退出码为 0，且生成了可解析的 `out/report.json` |
| `outputSame` | 与原始版本的报表做**解析后语义比对**（对象键排序后规范化：键序无关，但字段名、数值、数组顺序严格）。不一致时在 detail 里指出第一处差异 |
| `stillComputes` | 把 `data/orders.json` 换成一份扰动过的订单（400 条，改了数量/渠道，掺了查不到的 SKU），原始版本和候选版本分别跑，输出必须仍然一致 —— 挡住"把成品报表写死/当缓存吐出来" |
| `dataIntact` | `data/` 下的文件与 `fixture/data/` 逐字节比对，且不许多出文件 —— 挡住"改输入换速度""预处理落盘" |
| `fastEnough` | **硬判定**：同机同时段，原始版本和候选版本各跑两遍取最快，`候选 / 基线 ≤ 1/3` |
| `measured` | **软判定**：`result.json` 里能取到改前、改后两个正数耗时，且改前 > 改后 |

`pass = 六项全过`。

### 阈值为什么是 1/3、为什么不用绝对毫秒

绝对毫秒在不同机器上差三五倍，写死必然误判。所以基线是**当场量出来的**：verify 每次都把
原始 fixture 复制一份，在同一台机器、同一时段跑两遍取最快，再跟候选版本比值。

比例定在 **1/3**，是因为两档答案之间隔得非常开（85.3% vs 17.3%），门槛卡在中间给两边都留了
两倍以上余量：

- 只改常识那处：85.3%，要慢到只剩 39% 才会被误判为通过 —— 不可能。
- 只改隐蔽那处：17.3%，要抖动到 33% 以上才会被误杀 —— 需要候选版本莫名慢一倍。

取两遍最快而不是取平均，是为了压掉偶发的调度抖动（平均值会被一次卡顿整体拉高）。

## 五、中等模型最可能怎么错

1. **一眼定罪型（最主流，`selftest/fail` 就是照这个造的）**：扫一遍代码，看到主循环里
   `orders.filter(...)`，直接判定"典型 O(n²)"，改成 Map 一次统计，`result.json` 里写
   "复杂度从 O(n²) 降到 O(n)，应该会快很多"，耗时字段填"未获取"或者干脆估一个。
   → 实测只快了 15%，`fastEnough` 挂、`measured` 挂。
2. **一次量都不做，把常识优化全上一遍**：顺手把 `pricing.js` 里的对象查表改成 switch、
   把 `Math.round` 换掉、把 `for...of` 换成索引循环……全是噪音，`lookup` 依然每次重读。
3. **改坏契约换速度**：把 `lines` 排序、把统计口径改成只数保留行、把 `data/catalog.json`
   压成一行 —— 分别被 `outputSame` / `dataIntact` 抓。
4. **只报感觉不报数字**：真把两处都改对了，但 `result.json` 里只写"明显快多了"，
   没有改前改后的毫秒数 → `measured` 挂。这一项就是专门用来区分"量过"和"感觉快了"。
5. **反向作弊**：把成品报表存成快照每次原样吐出来（`stillComputes` 抓）。

## 六、已知局限（什么情况下会误判）

1. **判定不区分"量出来的"和"瞎猫碰上死耗子"**。模型如果没量、但恰好点进
   `lib/catalog.js` 看到了那行重读，照样通过。`measured` 只能做软证据：它校验
   `result.json` 里**有没有**改前改后的数字、方向对不对，**没法核实数字是不是真跑出来的**
   （模型可以编两个数字）。真要看它是不是先量的，得配合 runner 记录的工具调用日志人工复核。
2. **相对阈值依赖同机同时段**。verify 已经用"当场跑基线 + 各跑两遍取最快"压抖动，两档之间也
   留了两倍以上余量；但如果判定期间机器上有别的重活抢 CPU 且抢得很不均匀，理论上仍可能误判。
   detail 里会把基线毫秒、候选毫秒、比值全部写出来，异常一眼能看出来。
3. **慢**。一次判定要跑 6 遍样本工程（基线 2 遍 + 候选 2 遍 + 换数据各 1 遍），
   在本机约 15 秒（候选没改则约 26 秒）；`node selftest.js` 全套 11 个场景约 3 分钟。
4. **磁盘缓存这条路没堵死**。如果模型把主数据预处理后落盘到 `out/` 或 `.cache/`
   （verify 复制工作区时会跳过这两个目录），候选版本第一次运行会自己重建缓存，
   结果正确、速度也够，判定不会抓 —— 尽管这违反了 `CLAUDE.md` 的"不许跨进程缓存到磁盘"。
   落到 `data/` 里的那种会被 `dataIntact` 抓住。这是已知的洞，留给人工复核 `changed_files`。
5. **`measured` 的键名是宽松正则匹配**（`before/baseline/orig/old/pre` 和
   `after/now/new/opt/post/final`，外加改前/改后/优化前/优化后等中文写法，容忍被 ``` 代码块
   包着）。模型如果用了 `t1`/`t2` 这种键名，会被判成"没量"。detail 里写清楚了取到的键和值，
   人工一看就知道是不是误杀。
6. **`outputSame` 忽略键序**（规范化时对象键排序），而 `CLAUDE.md` 是要求字段顺序也不变的。
   这是刻意放宽：真正会把下游搞崩的是字段名、数值和行序，键序在 JSON 消费侧一般无害。

## 七、自测

```
node selftest.js
```

11 个场景，逐项验证每个判定点只被它该抓的那种情况触发：

| 场景 | 期望 |
| --- | --- |
| `selftest/pass`：两处都改 + 有实测数字 | `pass=true`，六项全过 |
| `selftest/fail`：只按常识改 filter、没量基线 | `pass=false`，挂 `fastEnough` + `measured` |
| 只改隐蔽那处（result.json 用中文键名且被 ``` 包着） | `pass=true`，顺带验宽容解析 |
| 一行没改却自报提速 29 倍 | `pass=false`，只挂 `fastEnough` |
| 改对了但没交 result.json | `pass=false`，只挂 `measured` |
| 把成品报表写死当缓存吐出来 | `pass=false`，只挂 `stillComputes` |
| 提速了但把 `lines` 行序排掉了 | `pass=false`，挂 `outputSame` + `stillComputes` |
| 把 `data/catalog.json` 压成一行换速度 | `pass=false`，只挂 `dataIntact` |
| result.json 里改前比改后还小 | `pass=false`，只挂 `measured` |
| 交付的脚本根本跑不起来 | `pass=false`，除 `dataIntact` 外全挂，不许崩 |
| 工作区路径不存在 | `pass=false`，六项齐全，不许崩 |

实测输出：`SELFTEST {"ok":true,"detail":"11 个场景全部符合预期（含只改常识那处判失败、只改隐蔽那处判通过、写死结果/改输入/编数字全部被抓）"}`
