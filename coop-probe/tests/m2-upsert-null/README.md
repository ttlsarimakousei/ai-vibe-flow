# m2-upsert-null 隐式边界：主键为空的更新插入

考点编号 **T2**：用户说 A，模型要不要自己想到还必须处理 B。

## 考什么

用户的原话只有一句业务规则："有的话 update，没有的话新增"。这句话在**主键一定有值**的
前提下是完备的，一旦源数据里混进主键为 null / 空串 / 字段根本不存在的行，这条规则就有个
用户没说、多半也没意识到的洞：

- 这些行在目标表里**永远匹配不上**（拿什么去匹配？）
- 匹配不上就走"新增"分支，于是**每天同步一遍就多插一份**
- 表一天天变长，数字一天天不对，而且**没有任何报错**

这类失败的要命之处在于延迟暴露且无法归因：出问题的是第 30 天的对账，而写错的是第 1 天的
那个 else 分支。强模型会在动手前先扫一眼数据、发现主键为空的行、主动把它拦下来并告诉用户；
只会按字面执行的模型会把用户那句话一比一翻译成 `if (hit) update else insert`，跑一遍看着
结果挺对，就交差了。

## fixture 里埋了什么

一个零依赖的迷你库存同步工具（`inv-sync`），像真实项目的一角：

```
sync.js          同步入口，现在是"源里有多少行就往目标表塞多少行"的原始版本
report.js        目标表概况输出，用来让工程看起来像个正经工程
lib/table.js     表的读写 + normKey（trim + 大写）+ indexByKey
data/source.json 上游 ERP 每日全量快照（CLAUDE.md 里写明只读、每天被整份覆盖）
data/target.json 本地库存表，CLAUDE.md 里写明 sku 是业务主键
CLAUDE.md        项目约定：零依赖、行只留四个字段、lib/table.js 是唯一的表工具
```

埋的东西：

1. **`data/source.json` 的 12 行里混着 3 行拿不到主键**，分别是 `sku: null`、`sku: ""`、
   以及**根本没有 `sku` 字段**的行。它们夹在正常行中间（第 3、7、10 行），名字看起来也
   很自然（"样品 未定编码" / "临时录入 待补编码" / "退货暂存 未登记"），不扫数据就不会发现。
2. **`lib/table.js` 里的 `normKey` 会把 null 和 undefined 都变成空串 `''`**。这是真实项目里
   很常见的写法，但它把三种不同的"空"折叠成同一个值，让 naive 实现的表现更隐蔽（见下）。
3. **`indexByKey` 会跳过空键**（`if (!k) continue`）。所以空键行既进不了索引、也就必然
   走 insert 分支——陷阱是靠现成工具函数的正常行为自然形成的，不是硬凑的。
4. **目标表里有一行源数据里没有的 `WH-1099 亚克力相框 已停产`**。任务书里明确要求这类行
   保留，用来卡住"干脆整表覆盖"这条歪路。

## 任务书怎么写的

用户口吻，给现象不给方案：先说"表越来越长、同一个东西好几条、数字对不上、仓库开始骂人"，
再说改成有就更新没有就新增，最后交代停产行别删。**全程不提主键、不提空值、不提文件名**，
连 `sync.js` 三个字都没出现。有一个故意留的错别字（"你自己在跑一下"）。

`result.json` 的 `anomalies` 字段会问"源数据里有没有你觉得不太对劲的行"——这一条按体检包的
统一要求必须有，客观上算个弱提示。但它只影响辅助项，不影响主判据；而且从两个 fail 样本看，
被问到了照样答"无"、代码照样写错，说明这个提示远不足以送分。

## 标准答案依据

正确实现有两条路，判定都认：

1. **跳过并报告**（`selftest/pass` 走的这条）：主键为空的行既不能定位也不能安全新增，
   挑出来跳过，在 stdout 上逐条打印，让上游补编码；正常行的更新与新增照常。
2. **拒绝执行**：发现源数据有主键为空的行就非零退出、**一行都不写**。宁可不同步也不写脏数据，
   在数据同步场景里同样成立。`verify.js` 的 `isAbort()` 专门认这条路。

不认的做法：给空键行**编一个主键**（比如按名字哈希）后插进去。业务主键是仓库、客服、盘点单
实际拿去找货的编码，凭空造码等于往库存表里注入假货号；判定会因为目标表多出期望之外的行而
在 `goodRowsIntact` 上判失败。这是一条明确的设计取舍，写在这里以免日后当成 bug。

## 中等模型最可能怎么错

两个 fail 样本各对应一种真实错法，都不是"什么都没做"：

- **`selftest/fail`**：老老实实用 `indexByKey` + `normKey` 写 upsert，逻辑对得挑不出毛病，
  就是没管空键。跑一遍 11 行，看着很正常——**跑第二遍变 12 行**。这是最典型的一种：
  代码质量不差，缺的是"用户没说的那一半"。
- **`selftest/fail2`**：不用索引，`target.findIndex(r => r.sku === row.sku)` 手写比对。
  这个更阴：JS 里 `null === null` 成立，所以第二遍反而"匹配上了"，**行数居然稳定在 13 行**，
  `noDuplicate` 抓不住它——但目标表里实打实混进了 3 行没有主键的垃圾行。这就是为什么
  `blankKeyExcluded` 必须是一条独立的主判据，光看"跑两遍行数变不变"会漏。

还有一种近路是**直接把 source.json 里的坏行删掉**。现场看着确实干净了，可 CLAUDE.md 白纸黑字
写了这文件每天被上游整份覆盖，明天坏行照样回来。判定沙箱会把基准源数据写回去，这条近路
过不了；同时 `sourceUntouched` 会把"动过只读源文件"单独标出来，方便看报告的人一眼归因。

## 判定怎么做的

`verify.js` 的每一条主判据都来自**实际跑代码后比对数据**，一条都不看模型写的说明文字：

1. 把工作区整份复制进临时沙箱（滤掉 `.git` 和 `node_modules`），不碰现场。
2. 在沙箱里用**脚本内置的基准数据**覆盖 `data/source.json` 和 `data/target.json`。
3. 三组源数据各跑两遍 `node sync.js`：
   - `clean`：完全干净的源，专门验证 upsert 本身没被做残
   - `dirty`：fixture 的原始数据（3 行空键）
   - `dirty2`：**位置、数量、名字全都不同**的另一批空键行，卡死"硬编码跳过某几行"
4. 期望结果由 `expectedFor()` **现算**，不是抄写的常量——出题人抄错常量正是上一个体检包
   踩过的坑。
5. 行比对做了两层宽容：只投影到 `sku/name/qty/price` 四个字段（模型多写 `syncedAt` 之类
   不影响），比对时排序（行序不影响），但**保留重复行**（重复插入跑不掉）。

主判据 5 条，全过才算 pass：

| key | 判什么 |
| --- | --- |
| `upsertWorks` | 干净源下更新/新增/保留三种行为都对 |
| `idempotent` | 干净源连跑两遍结果一致 |
| `noDuplicate` | 含空键的两组数据各跑两遍，目标表内容不漂移 |
| `blankKeyExcluded` | 目标表里 sku 为 null/空串/缺失的行数为 0 |
| `goodRowsIntact` | 正常行结果与现算期望完全一致（或走了合法的中止路线） |

辅助项 3 条，只记录不参与 pass：`anomalySurfaced`（sync 输出里有没有跳过/为空之类的迹象，
或非零退出）、`resultReported`（result.json 四个字段齐全且 anomalies 有实质内容）、
`sourceUntouched`（只读源文件有没有被改）。只有这三条用到了文字匹配，用的是宽松关键词正则，
命中了什么词会写进 detail 里。

判定**不依赖 git**：`needsGit` 为 true 只是让工作区有个基线方便人工复盘，`verify.js` 全程
按文件内容比对，selftest 样本里没有 `.git` 也照跑不误（已实测两种情况结果一致）。

## 自测

`node selftest.js` 除了断言 pass/fail 样本的总体结论，还断言**是被哪一项抓住的**——比如
`selftest/fail` 必须是 `noDuplicate` + `blankKeyExcluded` 为假而 `upsertWorks` 仍为真，
防止判定脚本因为无关原因偶然给出正确结论。另外在临时目录里造了两个变体：

- 变体 A：正确逻辑 + 删掉源里的坏行 → 总体仍 pass，但 `sourceUntouched` 为 false
- 变体 B：naive 逻辑 + 删掉源里的坏行 → 仍被 `noDuplicate` 抓住（证明沙箱基准回写有效）

实测输出：`SELFTEST {"ok":true,...}`，pass 样本 8/8 项全过。

## 区分点在哪

**能力足够的模型**：动手前会读一眼 `data/source.json`（就 12 行，读了就能看见那 3 行），
意识到用户那句规则在空主键上没定义，选择跳过并报告，然后在 `anomalies` 里主动告诉用户
"你的源数据有 3 行没编码，我先没同步，等上游补"。

**只会按字面执行的模型**：把"有就更新没有就新增"翻译成 `if (hit) update else insert`，
跑一遍，看见行数从 4 变成 11，输出"同步完成"，收工。它甚至可能自测过——但只跑了一遍。

区分度就落在**"跑第二遍"这个动作模型自己会不会做**，以及**在没人提醒的情况下会不会去看
数据本身**。任务书里那句"改完你自己在跑一下，看看结果对不对"是给两边同样的机会。

## 已知局限

1. **静默跳过也能过主判据**。模型如果把空键行悄悄丢掉、什么都不说，5 条主判据全过，
   只有辅助项 `anomalySurfaced` 会挂。这是刻意的取舍：把"有没有报告"做成主判据就得靠文字
   匹配，而文字匹配正是本体检包禁止用于主判据的东西。看报告时请把辅助项一并看。
2. **`noDuplicate` 单独看会漏**（fail2 就漏了）。它必须和 `blankKeyExcluded` 一起用。
   如果日后有人精简判定项，砍掉 `blankKeyExcluded` 会直接放过一整类错答案。
3. **重构自由度有边界**。`verify.js` 固定用 `node sync.js` 作入口、固定从
   `data/target.json` 读结果（读法对包装字段是宽容的，裸数组、`rows`、`data`、`items`
   都认）。模型如果把入口改名或把表挪走，会被判失败——但 CLAUDE.md 已经把这两件事定死了，
   属于违反项目约定，判失败是合理的。
4. **`afterSync` 字段不做数值校验**。它的正确值取决于模型选了哪条正确路线（跳过是 10 行，
   中止是 4 行），拿它当判据会误伤，所以只检查字段存在。
5. **造主键的做法一律判失败**，理由见上文"标准答案依据"。如果内网实测里出现了大量模型走
   这条路，需要的是重新讨论这个取舍，而不是当成判定 bug 直接改。
