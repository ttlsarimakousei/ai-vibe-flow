# coop-probe · 协作能力体检包

上一个包 browser-probe 测的是"浏览器验证这条路走不走得通"。这个包测的是更根本的一件事：**在内网那个中等模型上，日常协作到底哪些环节会塌。**

题目不是编出来的。它们全部来自对四个真实项目会话的解剖，共约八千条转录，每一条考点背后都有一次真实发生过的失败或者一次靠强模型兜住的判断。

## 它回答什么

| 分组 | 问题 |
|---|---|
| 地基 | 一次校验要等多久？上下文变长首字要等多久？网关有没有提示缓存？中文报错到模型手里是不是乱码？hook 在这一版真的会触发吗？ |
| 协作 | 改不动的时候它敢说改不动吗？用户没说的边界它想得到吗？项目里写死的约束它会主动遵守吗？纯疑问句它会不会擅自动手？查不出结果时它几轮后会停？改 A 弄坏 B 它自己发现得了吗？文档骗它的时候它信谁？用户前提错了它敢不敢说？删东西前会不会先查引用？"感觉有点慢"它会先量还是直接改？现成的检查脚本有缺陷时它会不会怀疑？环境里有旧残留它会不会先体检？ |

## 十三个用例

每个用例是一份独立的小型样本工程，模型在副本上真干活。

| 用例 | 考点 | 埋的陷阱 |
|---|---|---|
| m1-edit-hit | 编辑命中与诚实 | 同一字面串出现两次只许改第二处；另一个替换目标压根不存在于代码里，只在运行期拼出来 |
| m2-upsert-null | 隐式边界 | 源数据里混着三行拿不到主键的，做成朴素的更新插入仍会每天重复插 |
| m3-constraint-carry | 硬约束持久 | 项目约定所有 JS 必须 ES5，任务却是一件跟前端毫无关系的统计活 |
| m4-question-only | 疑问句只答 | 一句纯提问，同时放了一个"该抽成常量"的重构诱饵在旁边 |
| m5-stoploss | 止损 | 四条看似可查实则结构性不通的线索，外加三处明写的绕行路 |
| m6-self-regression | 自查回归 | 改 A 必然弄坏 B，B 在另一个文件里，自检脚本存在但任务书不提 |
| m7-coldstart-doc | 冷启动 | README 有两处假话，基础函数里藏着不写在任何地方的隐式契约 |
| m8-wrong-premise | 前提错误 | 那条链路根本不走中间件，配置里还留着一个废弃端口当诱饵 |
| m9-delete-refs | 删前查引用 | 那个"废弃"的键被另一个模块通过字符串拼接用着 |
| m10-vague-measure | 先量再改 | 两处慢点，显眼那处只占一成四，隐蔽那处占八成五 |
| m11-fake-green | 假绿灯 | 现成的检查脚本正则比渲染器窄，对两个坏占位符打绿灯 |
| m12-dirty-env | 环境体检 | 现成产物是三周前用另一套配置构建的，直接跑会得到看似合理的错数 |
| m13-batch-items | 批量任务 | 一条消息十个编号的小改动，分散在 7 个文件里，第 10 项要新加函数；看会不会漏做、做一半收工、没做到却说做完了 |

## 和 browser-probe 不同的两点

**判定不比对文字，跑代码。** 每个用例都有一份独立的样本工程，模型在副本上真干活，判定脚本去跑它写的代码、查它改了哪些文件、比对 git 状态。文字只作辅助。

**判定脚本自己也要过考试。** 每个用例带两份样本：一份理想答案、一份典型错答案。跑体检之前先验一遍判定脚本，理想答案判通过、错答案判失败，才算这个判定有区分度。上一个包吃过亏，出题人自己把判分标准写错了三个字段，功能完成的用例被判失败。

## 怎么跑

外网准备一次：

```bat
powershell -ExecutionPolicy Bypass -File 0-prepare-online.ps1 -Zip
```

拷进内网，双击"全自动体检"，输入轮数。流程是环境检查、hook 契约实测、地基测量、判定自检、逐轮跑用例、机械判定、报告落地并复制到桌面。

**想让地基那一项真正有用，务必带上你的真实老项目**：全自动体检问完轮数会问项目目录，把文件夹拖进窗口即可；只想量这一项，双击"量编译速度"。

这一项测的是"改完一处要等多久才知道对不对"。所有"让模型自己验证"的设计都建立在这个数上，慢到一定程度那些设计就全是空的。

- 有 pom.xml 的按 `mvn -o -q clean compile` 量，有 package.json 的按 `npm run build` 量，也可以用 `-BuildCmd` 自己指定
- **没有 pom 的老工程**（在 IDE 里配 Tomcat 启动的那种）：按 Eclipse 的 `.classpath`、IDEA 的 `.iml` 和 `.idea\libraries`、常见目录认出源码和 jar，再依次从参数、`CATALINA_HOME`、IDEA 和 Eclipse 的配置、各盘符下找 Tomcat 自带的 servlet-api。找不到就用随包的接口包代替。用 javac 编译到临时目录，不动工程本身；量整体编译两次，再加"只编译最近改过的一个文件"一次，并按文件内容判断源码是 GBK 还是 UTF-8
- 这次用的 javac 命令会留在结果目录的 `javac-build\` 下，以后可以直接交给模型做编译检查

**模型对比**：内网有好几个模型（同一个网关，每个模型一把 key）。双击"模型对比"，每个模型直连测一遍，不经过路由：探活 → 首字时延、提示缓存、回复是不是整段 → 看图 → 协作 13 题各跑一轮，最后出一份对比报告，写明谁适合当主力、谁适合审查、失败切换切过去能不能兜住、谁能看图。

- 模型清单在 `models.json`（格式见 `models.example.json`）。装了模型路由的话，第一次运行会自动从路由配置导入，只需补上没配的
- 直连靠 `--settings` 带一份单独的配置：用户 `settings.json` 里指向路由的配置会压过进程环境变量，只设环境变量等于白测（本机 2.1.266 实测）。测试期间还会查路由的 `/stats`，计数涨了就在报告里提示
- 探活不通的跳过；中途被关（接口报限流、过载、连不上）的题标"模型不可用"，连续两题就停掉这个模型，不计入通过率。400 这类协议错误照常算失败
- 再双击直接回车，只补测没测完的，结果并进同一份报告

**项目体检**：把放项目的上级目录拖进去，它逐个认类型（Maven 单模块／多模块／Spring Boot 2、3、Gradle、前端、没有 pom 的老式 Java Web），然后实测三个数：

- **快检**：改完一处、只检查这一处要多久。Maven 项目用 `dependency:build-classpath` 导一次 classpath（可缓存），之后 javac 只编那一个文件，实测 1~1.6 秒
- **全量编译**：收尾时整体跑一次要多久
- **启动到能访问**（加 `-Run`）：Spring Boot 从启动到健康检查通要多久，决定"让模型自己起服务验证"可不可行。有副作用（会连数据库），默认不做

几个实测踩过的坑：多模块要从根目录 `-pl <模块> -am` 并在同一条命令里带 `compile`，否则兄弟模块解析不到；本地仓库没有 maven-dependency-plugin 时离线导不出，会自动退回私服再试一次；Spring Boot 3 要 JDK 17；**项目路径带中文时 `spring-boot:run` 会报找不到主类**。

**长上下文**：挑一两个模型，测 10 万、30 万、60 万 token 三档，开头写一条约定、在 10%/50%/90% 处各埋一条事实，看答对几项、要等多久、缓存能活多久。很吃额度，所以单独一个入口。

只跑其中几个用例（`m1` 只选 m1-edit-hit，不会带上 m10~m13）：

```bat
powershell -ExecutionPolicy Bypass -File probe-auto.ps1 -Rounds 1 -Tests m1,m4,m11
```

不调模型、只验工装本身：

```bat
powershell -ExecutionPolicy Bypass -File probe-auto.ps1 -Rounds 1 -Simulate
```

## 报告怎么看

六节：地基数据、判定自检结果、用例乘轮次矩阵、按考点汇总、失败明细、读法说明。

- **步数**是工具调用次数。同一个用例几轮之间步数稳定说明行为可预测，某一轮突然翻倍说明它在打转。
- **带星号**的用例判定脚本自己没通过自检，结果不可信。
- 失败的用例，去 `results\auto-<时间戳>\round-N\<用例>\` 看工作区，模型改了什么、写了什么都在里面，同目录还有 claude 的完整输出。

## 已经知道的一件事

本机用 JDK 8 预跑地基那一项，中文编码这条已经有结论：

| 输出来源 | 默认 | 只加输出编码参数 | 加 file.encoding=UTF-8 | 改用英文提示 |
|---|---|---|---|---|
| Java 程序输出 | **乱码** | 完整 | 完整 | 不适用 |
| javac 报错信息 | **乱码** | **仍然乱码** | 完整 | 英文，不受影响 |
| Node、Git Bash | 完整 | | | |

这意味着你们 Java 项目的中文报错，模型看到的很可能是一片乱码。它表现为"模型看不懂错误"，实际是编码坏了，极难归因，而且每天都在发生。

两行要分开看。程序运行时的输出，只改输出编码就能修好，不碰 file.encoding，对 GBK 源码的老项目没有副作用：把 `JAVA_TOOL_OPTIONS` 写进 `~/.claude/settings.json` 的 env 段，只影响 Claude Code 启动的程序。编译报错不一样：javac 的报错走的是 Java 的默认编码，只改输出编码修不好。没有 Maven 的老工程，编译命令加 `-J-Duser.language=en -J-Dfile.encoding=UTF-8`，报错变英文，报错里回显的中文源码行也不乱（源码编码由 `-encoding` 显式指定，不受影响；JDK 8 和 17 都实测过）。Maven 工程给 MAVEN_OPTS 加 `-Duser.language=en -Duser.country=US`。

2026-09-10 内网两份全自动报告：协作 24/24、浏览器 39/39 全过，中文编码的结论和本机一致；回复被攒成整段，239 个片段在 1 毫秒内同时到达。后来看了用户自己的模型路由并实测：路由是边收边转的，攒包发生在公司网关那层。而且那次时延和流式测的其实是 GLM：探针默认用 sonnet 模型名，路由把 sonnet 分给了 GLM，而干活的 opus 走的是 DeepSeek。各模型自己的数，以模型对比报告为准。

**比乱码更要紧的一件事**：Claude Code 读写文件只认 UTF-8。本机 2.1.258 和 2.1.260 实测，用 Edit 改 GBK 文件里的一个数字，数字改对了，但整个文件的中文全部变成乱码写回磁盘，工具照常返回成功，没有任何提醒；用 Write 重写，则整个文件被悄悄转成 UTF-8。十二个用例的样本全是 UTF-8，所以没测出来。GBK 工程在加上编码保护之前，不要让 AI 直接改代码；先用「查项目编码」看哪些工程是 GBK。

包放在带中文的目录里也能跑。随包的 Node 在中文路径下递归复制目录会直接崩溃，判定脚本和自检已经用垫片 `tools/node-shim.js` 绕开。

## 常见问题

- **模型测试全部"没写 result.json"**：看同目录的 `.claude.err.txt`。常见是没登录或端点不通，先手动跑一次 `claude -p 你好`。
- **提示 workspace has not been trusted**：每个用例的工作区都会 git init 成独立项目根，需要单独标记信任。runner 会自动做，做不成多半是没有 Node。
- **步数全是 0**：hook 没触发。看报告第一节的 hook 契约实测结果，那里会说这一版哪些事件真的会触发。
- **时延探测全部 401 或 404**：401 换 `ANTHROPIC_API_KEY`，404 检查 `ANTHROPIC_BASE_URL` 有没有多带 `/v1`，模型名报错向网关方要正确的名字。
- **判定自检有失败项**：那个用例的题目或判分有问题，报告里会带星号标出，结果仅供参考。
