# 自动更新和上报

团队的 GitLab 仓库有两个用途：仓库里放着解开的安装包，各台电脑从这里拿新版；仓库的 issue 收问题反馈和使用情况。都在配置页"更新和上报"那一页看和改。回到[用户手册](../README.md)。

## 你要做什么

1. 装一次（见用户手册"装和升级"）。以后不用再拷压缩包。
2. 电脑上要有 git。
3. 和 GitLab 换过 SSH 密钥的，什么都不用填。没换过的，在配置页"更新和上报"里填一个个人访问令牌。

仓库地址默认是团队的那个，不用改。

## 连仓库走哪条路

挨个试，走通的那条记下来，下次先试它：

| 顺序 | 走哪条 | 要什么 |
|---|---|---|
| 1 | 配置页里手填的令牌 | 个人访问令牌，勾 `read_repository`；要建 issue 再勾 `api` |
| 2 | SSH 密钥 | 这台电脑的公钥登记在 GitLab 上，并且手动连过一次（确认过指纹） |
| 3 | 这台电脑上 git 已经登录的账号 | 凭据管理器里记着 |

- SSH 地址默认照仓库地址推（`http://主机/组/项目.git` 推成 `git@主机:组/项目.git`）。SSH 端口不是 22 的，在配置页填 `ssh://git@主机:端口/组/项目.git`。
- git 和 ssh 一律不交互：要输口令、要确认指纹的直接失败并说明原因，不弹框、不卡住。密钥带口令的在后台用不了，要填令牌。
- 令牌不写进仓库地址，也不写进 `.git/config`。模型读不到令牌，见[保护和放行](保护和放行.md)。

## 自动更新

1. 会话开始、你发消息、Claude 收工的时候，钩子看一眼该不该检查了；该了就甩一个后台进程，钩子马上返回。
2. 后台进程问仓库现在是哪个提交，和上次一样就结束。
3. 不一样就下载到 `~/.claude/vibe-kit/update/repo`，只拿最新的那一个提交。
4. 等路由手上没有请求（最近 20 秒也没来过请求），再运行下载下来的 `install.js`，和手动双击安装是同一个程序。
5. 装完自检：每个钩子、每个库都载得进来，状态栏跑得出来。
6. 自检不过：从仓库拿上一版的标签装回去，记一条问题反馈。同一版装坏两次就不再装，等仓库里出新的。

| 开关 | 默认 | 说明 |
|---|---|---|
| 发现新版之后 | 自动装上 | 还可以选"只提醒""不检查" |
| 几小时检查一次 | 2 | 1 到 24 |

- **装着的版本跟着仓库走**：仓库退回了旧版，开着自动更新的电脑也跟着退；手动装了比仓库新的包，下一次检查会换回仓库里那一版。
- 你的开关、本机环境、模型和 key、问题反馈、仓库地址和令牌，更新时原样保留。没装过路由的电脑，自动更新不会给它装上路由。
- 状态栏：刚更新过的一小时里显示"已更新到 xxx"；选了"只提醒"时显示"有新版 xxx，去配置页更新"；装不上时显示"新版 xxx 没装上，看配置页"。
- 日志在 `~/.claude/vibe-kit/update/update.log`，安装器的输出在 `update/last-install.log`。
- 临时不想让它在后台检查和上报：设环境变量 `VIBE_KIT_NO_UPDATE=1`。

## 问题反馈

套件拦错了、漏拦了、报错、提示看不懂、卡住，都应该回到改套件的人手里，而不是停在某次聊天里。

- 记在 `~/.claude/vibe-kit/feedback/`，一台电脑一处，装新版、卸载都不删。一条问题一个 `.md`：套件和 Claude Code 版本、模型、哪道检查、现象、当时在做什么、为什么认为是套件的问题、怎么处理的、建议，附上拦下时的原话和钩子流水账的最后 20 行。密码、token 之类遮掉。同样的问题不另起一条，只把次数加一。本机最多留 1000 条。
- 谁来记：Claude 觉得套件有问题时用 `tools/feedback.js add` 记（它嘴上说了"是钩子的问题"却没记，收工检查会让它补）；钩子出了异常、HTTP 方式下 25 秒没结果，自动记。已经记过的用 `feedback.js add --same <问题编号>` 并上去。
- 这个会话记过套件问题的，收工交代里只列数量和可点击的详情链接；真正影响交付的问题照样要说清楚。
- 不记成问题的：同一条理由反复拦（记次数，配置页"更新和上报"的"拦得最多的规矩"）；在配置页改开关（"保护"一节的改动记录）；申请放行（"放行记录"，申请时加 `--bug` 才记成问题）。

## 问题上报

- 本机记下的问题由后台进程建成仓库里的 issue，传的就是本机那份记录（已经遮过密码、令牌、内网地址）。配置页"更新和上报"列着每条报成了哪一条 issue，点编号打开。
- 不重复建：别的电脑报过同样的问题、issue 还开着，就在那条下面加一句"这台电脑上也出现了"。又出现了在对应 issue 下补一句，同一条 12 小时最多补一次。issue 已经关了又出现，新建一条，写明之前是哪条。
- 装好那一刻之后新记的、又出现的才传。套件代码被改过的记录不传。一次最多传 8 条，剩下的下次传。
- 传不上去不影响使用，问题照旧存在本机。令牌不对、没权限时停 6 小时再试。

GitLab 的接口只认令牌：

| 情况 | 怎么办 |
|---|---|
| 配置页里填了令牌 | 用它 |
| 没填，SSH 是通的 | 用 SSH 密钥向 GitLab 申请一个，权限 `api`，30 天，到期前自动换。在 GitLab 账号的"访问令牌"里看得到，名字是 `vibe-kit-<电脑名>`。不想让它申请：配置页"没填令牌的时候"选"不申请" |
| 没填，GitLab 不支持用 SSH 申请 | issue 建不了，问题只存在本机；要上报就手填一个令牌 |

## 使用情况上报（默认开）

拦对了但提示写得不清楚、上下文涨过了线、审了好几轮才过，这些不会有人记成问题。所以每天数一数次数，传给改套件的人。

- 数什么：会话怎么来的（新开、恢复、/clear、压缩后）、开口几次、进 OpenSpec 流程几次、交接几次、收工报告几次；各道检查拦了几次、放行几次；上下文到 70%、90%、超过上限的会话各几个；各审查点审了几轮、报"0 条"的几轮、轮数用完几次；开工前拉代码的结果；钩子出错几次；Claude Code 和套件的版本、系统、和默认不一样的开关；路由里各模型当天的请求、失败、切换、token；审查超时次数。
- 不传：路径、项目名、文件名、分支名、提交信息、提示词、代码、模型的回答、令牌、key。模型名字里带内网地址的遮掉。耗时只在本机"本机环境"页看，不上报。
- 怎么传：每份安装一条 issue，标题"[使用情况] 设备标识"，一天补一条。设备标识是随机的，不从电脑名来。只传过完的日子；一次最多补 7 天，本机的数留 14 天。
- 配置页"使用情况上报"：看传到了哪一天；"看看要传的内容"看今天攒下的样子；"立即上报"马上传过完了的日子。关掉之后本机照样数，不传。

## 出了问题先看哪

1. 配置页"更新和上报"点"测试连接"，分三行说拿新版、SSH、建 issue 通不通，不通的写明原因。
2. 这一页上"上次检查""上次上报"两行，失败原因直接写在那里。
3. `~/.claude/vibe-kit/update/update.log`。

## 维护的人：导出 issue

"更新和上报"那一页"问题上报"的最下面，只在维护套件的那台电脑上出现（是哪台写死在套件代码里）。

- 只导出开放中的问题 issue 和下面的补充，合成一份 `.md` 由浏览器下载，本机不存；最后附上各台电脑的使用情况汇总（上次导出之后的，没导出过就是最近 7 天）。页面上留一个"再下载一次"。
- 文件交给浏览器之后问一句存下来没有：点"确定"这一批才在 GitLab 上关闭，下面留一句"已导出"；点"取消"不关，下次再带上。导出之后、关掉之前又有人补充的不关。各台电脑的"[使用情况]" issue 不关。
- 只想看不想关：去掉"下载之后把这一批关掉"的勾。

## 维护的人：发布

1. 打包，把压缩包整个解压出来。
2. 双击 `发布到 GitLab（双击我）.bat`。

它按顺序做：关掉这台电脑的自动更新（不然会被换回仓库里的旧版）；在这台电脑上装一遍、自检，不过就停；连仓库看现在是什么；推一个提交和一个标签 `v<版本号>`（各台电脑装坏了退回上一版靠这个标签）；更新说明这一版里写了"修了 #编号"的 issue，下面留一句是哪一版修的。

| 仓库里现在是 | 怎么处理 |
|---|---|
| 空的，或者只有建项目时带的 README | 照常发布 |
| 不是套件的安装包 | 不发；确实要用这个仓库，加 `--force` |
| 同一个版本号、内容一样 | 已经发过了，什么都不做 |
| 同一个版本号、内容不一样 | 不发，重新打包换一个版本号 |
| 比这个包新 | 要输入 yes 确认：发布之后所有人都会退回这一版 |

- 要推送权限：令牌勾 `write_repository`；走 SSH 的账号在项目里至少是 Developer，分支受保护的要 Maintainer。
- 命令行参数：`--no-install` 不装只发，`--dry-run` 只看不推，`--rollback` 退回旧版不再问。
- Claude 要跑发布脚本时，和 `git push` 一样弹确认框，要你点头。
