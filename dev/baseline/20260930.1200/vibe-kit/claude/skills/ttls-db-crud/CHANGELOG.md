# ttls-db-crud 变更记录

> 当前版本 **1.0.0**。这个技能原来叫 urai-db-crud，在 skytech-skills 仓库里；2026-09-30 并进 vibe-kit，以后在 vibe-kit 这边维护。

## 1.0.0 —— 2026-09-30　并进 vibe-kit：改名、驱动不随包、少起进程、少写 SQL

**为什么改**

使用者提的：并进 vibe-kit 一起装；名字改回 db-crud，套件里的技能统一加 `ttls-` 前缀；驱动不要再随包带；用起来慢、要写很多 SQL。

**改了什么**

- 名字：`urai-db-crud` → `ttls-db-crud`。配置文件新建的叫 `.vibe/db-crud.ini`，以前的 `.vibe/urai-db-crud.ini` 照样认，两个都在用最近改过的那一份
- **驱动不随包带**。登记在 `~/.claude/vibe-kit/drivers.json`，在配置页「数据库驱动」里管（到 Maven 本地仓库里找，或者自己选）。升级时旧技能自带的驱动自动挪过来
- **一条命令只起一次 java**。执行器加了几种模式：`describe`（几张表的列和主键，大小写自己试）、`peek`、`multi`（几条查询）、`find`、`apply`（核对行数、快照、执行、提交、取主键）。以前看一张表的结构要起 2 到 4 次，写操作的第二步要起 3 到 5 次
- **少写 SQL**：新命令 `find <关键字>`；`columns --table A,B,C`；`peek --eq 字段=值`（参数绑定，值不用加引号）、`--cols`、`--count`；`query` 可以给几个 `--sql`
- **表结构存在本地**（`.vibe/db-crud.cache.json`，12 小时）：再看同一张表不连库。输出里说明是缓存；`--fresh` 重新查；通过这个工具改了结构会自动作废
- **写操作的行数在事务里核对**：确认的时候是 N 行，执行的那一刻不是 N 行了就不执行。以前是先数一遍、再执行，中间有空档
- **`query` 只许跑查询**。以前不查：有的驱动用查询的接口也能执行写语句，改结构的语句还会自己提交，等于绕过了确认。现在增删改、改结构、`SELECT … INTO`、`EXPLAIN ANALYZE` 都拦下（退出码 3）
- **只读的模式最后一律回滚，不提交**
- 取列的元数据时按表名原样再筛一遍：`getColumns` 的表名是个模式，下划线是通配符，`T_ORDER` 会把 `TXORDER` 的列也带出来
- java 的启动参数加了 `-XX:TieredStopAtLevel=1 -XX:+UseSerialGC -Xshare:auto -XX:-UsePerfData`，起得快一些；JVM 不认的话自动去掉再来
- 找 java 多看一处：vibe-kit 配置页「本机环境」里配的 JDK
- **后台执行器**（开关，默认关）：打开之后连接留着，几分钟不用自己退。见 `references/连接配置.md`
- **用量和毛病自动记**：每条命令的耗时、起了几次 java、出错的类别记进 vibe-kit；脚本自己崩了、执行器没有输出、找不到驱动，自动记成套件的问题反馈。不记 SQL、数据、连接串、口令
- 起子进程一律不弹窗口（后台自动探索、配置页调它的时候没有控制台）

**发布前全仓审查之后改的**（同一个版本）

- **`init` 只配开发环境的库**。以前会把扫到的都写进来，生产库只有文件名里带 prod 的才标只读；这个命令模型自己会跑。现在交给套件的探索去做（和后台自动探索同一套），测试、生产的只列出来、不配
- **执行的是分析过、确认过的那一条**，不是文件里的原文。原文结尾的分号（Oracle 不收）、注释不再交给数据库
- **SQL 的注释和转义按数据库分**：反斜杠转义、`#` 注释只有 MySQL 认；MySQL 的 `--` 后面要有空白才是注释。以前一律按 MySQL 的认，Oracle、达梦上 `'D:\dir\'` 后面的 WHERE 会被当成在字符串里
- **带别名的、子查询里有 GROUP BY / ORDER BY 的 UPDATE / DELETE 能数行数、能取快照了**；连了别的表的数不出来，判成 DANGEROUS
- **风险收紧**：影响面数不出来的、认不出目标表的判 DANGEROUS；`ON DUPLICATE KEY UPDATE`、`ON CONFLICT` 的插入判 WARN
- **确认串只能用一次**，而且绑着连的是哪台库、哪个账号。影响面里打出地址和账号
- **提交之前再核对一遍实际动了多少行**：比确认的多就回滚；到了硬上限也回滚
- **禁止名单和上限写进连接配置**，命令行上只能收紧
- **`exec --undo <留痕目录>`**：照反向 SQL 还原，整份在一个事务里，每一条都得正好动一行
- **`peek` 的 `--where`、`--order` 拼进 SQL 之前先查**；表名、列名加着引号拼（保留字、大小写混写的名字以前会拼出错的 SQL）
- **没指定 schema 时只在当前的 schema / 库里找**，同名的表不再混在一起；`tables` 不再列整台服务器的表
- 大小写的试法补全：schema 和表名分开试（`sysdba.T_ORDER` 以前找不到）
- 表结构缓存：看过别的 schema 的同名表之后，默认 schema 的那张不再拿到它的结构
- **查询结果看得全**：`--width`；结果只有两三行、有长值时竖着排
- **记坑**：人记的排前面，`note --list` 列全部；大小写一个连接只记一条；没有主键的不再往配置里记
- 改前快照交给驱动限行数，大范围的改动不再把整个结果集读进内存
- 执行器没看到结束标记就不执行（那头写到一半断了，收到的可能是半截 SQL）
- 后台执行器：先握手再交口令；写操作交出去之后没等到回话的不重发；状态文件被别的执行器接管之后自己退
- 找 java：配置页里的 JDK 排到缓存前面；java 太老时明说
- 连接串、报错里带着的口令遮掉；口令不对时让模型告诉用户去改，不让它自己打开配置文件
- `jdbc:postgresql` 的连接找 PostgreSQL 的驱动
- 反向 SQL 里的列名是保留字的加引号；没有主键的表上的更新不再生成一份定位不到行的反向 SQL
- 去掉了没人用的 `write` 模式

**没跟着改名的：`~/.db-crud/`**（留痕、以前放的驱动、兜底配置）。

**动了哪些文件**

`scripts/db.py`、`dbconf.py`、`vibe.py`、`sqlguard.py`（加 `readonly_problem`、`rows_in_token`）、`notes.py`、`discover.py`、`runner/DbRunner.java`；新增 `scripts/metacache.py`、`stats.py`、`daemon.py`；`SKILL.md`、`references/连接配置.md`。删了 `drivers/`。

**验证**

三个自测（分级和分析 83 项、记坑、剥注释和落点）通过。连库的部分拿 H2（MySQL 兼容模式）走了完整的读写循环：建表、插入含中文 / NULL / 空串 / 引号的行、看结构、按值找、几条查询一起跑、两步确认的更新、行数变了不执行、反向 SQL、照反向 SQL 还原、确认串用第二次、同名的表在几个 schema 里、后台执行器握手和不重发（`dev/test-dbcrud.js`，154 项）。
**达梦、神通、Oracle、金仓、MySQL 的真库在这次改动之后没有验过**：改的是执行器的编排，连库、取数、提交用的还是原来的 JDBC 调用。第一次在真库上用的时候跑一遍 `conn test` 和一次完整的读写。

## 0.7.0 —— 2026-09-23　少写 SQL 文件、标识符大小写自适应、踩过的坑记进配置

**为什么改**

使用者用下来提的三条：

1. 「查数据库之前你总会产出很多 sql 文件，这是必要的还是什么，我其实希望效率优先」
2. 「还出现过大小写问题」
3. 「使用的过程中遇到的问题你能一起记录到 urai-db-crud.ini 文件中吗，防止二次触发」

**改了什么**

**一、少写文件。** 原来 SKILL.md 那条「SQL 写成文件」的纪律是为长 SQL 和转义问题定的，
结果查一行数据也先落一个 .sql 文件，纯属浪费。改成分三档：
看某张表里有什么用新加的 `peek`（连 SQL 都不用写）；一行能写完的用 `--sql`；
只有多行、带中文字面量、带嵌套引号的才落文件。

新增 `peek --table X [--where ...] [--order ...] [--limit N]`。

**二、标识符大小写自适应。** 达梦、Oracle、金仓的 Oracle 兼容模式把不带引号的标识符
折成大写，神通和 PG 模式折成小写。人按代码里的写法敲 `t_order`，库里是 `T_ORDER`，
`getColumns` 返回空 —— **而且不报错**，「查不到」和「表不存在」长得一模一样。

`columns` / `peek` / 取主键三处都改成自己试：原样 → 全大写 → 全小写。
取主键那处尤其要紧 —— 认不出主键，UPDATE 的反向 SQL 会退化成拿整行当条件，
是悄悄降级，不会有任何报错。试出来和输入不一样时顺手记一条坑。

表实在找不到时明说「三种写法都试过了」，并给出下一步，不再拼一条注定失败的 SQL
去换一句数据库原话。

**三、踩过的坑记进 urai-db-crud.ini。** 新增 `scripts/notes.py` 和 `note` 子命令：

    db.py --conn main note "这个库是 Oracle 兼容模式，空串会变 NULL"

记在配置里那个连接名下，**之后每次用这个连接都会先打出来**。
大小写、某张表没有主键这两类工具会自动记。

- 坑跟着连接走，所以记在连接旁边，谁用谁看得见
- **改文件用文本方式，不走 configparser 回写** —— 回写会把注释全吃掉，
  而「来自 application.yml:6」这种出处注释是有用的
- 同一条不重复记：这功能是「别再踩第二次」，记成流水账人就会连要紧的提示一起跳过

**动了哪些文件**

新增 `scripts/notes.py`、`scripts/notes_selftest.py`；
改 `scripts/db.py`、`scripts/dbconf.py`、`SKILL.md`、`docs/urai-db-crud/` 三份文档、`expected.json`

**验证**

达梦上用小写表名 `dept` 查（库里是 `DEPT`）：自动试出来、提示了、并把这条记进配置；
再查时坑自动出现在最前面；重复记同一条会拒绝；记完之后配置里的注释、
另一个连接段、原有字段原样还在。MySQL 上 `peek` 带 `--where` / `--order` 正常出数据。
新增 `notes_selftest.py` 盯着「改配置不能弄坏别的东西」，冒烟 12 → 13 条。

## 0.6.0 —— 2026-09-23　不再劝人别用明文口令；.vibe 落到拥有配置的项目下

**为什么改**

使用者提的两条：

1. 「总是提示密码要用占位符，我是内网的开发环境，密码就用明文就行」
2. 「之前 init 把配置初始化到壳子里面了，这次又到了对应的后端。
   以后 init 直接到对应的项目中的 .vibe 就行，考虑有壳子和没壳子情况」

**改了什么**

- **撤掉明文口令的警告。** 这个工具面向内网开发库，连接信息本来就躺在项目的
  `application.yml` 里，`init` 扫出来的口令也是从那儿原样抄的 ——
  提醒的那个「风险」在工具介入之前就存在。而这句话出现在**每一条命令**的输出里，
  结果是人对所有提示脱敏，连快照没取全这种要紧的也一起忽略。
  占位符写法仍然支持，只是不再推销
- **`init` 把 `.vibe` 写进真正拥有这份配置的项目**：从配置文件往上找带 `pom.xml` /
  `build.gradle` / `build.xml` 的目录，取最靠外的那个。有壳子落后端、没壳子落自己、
  多模块落聚合根。**刻意不认 `.git`** —— 壳子常常本身就是 git 仓库，按 `.git` 找会落回壳子
- **查找时上下都找**：当前目录 → 往上最多 5 层（子模块里开 Claude Code）→
  往下最多 3 层（壳子根上开 Claude Code）。往下找到多份会明确报错让人用 `--project` 指定，
  不猜 —— 猜错就是连到另一个库上
- 探测缓存跟着配置走，不跟着当前目录走
- 一个壳子里有多个后端时各写各的 `.vibe`，并提示「在哪个项目目录里开就用哪一份」
- 新增 `scripts/discover_selftest.py`：剥注释 + 落点的离线回归（这两块错了不会报错，
  只会悄悄连到别的库上）。冒烟 11 → 12 条

**动了哪些文件**

新增 `scripts/discover_selftest.py`；改 `scripts/dbconf.py`、`scripts/db.py`、
`scripts/discover.py`、`scripts/vibe.py`、`SKILL.md`、`references/连接配置.md`、
`docs/urai-db-crud/` 三份文档、`expected.json`

**验证**

四种落点情形实测：有壳子（落后端，壳子根和后端目录两头都找得到）、没壳子、
多模块（落聚合根）、壳子里两个后端（各写各的，从壳子根查会明确报「有好几份」并退 1）。
冒烟 12 条全过。

## 0.4.0 —— 2026-09-21　init 改成自动扫项目配置

**为什么做**

原来的流程是「init 生成空样例 → 人手填 jdbc 串和账号 → setx 设口令 → 自检」，
四步，太啰嗦。而**被操作的项目自己就存着这些信息**。

**做了什么**

- `db.py init` 现在会扫项目配置，把找到的连接写进 `.vibe/urai-db-crud.ini`，再逐个试连。
  覆盖 Spring Boot（`application*.yml` / `.properties`，含 Druid 多数据源）和
  Spring MVC 老项目（`jdbc.properties`、XML 里的数据源 bean）两种形态
- 新增 `db.py discover`：只看不写，报这个项目用到了哪些库、配置在哪
- **扫描前先剥注释**。实测一个老项目的 `proxool.xml` 里 11 条 JDBC 串只有 1 条生效，
  其余都在 `<!-- -->` 里 —— 照单全收会生成一堆假连接，而那些地址多半是别的环境甚至生产库
- **像生产库的自动标只读**：文件名或数据源名里带 prod / 生产 / online 的加 `readonly = true`
- 连不上时给能照做的下一步：库名不对会列出这台服务器上实际有哪些库；
  口令不对、地址不通分别给不同的提示
- 靶场新增 `fake-project/`：Spring Boot 多数据源 + 老项目 properties + XML 三种形态，
  里面埋了 5 处注释掉的旧地址做回归；冒烟从 9 条加到 11 条

**动了哪些文件**

新增 `scripts/discover.py`、`testbed/urai-db-crud/smoke/fake-project/`；
改 `scripts/db.py`、`SKILL.md`、`docs/urai-db-crud/` 三份文档、`expected.json`

**验证**

在真实项目上验过两种形态：一个 Spring Boot 项目（扫出 MySQL 并试连，
库名不存在时列出了服务器上实际有的库）、一个 Spring MVC 老项目
（`proxool.xml` 11 条里正确只留下生效的 1 条）。冒烟 11 条全过。

## 0.3.0 —— 2026-09-21　驱动随包自带；配置搬进 .vibe；金仓实测通过

**为什么做**

拷到别的电脑上用还要另外准备驱动 jar 太麻烦，国产数据库的驱动又不在
Maven 中央仓库，很难找。配置放在用户目录也不对 —— 一个项目连哪几个库，
应该跟着项目走。

**做了什么**

- **五种数据库的驱动随包自带**（`drivers/`，10 MB）。查找顺序仍把"项目自己的驱动"
  排最前，自带的排在 `~/.m2` 前面（Maven 仓库里是什么版本全凭运气，
  比如 `ojdbc8-21.5` 连不上 Oracle 11.2）

## 0.1.0 —— 2026-09-21　首版：达梦和神通可用

**为什么做**

原来这套能力在一个独立的 Java MCP 服务器里（ADT，`AI-Database-Tool`）。
它要注册进 `settings.json`、改完得重启 Claude Code、分发包 70MB 还自带一个 45MB 的 JRE，
而且编译目标是 Java 17，被操作的老项目机器上常常只有 JDK 8。
决定不再维护那个工程，把「读 + 写」这部分搬成不需要任何常驻服务的 skill。

搬迁的前提在读代码时确认了：那套东西**没有跨调用的数据库事务**，
每次工具调用都是自己取连接、自己提交，所以「一条命令一个进程」在语义上不丢东西。

**做了什么**

- **执行器 `scripts/runner/DbRunner.java`**：只 import `java.sql`，不依赖任何第三方库。
  用 `javac --release 8` 编一次，JDK 8 / 11 / 17 通吃。驱动用被操作项目自己的 jar，
  靠 `-cp` 挂进来，不随包分发。口令走环境变量，SQL 走标准输入，结果一行 JSON 打到标准输出。
- **`scripts/dbconf.py`**：ini 格式的连接配置、`${ENV:}` / `${FILE:}` 口令占位符、找 java、找驱动 jar。
- **`scripts/sqlguard.py`**：保守的 SQL 分类与四级风险分级。规则表从 ADT 的 `RiskClassifier` 移植。
  **拿不准一律判 DANGEROUS**，看不懂的语句绝不放行。
- **`scripts/journal.py`**：改前快照、操作日志、反向 SQL 生成。落在 `~/.db-crud/journal/` 下，
  **刻意不放进被操作的项目里**——快照里是真实业务数据，放项目里早晚被 git 提交上去。
- **`scripts/db.py`**：入口。`conn list/test`、`tables`、`columns`、`query`、`exec`。
- **`scripts/sqlguard_selftest.py`**：45 条离线用例，其中 14 条移植自 ADT 的 `RiskClassifierTest`。

**和 ADT 不一样的几个决定**

- **不自动回滚**，只生成反向 SQL 给人看。ADT 的自动 undo 有「失败了记成已撤」
  「无主键 UPDATE 匹配 0 行仍报成功」这类毛病，做成「看起来撤回了其实没撤」比不做更糟。
- **快照存 JSON 不存 CSV**，值带 JDBC 类型，NULL 存成 `null`。
  ADT 用 CSV，分不清 NULL 和空串、丢了列类型，这是它还原不可靠的根源。
- **元数据走 `DatabaseMetaData`**，不拼各家的系统表 SQL。五种数据库一套代码，
  达梦和神通的系统视图名都不用维护。
- **失败显式 `rollback()`**。ADT 靠连接池归还连接时回滚，直连模式下这个行为由驱动自己决定，
  Oracle 系的驱动关闭连接时可能隐式提交。
- **任何会改数据库的语句都要确认**，不按风险等级放行。
  测试时发现按等级放行会导致「先跑一次看看影响面」的那次调用本身就把数据改了。

**动了哪些文件**

新建 `skills/urai-db-crud/` 全部内容、`docs/urai-db-crud/` 五份文档、`testbed/urai-db-crud/smoke/`；
`README.md` 注册表加一行；根 `CHANGELOG.md` 记一条。

**验证**

达梦 8.0 和神通 7.0.8 两个本机实例上跑完了完整读写循环：建表、插入、查询、
带主键的 UPDATE、DELETE、删表，以及用生成的反向 SQL 把数据还原回去。
NULL 与空串经过「删掉再插回来」仍然分得清。离线用例 45 项全过。
详见 `docs/urai-db-crud/验证记录.md`。
