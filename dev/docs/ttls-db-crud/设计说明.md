# 第一部分：给所有人看的

## 一、要解决什么问题

让 Claude 能直接对开发库做读写，但**改之前必须把要发生的事摆出来给人看**。

## 二、它靠什么判断

静态看 SQL（类型、目标表、有没有 WHERE）+ 去库里问一句影响多少行（只问不做），
两样凑齐定风险等级。看不懂的一律按最严处理。

## 三、用起来是什么样

见 `一页看懂.md`。要点：写操作两步走，第一步不改任何东西。

## 四、需要你们配合提供什么

机器上的 java 和数据库的驱动。连接配置（`<项目>/.vibe/db-crud.ini`）一般不用手写：
vibe-kit 在后台自动探索项目时把开发环境的库配进去。驱动在配置页「数据库驱动」里管，
可以让它到 Maven 本地仓库里找，也可以自己选一个 jar。

## 五、能拿到什么

查询结果、表结构；写操作的执行结果、改前快照、反向 SQL。

## 六、做不到什么

不自动回滚、不跨命令保持事务、不翻译 SQL 方言、不替你管口令。

# 第二部分：技术方案

## 七、为什么是 skill 而不是 MCP 服务器

这套能力原先在一个独立的 Java MCP 服务器里（ADT，`D:/WorkSpace/AI/AI-Database-Tool`）。
放弃那个形态的理由：

| 痛点 | 说明 |
|---|---|
| 要注册 | 得改 `~/.claude/settings.json`，改完还要重启 Claude Code |
| 包太大 | 分发包解压 70MB，其中 45MB 是自带的 JRE |
| Java 版本对不上 | 编译目标 Java 17，而被操作的老项目机器常常只有 JDK 8 |

**搬迁成立的前提**，是读代码时确认的一件事：ADT **没有跨调用的数据库事务** ——
每次工具调用都自己取连接、自己提交。所以「一条命令一个进程」在语义上不丢任何东西。
它的「会话」本来就是磁盘上的目录，不是数据库事务。

## 八、为什么必须有 Java

Python 标准库连不了这几种数据库：

| 数据库 | 纯 Python 直连可行吗 |
|---|---|
| MySQL | 可行（协议公开），但只有它可行 |
| 人大金仓 | 勉强（PG 协议），国密认证是坑 |
| Oracle | 不现实，TNS/TTC 协议不公开，认证要 AES |
| 达梦 | 不现实，协议不公开 |
| 神通 | 不现实，协议不公开 |

厂商命令行客户端（`sqlplus`、`disql`、`isql`）在只连远程库的开发机上普遍没装，
输出也不好解析。**JDBC 是唯一能覆盖五种库的现实路径。**

脚本只用 Python 标准库，执行器只 import `java.sql`：内网装不了包。
依赖的是机器上已有的 python、java 和登记好的驱动 jar，不需要安装任何东西。

**并进 vibe-kit 时为什么没有改成 Node**：判断和留痕的代码（分级、快照、反向 SQL）有 45 条离线用例和三轮真库验证垫着，
换语言等于把这些重新验一遍，而快慢不在 Python 这一层（起 Python 约 60 毫秒，起 java、连库要一两秒）。
连库必须走 JDBC，换成 Node 也省不掉 java。只有"扫项目的配置文件"搬了一份 Node 的（`kit/lib/discover.js`），
因为后台自动探索跑在钩子甩出去的 node 进程里，不能指望那时候有 python。

## 九、三块怎么分工

```
db.py         入口：判断、编排、排版、留痕
  ├ dbconf.py   连接配置、口令占位符、找 java、找驱动
  ├ vibe.py     .vibe 目录、探测缓存、读 vibe-kit 的配置
  ├ sqlguard.py 分类与风险分级、查询命令的只读检查（不连库）
  ├ journal.py  快照、操作日志、反向 SQL（不连库）
  ├ notes.py    踩过的坑记进连接配置
  ├ discover.py 扫项目的配置文件（db.py init / discover 用）
  ├ metacache.py 表结构的本地缓存
  ├ stats.py    用量和毛病记给 vibe-kit
  ├ daemon.py   后台执行器的客户端（开关，默认关）
  └ runner/DbRunner.class   唯一连库的东西，只依赖 java.sql
```

**判断逻辑全在 Python，Java 只当执行器。** 这样闸门逻辑是可读、可改、可离线测试的；
Java 那头只负责「连上、按吩咐执行、把结果 JSON 打回来」。

## 十、为什么执行器编译到 Java 8

被操作的老项目机器上常常只有 JDK 8。`javac --release 8` 编出的 class
在 JDK 8 / 11 / 17 上都能跑，**一份产物覆盖全部**。

不走 `java DbRunner.java` 源码直跑（JEP 330），因为：JDK 8 不支持；
而且实测每次多付约 0.9 秒编译开销（源码直跑 1.2 秒 vs 预编译 0.32 秒）。

## 十一、参数怎么传

| 传什么 | 走哪 | 为什么 |
|---|---|---|
| 口令 | 子进程的环境变量 | 命令行会进进程列表，也会进对话记录 |
| SQL | 标准输入 | Windows 命令行 8191 字符上限；引号和中文经两层 shell 转义会坏 |
| 其余参数 | 命令行 | 短、没有敏感内容 |
| 结果 | 标准输出，一行 JSON | 成功失败都是 JSON，上层只解析一种格式 |
| 改前快照 | 单独的文件 | 可能很大，不该挤在标准输出里 |

stdout 显式用 UTF-8 的 `PrintStream`，不依赖 `file.encoding` ——
Windows 上 JVM 默认跟随系统代码页（GBK），不这么做中文会变问号，各 JDK 版本行为还不一致。
Python 侧 `sys.stdout` 和 **`sys.stderr` 都要 reconfigure**，漏了 stderr 错误信息就是乱码。

## 十二、元数据为什么走 DatabaseMetaData

不拼各家的系统表 SQL，一律走 JDBC 的 `DatabaseMetaData`（`getTables`、`getColumns`、
`getPrimaryKeys`、`getIndexInfo`、`getImportedKeys`）。

五种数据库共用一套代码，达梦的 `ALL_TABLES`、神通的 `information_schema` 这些
系统视图名一个都不用维护。ADT 为此写了五份方言实现，其中 85% 是 SQL 模板。

两处要注意的差异：

1. **MySQL 把库名放在 catalog 上，其它几家放在 schema 上**，在 `meta_scope_args()` 里抹平。
2. **元数据的列标签大小写不一致**。JDBC 规范说是大写（`COLUMN_NAME`），
   达梦、Oracle、MySQL、神通都照办，但金仓这类 PG 系的驱动返回小写（`column_name`）。
   所以取列一律走 `_col_index()` 做大小写不敏感匹配。按大写精确匹配的话，
   在金仓上认不出主键，反向 SQL 会**悄悄退化成拿整行当条件** —— 这是实测撞出来的。

主键列要按 `KEY_SEQ` 排序，不能用 JDBC 默认的列名序——联合主键里列的先后是有意义的。

## 十三、风险分级

规则表移植自 ADT 的 `RiskClassifier`，四级定义不变（SAFE / WARN / DANGEROUS / FORBIDDEN）。
移植的保真度由 `sqlguard_selftest.py` 里那 14 条原样搬过来的用例保证。

**分类器是自己写的，没有用 JSqlParser。** 理由是不引第三方 jar，而且保守策略下
不需要完整的语法树——只要能分辨语句类型、目标表、有没有 WHERE 就够了。
代价是像 `MERGE`、CTE 开头的写语句这类会被判成「看不懂」→ DANGEROUS，
换来的是多问人一次，不是更不安全。

分类器要处理的坑（每一条都有对应用例）：

- 注释：`--`、`#`、`/* */`；但 MySQL 的 `/*! */` 是**可执行注释**，不能当注释去掉，直接判危险
- 字符串字面量：`''` 转义、反斜杠转义；里面的 WHERE 和分号都不算数
- WHERE 必须在**括号深度为 0** 的地方找，子查询里的不算外层的
- WHERE 要截到 `ORDER BY` / `LIMIT` / `RETURNING` 之前
- 词边界：列名叫 `where_col` 不能误判成有 WHERE

## 十四、为什么任何写操作都要确认

首版曾按风险等级放行：SAFE 的写操作直接执行。而 INSERT 行数数得出来就判 SAFE，
结果**「先跑一次看看影响面」的那一次调用本身就把数据改了**。

改成：**凡是会改数据库的语句都要确认**。要预览用 `--dry-run`。
简单的规则才不会被误解。

### 确认串为什么长那样

`UPDATE-T_ORDER-3行-11fd6ccd`

前半段是给人看的（动哪张表、多少行），后半段是 SQL + 影响面 + 风险的指纹。

人话部分放在命令行上是有意的：**Claude Code 的确认弹窗只显示命令行**，
SQL 在文件里它看不见。把关键信息塞进确认串，弹窗里才看得出要动什么。

指纹保证任何一样变了旧串立刻失效，不能拿上次的确认串来批准这次的操作。

## 十五、硬拦截为什么必须在脚本里

查证过 Claude Code 的权限机制：`ask` 规则是真正的强制询问，优先级压过 `allow`，
复合命令也会被拆开逐条检查——但 **`ask` 在 `bypassPermissions` 这类模式下会失效，
只有 `deny` 在所有模式下都生效**。而且 skill 无法随包安装权限规则或 hook，
必须由使用者自己改 `settings.json`。

所以红线（删库、禁止名单、只读连接、超过硬上限）一律由脚本自己拒绝，退出码 3。
弹窗是额外一层，不是唯一一层。

## 十六、快照与反向 SQL

### 为什么存 JSON 不存 CSV

ADT 用 CSV 存快照，有两个后果：**分不清 NULL 和空串**、**丢了列类型**。
这是它的 undo 不可靠的根源。

这一版存 JSON：NULL 就是 `null`，空串就是 `""`，每列带 `jdbc_type`。
值一律以字符串形式输出，`BigDecimal` 不会被 JSON 的浮点数吃掉精度。

### 快照完整性必须写进快照文件

`snapshot_complete` 这个标记要写进**快照文件本身**，不能只放在返回值里——
生成反向 SQL 时只读得到文件。默认当成「取全了」，就会生成一份
「只还原一部分」的反向 SQL，那比没有反向 SQL 更危险。

### 为什么不自动回滚

ADT 的自动 undo 有一批毛病：失败的 undo 被记成已撤、无主键 UPDATE 匹配 0 行仍报成功、
ALTER 的 undo 是空操作却标为可撤。做成「看起来撤回了其实没撤」比不做更糟。

这一版不自动撤：执行完只生成 `undo.sql`，要还原由人发起 `exec --undo <留痕目录>`，和别的写操作一样走两步确认。
人会看到「这期间可能有别人改过」「快照没取全」这些提醒。
整份反向 SQL 走执行器的 `batch`：一个事务里逐条执行，每条都得正好动一行（`--expect-each 1`），有一条不是就整体回滚；
同一次只能还原一遍（留痕里记下已还原），还原本身不再取快照。
0930 审查之前 `exec` 只收一条语句，`undo.sql` 是好几条，说明里写的"当成普通写操作"其实走不通。

### 时间字面量的方言差异

达梦和 Oracle 直接拿字符串比日期会依赖会话的 NLS 设置，所以套 `TO_DATE` / `TO_TIMESTAMP`；
MySQL、神通、金仓用普通字符串字面量就行。这是 `journal._temporal_literal()` 里唯一的方言分支。

## 十六之二、驱动：随包带过，现在不带了

最早是"不带驱动，用被操作项目自己的"。0.6.0 改成五种驱动随包带，理由是换一台电脑就要重新准备、
国产数据库的驱动不在 Maven 中央仓库。代价是包涨到 10 MB，而且
**达梦、神通、金仓的驱动仅限内部使用，不得公开二次分发**，带着它的包不能对外发。

1.0.0 并进 vibe-kit 时改成不带：套件的安装包要发给所有同事、要进 GitLab，不能夹着厂商的 jar。

现在的做法：

- 驱动登记在 `~/.claude/vibe-kit/drivers.json`，文件放在 `~/.claude/vibe-kit/drivers/`，每种数据库一个
- 在配置页「数据库驱动」里管：**自动搜索**（到 Maven 仓库里找，按"本机环境"里配的 Maven、`~/.m2` 的顺序），或者点那种数据库那一行后面的**换驱动**自己选一个 jar
- 认驱动不看文件名，打开 jar 看里面有没有那种数据库的驱动类（`kit/lib/drivers.js` 的 `inspect`）
- 后台自动探索发现项目用到的数据库还没有驱动，会自己到 Maven 仓库里找一遍、找到就登记
- 从旧技能升上来：安装器删旧技能之前把它自带的驱动挪进来登记（`rescueFrom`）
- 卸载套件不删驱动

查找顺序：连接配置里的 `driver_jar` → 项目自己的 `lib/`、`WEB-INF/lib/` → 登记表 →
`~/.db-crud/drivers`（以前手放的）、套件的驱动目录、本机的 Maven 仓库（这一步要翻目录，探到一次记进探测缓存）。
"项目自己的"排在登记的前面：它的版本和项目实际连的库对得上。

打包脚本（`dev/pack.js`）会查：包里有 jar 就不让打。

## 十六之二点五、配置为什么能自动扫出来

**被操作的项目自己就存着连接信息。** Spring Boot 的 `application.yml`、
老项目的 `jdbc.properties`、Druid 的 XML 里，JDBC 串、账号、口令多半都是现成的
（口令那边本来就是明文）。既然是要操作这个项目的库，没道理让人再手打一遍。

`db.py init` 扫这些文件，把结果写成配置再逐个试连。做法是先在文件里找出所有
`jdbc:xxx:` 串，再在它附近十几行里找 user / password 这类键 ——
配置文件都很小、结构规整，靠邻近就够准，不用给每种框架写一个解析器。

**两处不能省的处理：**

1. **先剥注释再扫。** 老项目的配置里常年躺着一堆注释掉的旧地址，
   实测一个 `proxool.xml` 里 11 条 JDBC 串只有 1 条是生效的，其余都在 `<!-- -->` 里。
   照单全收会生成一堆假连接，而那些地址很可能是别的环境甚至生产库 —— 连过去就是事故。
   这和 SQL 分类器必须先剥注释是同一个道理。
2. **只配开发环境的。** 0930 审查之前，像生产库的配进来、标成只读，测试库原样配成可写。
   可 `init` 是模型自己会跑的命令（技能说明让它在"找不到连接配置"时跑），这等于把测试库、生产库交到了它手上。
   现在 `init` 和后台探索一样，测试、生产环境的一律不配，要用的人自己照 `references/连接配置.md` 手写。

扫不出来的两类会明确跳过并说明原因：连接串里有没展开的 `${...}` 占位符（填了也连不上）、
不支持的数据库类型（比如 SQL Server）。

**并进 vibe-kit 之后，平时扫配置的是套件的后台自动探索**（`kit/lib/discover.js`，同一套办法的 Node 版）：
会话开始、用户开口时发现项目没探索过、或者依据的配置文件改了，就在后台扫一遍，把结果并进 `.vibe/db-crud.ini`。
它和 `db.py init` 一样**只配开发环境的连接**。测试、生产环境的（看文件名、目录、YAML 的分段、数据源的名字、pom 的 profile）
不配进来，项目说明里写一句"测试、生产环境的连接没有配进来"，并说明模型不要自己去配。
`db.py init` 装了套件时直接调套件的探索，套件的探索跑不成才用技能自带的扫描（`discover.py`，同样只配开发环境的）。
`${NAME:默认值}` 这种占位符按默认值展开；`ENC(...)` 这种加密过的口令认得出来，不当成明文写进去。
人手写的连接、记过的坑它不动；来源文件里找不到了的连接不删，加一行说明。
`db.py init` 和 `discover` 还在，给不装套件、或者想手动扫一遍的时候用。

## 十六之三、.vibe：配置和探测缓存

配置默认放在被操作项目的 `.vibe/db-crud.ini`，一个项目可以配多个库
（主库、历史库、报表库），跟着项目走才对得上。
以前的名字 `.vibe/urai-db-crud.ini` 照样认；两个都在，用最近改过的那一份。

同目录下还有 `db-crud.env.json`，缓存探测结果：java 在哪、每种方言的驱动 jar 在哪。
找 java 和在 Maven 仓库里翻 jar 都不便宜，探一次写下来，后面直接读；
缓存里的路径不存在了（换机器、删 jar、重装 JDK）就自动重新探。
表结构的缓存 `db-crud.cache.json` 也在这里，见二十四节。

**这个目录不能进版本库**，里面有账号口令。`doctor` 用 `git check-ignore`
实地查一下到底有没有被忽略，没有就提醒。vibe-kit 的后台自动探索往 `.vibe` 里写连接配置之后，
会把 `.vibe/` 加进那个项目的 `.gitignore`。

## 十六之四、.vibe 落在哪：认项目，不认当前目录

`init` 不把 `.vibe` 写在当前目录，而是写进**真正拥有这份数据库配置的项目**。

起因是实际用的时候踩了：项目外面套了一层壳子（把前端后端装在一起的目录），
在壳子根上跑了一次 `init`，配置落在壳子上；后来在后端目录里又跑一次，
又落了一份。两份配置，用哪份取决于当时在哪个目录，这是个陷阱。

**怎么认项目根**：从配置文件往上走，收集带 `pom.xml` / `build.gradle` /
`build.xml` 的目录，取**最靠外的那个**。

- 有壳子：壳子没有构建文件，往上走到它就停了，结果是里面的后端 ✓
- 没壳子：当前目录自己就是项目根，结果不变 ✓
- 多模块：聚合根也有 pom，落在聚合根而不是 `xxx-admin` 子模块 ✓

**刻意不认 `.git`。** 壳子常常本身就是个 git 仓库，按 `.git` 找会落回壳子上。
只认构建文件，才能分清「一个代码仓库」和「一个 Java 项目」。

**查找时上下都找**：当前目录 → 往上最多 5 层（子模块里开 Claude Code）→
往下最多 3 层（壳子根上开 Claude Code）。往下找到多份会明确报错让人指定，
不猜 —— 猜错就是连到另一个库上。

探测缓存跟着配置走，不跟着当前目录走，免得一份配置配出一堆散落的缓存。

## 十六之五、为什么不再劝人别用明文口令

早先每次解析到明文口令都会警告一句「建议改成 ${ENV:变量名}」。撤掉了。

理由：这个工具面向**内网开发库**，连接信息本来就躺在项目的 `application.yml` 里，
`init` 扫出来的口令也是从那儿原样抄的 —— 提醒的那个"风险"在工具介入之前就存在。
而这句话会出现在**每一条命令**的输出里，结果是人对所有提示都脱敏，
连真正要紧的（快照没取全、影响面比预期多）也一起忽略掉。

**提示要留给真正需要停下来看的事。** `${ENV:}` / `${FILE:}` 仍然支持，
只是不再推销。

## 十六之六、为什么要自己试标识符大小写

达梦、Oracle、金仓的 Oracle 兼容模式把不带引号的标识符折成**大写**，
神通和金仓的 PG 模式折成**小写**。人按代码里的写法敲 `t_order`，
库里存的是 `T_ORDER`，`getColumns` 返回空 —— **而且不报错**。

「查不到」和「表不存在」在输出上长得一样，这是最坑的地方：
人会以为表名写错了，去翻代码、去问同事，而实际上只差一个大小写。

所以 `columns` / `peek` / 取主键这三处自己试：原样 → 全大写 → 全小写。
取主键那处尤其要紧 —— 认不出主键，UPDATE 的反向 SQL 会**退化成拿整行当条件**，
这是悄悄降级，不会有任何报错。

试出来和输入不一样时，顺手记一条坑进配置（见下一节），下次不用再试。

## 十六之七、踩过的坑为什么记在配置文件里

坑几乎都是**跟着某个连接**走的：这个库的表名要大写、那个库是 Oracle 兼容模式
空串会变 NULL、某张表没有主键。写在连接旁边，谁用这个连接谁就看得见 ——
比记在另一份文档里、指望人主动去翻要实在。

**改文件用文本方式，不走 configparser 回写。** 回写会把注释全吃掉，
而自动生成的配置里「来自 application.yml:6」这种出处注释是有用的。
自测（`notes_selftest.py`）专门盯着这件事：记完之后注释、其它连接段、
原有字段都得原样还在。

**同一条不重复记。** 这个功能是「别再踩第二次」，不是攒一堆重复提醒 ——
记成流水账，人就会连真正要紧的提示一起跳过。

## 十七、留痕为什么放在用户目录

`~/.db-crud/journal/`，**刻意不放进被操作的项目里**。
快照里装的是真实业务数据，放进项目目录早晚会被 git 提交上去。

留痕和连接配置分在两处是有意的：配置跟着项目走（`.vibe/`），
留痕跟着人走（`~/.db-crud/journal/`）。快照可能很大、积得很快，
堆在项目目录里碍事，而且一旦被提交就是业务数据泄漏。

# 第三部分：并进 vibe-kit 时加的（1.0.0）

## 二十一、一条命令只起一次 java

用起来慢，量下来慢在起进程：起一次 java、连一次库要一两秒，而以前看一张表的结构要起 2 到 4 次
（试大小写各一次、取列一次、取主键一次），写操作的第二步要起 3 到 5 次（数行数、取快照、执行、取主键）。

办法是把"一件事"整个交给执行器，在一次连接里做完。执行器加了几种模式：

| 模式 | 干什么 | 哪条命令用 |
|---|---|---|
| `describe` | 几张表的列和主键；大小写原样、全大写、全小写自己试 | `columns --table A,B,C` |
| `peek` | 看一张表：`eq:字段` 按列的类型绑定参数、`cols`、`where`、`order`、只数行数 | `peek` |
| `multi` | 几条查询一起跑 | `query --sql … --sql …` |
| `find` | 在表名、列名、注释里找关键字 | `find` |
| `apply` | 核对行数、取快照、执行、核对实际影响的行数、提交、取主键 | `exec --ack` |
| `batch` | 一个事务里跑好几条写语句，每条的影响行数都要对 | `exec --undo … --ack` |

几段输入走标准输入，用 `--@@DBCRUD-SEP@@ <标签>` 隔开，最后一行是结束标记，没收到结束标记（输入被截断）就不执行。
原来的 `ping`、`meta`、`query`、`count` 还在；单独的 `write` 没人用了，0930 审查时去掉，写操作都走 `apply`、`batch`。

java 的启动参数加了 `-XX:TieredStopAtLevel=1 -XX:+UseSerialGC -Xshare:auto -XX:-UsePerfData`：
这种跑一两秒就退的进程不值得做完整的即时编译。JVM 不认这些参数（很老的、非 HotSpot 的）就去掉再起一次。

**少写 SQL 是同一件事的另一半**：模型每写一条 SQL 就是一次工具调用，写错了再来一次。
`peek --eq 字段=值` 让它不用拼 WHERE、不用管引号和中文；`find` 让它不用先列出所有表再一张张看。

## 二十二、query 只许跑查询

以前 `query` 不看语句是什么，直接交给执行器的查询接口。两个洞：

1. 有的驱动（Oracle、达梦）用查询的接口也能执行写语句
2. 改结构的语句会自己提交

等于绕过了"凡是改库的都要确认"。现在两头都堵：

- Python 这头 `sqlguard.readonly_problem()`：增删改、改结构、`SELECT … INTO`、`EXPLAIN ANALYZE` 都拦下，退出码 3，让它走 `exec`
- 执行器那头：只读的模式（`query`、`multi`、`peek`、`describe`、`find`、`count`）最后**一律回滚，不提交**

## 二十三、行数在事务里核对

以前第二步是"先数一遍、和确认串里的行数对一下、再执行"，数和执行是两次连接，中间有空档：
别人在这当口插了几行，执行的就不是确认过的那个影响面。

现在 `apply` 在**同一个事务里**：数行数（带 `--expect-count`）→ 不一样就回滚、报"没有执行：行数变了" →
一样才取快照、执行、提交。确认串 `类型-表-N行-指纹` 里的 N 由 `sqlguard.rows_in_token()` 取出来。

## 二十四、表结构存在本地

`columns` 看过的表结构存进 `.vibe/db-crud.cache.json`，12 小时内再看同一张表不连库。

- 输出里写明"来自本地缓存"。模型照缓存写的 SQL 报"列不存在"时知道该怀疑什么
- `--fresh` 重新到库里查
- 通过这个工具改了结构（DDL），缓存自动作废。别人改的结构它不知道，所以有 12 小时的期限

只缓存结构，不缓存数据。

## 二十五、后台执行器（开关，默认关）

一条命令起一次 java 已经是下限了，再快只能不起。后台执行器就是一个不退的执行器：
第一条命令把它起起来，后面的命令连它，连接留着。

- 只听 `127.0.0.1`，端口随机；每个请求要带口令牌，口令牌在状态文件里（`~/.db-crud/daemon/`）
- 几分钟不用自己退（默认 5 分钟，配置页上能改）
- 写操作照样两步确认，判断还是在 Python 这头

**默认关着**，理由：多一个常驻进程就多一种出毛病的方式（进程没退干净、连接被库那边掐断、换了口令还连着旧的），
而一条命令一两秒多数时候能接受。嫌慢的人自己到配置页打开（开关 `dbcrudDaemon`）。
环境变量 `DBCRUD_DAEMON=0 / 1` 压过开关，测试用。

## 二十六、用量和毛病怎么进套件

每条命令结束时往 `~/.claude/vibe-kit/state/tool-usage.jsonl` 记一行：哪条命令、多少毫秒、起了几次 java、
用没用缓存、退出码、出错的类别、方言。**不记 SQL、数据、表名、连接串、口令**。

套件的钩子（用户开口、收工）把这些并进统计（`kit/lib/toolstats.js`），配置页「数据库驱动」页的"用得怎么样"、
导出的问题反馈里的"工具用量""能优化的地方"两节用的就是它。

三种毛病自动记成套件的问题反馈（来源写"工具自动记录"）：脚本自己崩了、执行器没有输出、找不到驱动。
这样内网用出来的问题不靠人记得去报。

## 二十七、全自动模式

vibe-kit 的全自动模式开着时用户不在，没人确认。

1.0.0 的做法是一律不执行：`exec --ack` 直接拒绝（退出码 3）。用起来的问题是整条链卡在改库上，用户回来还得把每一条再跑一遍。
用户 2026-09-30 定了新规矩（1.1.0）：**不拦，条件是留得下备份**。改、删要有备份脚本；新增的要记下表和主键，方便他删。

还是两步，第二步不用等人。做不做由 `db.py` 的 `auto_plan()` 定，不靠模型自觉：

| 语句 | 要满足什么 | 留下什么 |
|---|---|---|
| UPDATE、DELETE | 风险是 SAFE 或 WARN；影响几行数得出来、不超过快照上限；UPDATE 的表有主键；表里没有二进制列 | `before.json`、`undo.sql`（和有人在的时候一样） |
| INSERT | 表有主键；不是撞键就改的插入；不是 `INSERT … SELECT` | `op.json` 的 `inserted`：表、主键列、每一行的主键值。`undo.sql` 是按主键一行一行删 |
| CREATE TABLE / INDEX / VIEW / SEQUENCE；ALTER TABLE … ADD 列、ADD CONSTRAINT 名字 | 不是 `CREATE OR REPLACE`；一条语句不夹着删、改、改名 | `op.json` 的 `created`；`undo.sql` 是对应的 DROP |
| 别的 | | 不执行，退出码 3，任务标"（留给用户：要改库）" |

几处细节：

- **主键、二进制列以库里现在的为准**：`_table_meta()` 不读本地缓存，当场跑一次 `describe`。
- **新增行的主键从哪来**：语句里写明了的（`insert_literal_ids()`，每一行的主键列都是字面量才算）直接记。没写的（自增、序列）让驱动带回来：
  执行器的 `apply` 模式收到 `--key-columns`，用 `prepareStatement(sql, 列名)` 执行、读 `getGeneratedKeys()`；
  带着 `--require-ids true` 时，驱动不支持、带回来的行数和插入的行数对不上，就回滚，报 `IDS_UNKNOWN`，这一条不执行。
- **DDL 的还原不自动执行**：`exec --undo` 碰到建表这一类只告诉用户还原脚本在哪。DROP 是不可逆的，要人看过再跑。
- **新增的还原**：`exec --undo` 认 INSERT 的留痕，执行的是按主键的 DELETE，照样两步确认。
- 留痕的 `op.json` 多了 `auto`（是不是全自动做的）、`project`（在哪个项目里做的）。套件的全自动报告靠这两个字段列"库里改过的"（`kit/lib/report.js` 的 `dbWrites()`）。

**怎么知道这条命令是不是全自动下跑的**（`auto_mode()`）：

1. 配置页的开关开着，而且封条对得上（手改 `config.json` 打开的不算）。
2. 全自动模式只在走 OpenSpec 流程的会话里算数，这件事工具自己看不到。套件的钩子在命令跑之前留一张条子
   （`state/tool-flow.json`，按当前目录记，两分钟内有效；`guard-commit.js` 的 `noteToolFlow()`）：这个会话在不在流程里。
3. 没有条子（在终端里手敲、套在脚本里跑，钩子没经过）：按用户不在算。宁可多留一份备份、多拒绝一条，不能没人看着把库改了。
