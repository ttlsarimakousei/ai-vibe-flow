## 2026-09-21　第三轮：人大金仓；驱动改为随包自带

**环境**：KingbaseES V8R6（本机 54321），驱动 kingbase8-8.6.0.jar。

**先验"驱动随包自带"**：把 `~/.db-crud/drivers/` 整个挪开，只留 skill 自带的
`drivers/`，四个库（达梦、神通、MySQL、金仓）全部连上，`conn test` 打出的
来源都是"skill 自带"。

同时验了 `.vibe`：一个项目的 `.vibe/urai-db-crud.ini` 里配四个连接，`doctor`
一次把四种驱动全找到并缓存进 `.vibe/urai-db-crud.env.json`，`git check-ignore`
也确认 `.vibe` 被项目忽略了。

**金仓的完整读写循环**：建表 → 插入 → 查询 → 看列和主键 → UPDATE →
反向 SQL 还原 → DELETE 两行 → 逐条插回 → 删表，全过。

### 撞出一个跨库的真 bug：元数据列名大小写

建表时明明写了 `PRIMARY KEY`，`columns` 却报"（没有主键）"。

查原始输出发现：**JDBC 规范说元数据的列标签是大写（`COLUMN_NAME`），达梦、
Oracle、MySQL、神通都照办，但金仓（PG 系）返回的是小写（`column_name`）**。
代码按大写精确匹配，于是在金仓上永远认不出主键。

后果不只是显示问题：UPDATE 的反向 SQL 靠主键定位行，认不出主键就会
**退化成拿整行的值当条件** —— 表里有重复行时一条反向语句会改掉多行。

修法：取列一律走 `_col_index()` 做大小写不敏感匹配。修完金仓认出了主键，
达梦那边回归正常。

### 另一件事：空串在金仓上本来就是 NULL

删掉一行空串的记录再用反向 SQL 插回来，`memo` 变成了 NULL。
一开始怀疑是往返丢了信息，查下来不是 —— 这个实例跑在 **Oracle 兼容模式**：

```
database_mode              oracle
ora_input_emptystr_isnull  on
```

这个模式下 `''` 写进去就是 NULL，工具从头到尾没见过那个空串。快照记的是 NULL，
还原回去也是 NULL，往返是忠实的。

**这是金仓特有的坑**：同一份 SQL 在 PG 模式和 Oracle 模式下行为不一样，
系统表也不同（这个实例用的是 `sys_settings` 而不是 `pg_settings`）。
在金仓上判断数据有没有还原成功，不能拿别的库的直觉去套。

**结果**：全过。要点几条：

- MySQL 把库名放在 catalog 上而不是 schema 上，`meta_scope_args()` 里的分支正确，

- `DECIMAL(10,2)` 的 `100.50` 原样回来，没有被当成浮点数丢精度

**这一轮新发现并修掉的两个问题**

1. **`--config` 指向不存在的文件时会悄悄回退**。原来的查找顺序是「显式路径 →

   这意味着**连上了另一个库，而使用者以为连的是自己指定的那个**。改成当场报错。
   这个问题是写冒烟用例时撞出来的 —— 用例本想验证「找不到配置」，却意外成功了。

2. **文档让用户把驱动放 `~/.db-crud/drivers/`，但自动查找没搜这个目录**。
   文档和代码对不上。补上了。

**顺带加的**：`db.py doctor` 自检命令。拷到新机器上先跑它，逐项报
Python、java、执行器、连接配置、留痕目录、每个连接的驱动 jar 在不在，
比一条条命令去撞报错快得多。

### Oracle 这轮没跑成

本机那台是 Oracle 11.2.0.1（1521）。走不通的原因查清楚了但没解决：

- `sqlnet.ora` 里 `SQLNET.AUTHENTICATION_SERVICES=(NTS)` 是开着的 ✓
- 但 `ORA_DBA` 本地组里只有 `NT AUTHORITY\SYSTEM`，**没有当前 Windows 用户**，
  所以 `sqlplus / as sysdba` 报 ORA-01031，拿不到任何账号的口令

要通的话得以管理员身份 `net localgroup ORA_DBA <用户名> /add`，再注销重登。

**驱动这一项已经备好了**：用的是 Oracle 安装目录自带的 `ojdbc6.jar`

21c 以上的驱动不再支持连 11.2 的库。ADT 当年的 B001 就是栽在驱动与库版本不匹配上。

**另外一个和数据库无关但会卡住人的坑**：这台机器的环境里有 `HTTP_PROXY`，
Oracle 11.2 的 sqlplus 一启动就报 `Error 46 ... HTTP proxy setting has incorrect value`。
调 sqlplus 前要把代理变量清掉；Git Bash 下还要 `MSYS_NO_PATHCONV=1`，
否则 `/ as sysdba` 里的斜杠会被当成路径转换掉。

### 五、过程中发现并修掉的两个问题

**1. 快照截断不会被发现**（严重）

`snapshot_complete` 这个标记只写进了返回值，没写进快照文件本身。
生成反向 SQL 时只读得到文件，于是默认当成「快照取全了」——
**快照被截断时不会警告，反向 SQL 会悄悄只覆盖一部分行**。
这正是「看起来撤回了其实没撤」那一类。

修法：Java 侧把 `snapshot_complete` 和 `snapshot_max_rows` 写进快照文件；
Python 侧同时检查 `snapshot_complete` 和 `truncated_rows`，任一为真就明说。

复现验证：故意把上限压到 1 行去删 2 行，提示变成
「★ 快照没有取全（1 行封顶），下面的反向 SQL 只覆盖取到的那部分，照它执行不会把数据完全还原」，
同样的话也写进了 `undo.sql` 的注释里。

**2. 「先看看」的那次调用会把数据改了**（设计问题）

原来按风险等级放行：SAFE 的写操作直接执行。而 INSERT 行数数得出来就判 SAFE，
于是「先跑一次看影响面」的那一次调用本身就完成了插入。

修法：规则改成**任何会改数据库的语句都要确认**，不按等级区分。要预览用 `--dry-run`。
简单的规则才不会被误解。

### 六、离线用例

`scripts/sqlguard_selftest.py`，45 项，全过，不连数据库。

其中 14 项移植自 ADT 的 `RiskClassifierTest`，用来保证规则搬过来没走样。
其余是它没覆盖但真实 SQL 里会遇到的：

- 注释里的 WHERE（`--`、`#`、`/* */`）不能当成真的 WHERE
- 字符串字面量里的 WHERE 和分号不算数
- MySQL 可执行注释 `/*! */` 判 DANGEROUS（里面的内容会被真的执行）
- 子查询里的 WHERE 不能当成外层的，嵌两层也不行
- 列名叫 `where_col` 不误判
- `INSERT ... SELECT` 估不出行数，要确认
- 达梦的双引号标识符、神通的 `RETURNING`、Oracle 系的 `FROM DUAL`

### 结论

方案成立，达梦和神通可用。

**还没验的**：MySQL、Oracle、人大金仓。JDBC 这条路对它们代价一样，
主要待验的是方言差异——Oracle 的 `ROWNUM` 分页和 GBK 字符集、
MySQL 用 catalog 放库名、金仓的国密认证。

**测不了的**：连库路径进不了 `tools/smoke.py`（它起不了数据库），
只有 `sqlguard_selftest.py` 那 45 项能进自动冒烟。连库部分靠这份文档做人工验证记录。
