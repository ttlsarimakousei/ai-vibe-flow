### R1　临时目录里的日志重定向让正常的验证命令不记证据（确认）

- 位置：`vibe-kit/kit/lib/evidence.js:95`（调用）、`:104-117`（`onlyTemp`）。
- 问题：`onlyTemp` 的判断是"命令里写全了的路径都在系统临时目录里就不记"。命令里只要出现一个临时目录的路径，哪怕它只是输出重定向、日志文件，真正的验证命令（`npm test`、`mvn test`）也被判成"没点名项目文件"而丢掉。
- 实测（`onlyTemp(cmd, 'C:/WorkSpace/proj')`，全部返回 `true`，即不记证据）：
  - `npm test > C:/Users/…/Temp/out.log 2>&1`
  - `npm test 2>&1 | tee /tmp/out.log`
  - `mvn test > /tmp/mvn.log`
  - `pytest tests --junitxml=/tmp/r.xml`
  - `node <temp>/x.js && npm test`（前半段是临时脚本，后半段是项目的测试）
- 触发场景：模型把测试输出落到 `/tmp` 或 `%TEMP%` 再看，这是很常见的写法。测试明明跑过且通过，`after-tool` 不记证据，`verify-gate` 会当成"没验证"反复催。#484 要挡的是"整条命令都在拿临时目录里的试验文件做事"，现在把"只是往临时目录写日志"也挡了。
- 建议：只在命令的"主体"都在临时目录里时才不记。做法之一：先把重定向目标（`>`、`>>`、`2>`、`| tee <文件>`）和 `--xxx=<临时路径>` 这类输出参数的路径从 `found` 里剔掉，剔完 `found` 为空就按"没点名"照旧记；只有剩下的路径（输入文件、被编译的文件）全在临时目录里才不记。再加一条用例：`npm test > /tmp/x.log` 要记。

### R2　到点替用户开工：只要选项里有"开始实施"就触发，没核对这是需求审过的那一问（可能）

- 位置：`vibe-kit/kit/hooks/ask-timeout.js:115`（触发条件）、`:153-173`（`startApply`），`vibe-kit/kit/lib/apply-scope.js:36-50`（`grant` 的定目标链）。
- 问题：条件只有 `st.on && st.stage !== 'apply'` 加"任何一个问题里有选项被 `autoAnswerOf` 认成 on"。没有核对：需求是否整套审过（`flow-policy.allDone(dir,'proposal')`）、问题里是否点名了一个现有变更。`grant` 在问题里没点名变更时会退到 `all.length === 1`（目录里唯一的变更）或 `touched.length === 1`，所以：
  - 目录里有一个没归档的旧变更 X，用户在流程里探索另一件新事（stage 还是 plan，变更还没建）。模型的某个提问框里有选项叫"开始实施……"，10 分钟没人答，钩子替用户把旧变更 X 开了工、开了自动。
  - 需求还没审过，模型提前问了"开始实施 / 先不实施"（规范不让，但模型会犯），到点同样开工。用户本人选"开始实施"时 `pre-edit` 之前有审查拦着没有，我没逐条查；但"没人答 = 同意"比"用户选了"的把握低得多，值得多挡一道。
  - 一个提问框里有多个问题时（例如另一问是"用哪个数据库"），钩子只管开工，另一问没人定，返回给模型的话也没提它。
- 建议：`startApply` 之前加三个条件：(1) 问题文本里点名了某个现有变更（`S.mentionsChange(question, name)` 至少一个，不靠 `all.length===1` 兜底）；(2) 那个变更的需求整套审过（`allDone(dir,'proposal')`）；(3) 整个提问框只有这一问，或者对其余问题仍按普通的"自己定"交代。条件不满足的走原来的"自己定"分支，不开工。
- 关联：`ANSWER_ON` 的 `开始实施` 分支（`vibe-kit/kit/lib/session-config.js:83`）认得太宽：`开始实施，但先不要改 B`、`开始实施，别动数据库`、`开始实施前先补充需求`、`开始实施 方案二`（有空格）、`开始实施下一个 change` 都判成 on（我逐个跑了）。原因是否定词的前瞻 `[^，,。；;]*` 过不了逗号，方案词的前瞻又把空格排除了。用户选了这类选项时 `syncAutoAnswer` 会开自动，到点时 R2 的路径会开工。建议 `开始实施` 分支改成"整个选项文字等于它、或只带括号里的（推荐）、说明"才认，其余不认。

### R4　`farInfo` 对每个"这边还没建的 change"都去扫上一级、上两级目录，每个钩子、每次状态栏刷新都付一次（可能）

- 位置：`vibe-kit/kit/lib/big-task.js:44`（`build`）、`:51-61`（`farInfo`），调用 `vibe-kit/kit/lib/session-projects.js:228-244`（`nearChanges`）。
- 问题：大任务的表里"后面要写的 change"是常态：目录还不存在、也没归档，每一行都走 `farInfo`。`nearChanges` 每次读上一级的所有子目录，再读上两级的所有子目录的子目录（预算上限 200 个），每个候选做两次 `existsSync`。`invocation.memo` 只在同一个钩子进程内缓存，每个钩子是新进程，状态栏不在钩子里（`store` 为空，`memo` 直接执行）。
- 实测：本机上一级只有 14 个子目录，10 行耗时约 390 ms（约 40 ms 一行）。内网那台装了文档加密、一条 git 要 3 秒，磁盘调用也会慢；壳子上一级目录项多的话，一行最多 400 次 `existsSync`，8 行表就是几千次，叠在每个 `task-anchor`、`pre-edit`、`verify-gate` 上。这批本来要修的正是钩子超时（#483、#484、#486）。
- 建议：(1) 把"表里行 → 兄弟壳子里的位置"（含"没找到"）写进状态文件，带 5 分钟左右的有效期，各进程共用；(2) 或者只在 `apply-scope.grant`、`review.js --change`、`/vk-resume` 这几个真要用到它的入口里找，`build` 默认不找；(3) 至少把同一次 `build` 里各行的 `subdirs()` 结果合起来读一遍，不要每行重读。

### R5　Bash 改需求文档的拦截有几个常见的绕过（确认，属于"尽力而为"的范围，建议至少把说法写实）

### R6　`#488` 判"壳子不是 git 仓库"靠 `W.git(...)` 返回空串，出错也是空串（可能）

- 位置：`vibe-kit/kit/lib/review-runner.js:140`。
- 问题：`W.git` 在任何错误下（git 不在 PATH、"dubious ownership"、读超时、预算外之外的异常）都返回 `''`（`workspace.js:66`）。壳子根其实是 git 仓库，但这一次 git 调用失败，也被判成"壳子不是 git 仓库"，壳子根悄悄从要基线的仓库里去掉，只在 `excluded` 里写了一句不实的说明。壳子根本身的改动（比如壳子里的文档、脚本）这一轮就没人审，而且不报 partial。
- 建议：改用文件系统判断（`fs.existsSync(path.join(root, '.git'))`，`flow-policy.inGit` 已有现成的向上找法），或者用 `W.checkedGit`（出错抛出来），出错时保持原来的行为（进 `skipped`）。

### R8　`ask-timeout` 到点开工的副作用发生在"用户已经答了"也可能发生的窗口里（可能，概率低）

- 位置：`vibe-kit/kit/hooks/ask-timeout.js:83-92`（`startApply`）、`:174-196`（`handle`）。
- 说明：`ask-timeout.js` 头注释自己写着"用户先答了，钩子的进程不会被结束，后到的决定不起作用"。以前到点只是打印一个被忽略的决定，现在 `startApply` 会写状态（`grant`、`setFlow`、`setSessionAuto`、基线）。`settled()` 靠会话记录判断用户答没答；记录读不到、`tool_use` 在最后 80 万字节之外、或者记录里 `tool_use` 的输入和钩子收到的不一致（别的钩子改写过）时，会走到"没找到"分支，一直等到点，然后开工，即使用户其实早就选了"先不实施"。
