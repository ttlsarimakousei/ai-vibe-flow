## 一、先看结论

### 1. 为什么"动不动拦、确认再确认"：五个根因

**R1 提交、推送、归档只认"最后一次开口"，而提问框的回答也算一次开口**｜已复核

- 证据：
  - `kit/lib/session.js:303` 的注释写明归档、提交、推送"只看最后一句"；`:318-319` 的代码也是这么判的。
  - 拿许可的 `kit/lib/permissions.js:43` 调的就是它。
  - 对照：审查、自测会往回看本轮（`:311-316`），提交这几项不会。
- 后果：用户先说"改完提交并推送"，人工模式下套件接着要求先问一句"要不要审查、自测"。用户一回答，原来那句许可就作废了，提交被拦一次、推送再拦一次。

**R2 同一件事过好几道门**｜push 部分已复核，其余子代理复核

- push 两道：
  - 钩子自己的许可检查。
  - Claude Code 的 ask 规则 `Bash(git push:*)`（`settings.fragment.json:4`）。`docs/claude-code-facts.md:121` 记着，ask 规则不管钩子返回什么都照查。
- 提案材料三道：`guard-spec` 拦一次，提交时 `guard-commit` 再拦一次，收工时 `verify-gate` 再拦一次。
- 开工三道：`guard-ask`、`pre-edit`、`guard-commit` 共用 `<会话>-flow.json`，这份状态错一处，三处一起拦。

**R3 三层文字各说各的，模型照着一层做，被另一层拦下**｜已复核

- 写需求文档：
  - OpenSpec 自带的 `/opsx:propose` 写的是"一步生成全部文档"（`kit/openspec/node_modules/@fission-ai/openspec/dist/core/templates/workflows/propose.js:19`）。
  - 套件的规范写的是"一份一份写，用 /opsx:propose 也一样"（`claude/rules/10-openspec.md:20`）。
- 推送：
  - 规范写"直接 `git push`"（`claude/rules/20-git-commit.md:19`），照着写会弹 Claude Code 的确认框。
  - 钩子的提示写"直接 `git -C <仓库> push`……不再问确认"（`kit/hooks/task-anchor.js:465`）。这种写法匹配不上 `git push` 开头的 ask 规则，所以不弹。这是在钻匹配规则的空子。
- 手册和 `vibe-kit/开发流程.md` 有几处还停在旧版，见第三节。

**R4 能确定判断的规矩，只在拦下时才告诉模型**｜子代理复核

串 cd、起服务要走 devserver、新文件要 add、审查要带 `--point`、需求文档一份一份写，这些都是拦下以后才提示的。模型总是先被拦一次，改了再来。O-流程估算：人工模式做一个新功能，约有 8 次本来可以第一次就做对。

**R5 认中文说法的规则散在五六处，有认错的，也有认漏的**｜已复核（实测）

- 问句"push 到哪个分支"被当成推送许可。
- "改完提交""先提交""推吧""可以推送了""可以归档了"都认不出来（`kit/lib/intent.js`）。
- 新需求被认成"报问题"（`session.js:163`），建提案时 `kit/hooks/guard-spec.js:55` 会拦一次。实测"新增异常订单导出""用户反馈列表加个导出""新增一个用户说明页""做一个登录失效自动跳转"都中了。
- `session.js:125-127` 定义了"动手""继续做""接着做""开始吧"这些开工说法，但没有任何地方调用。

O-流程按代码估算了一条典型路线：人工模式做一个有两组任务的新功能，用户要停约 19 次，其中约 6 次是同一件事问第二遍；模型被拦、被催 12—16 次，其中约 8 次本可以第一次做对。

### 3. devserver 为什么慢（详见第五节）

1. **认"改过"太宽，白白整轮重建、重启**｜已复核
   - `kit/tools/devserver.js:377` 只按几个目录名排除；`:399-402` 只要 git 看得到的文件修改时间晚于服务启动，就算改过；`:404-405` 启动之后有新提交也算改过。
   - 所以打一次勾、改一个 md，或者只是提交了一下，下次测试都会全量重来。
2. **每次查进程都起一个 PowerShell**｜已复核写法，次数是估算
   - `devserver.js:220-238` 每查一次就起 PowerShell 跑 Get-CimInstance。
   - 重启一次约查 5 次，合计 8—20 秒。
3. **启动命令每次去私服查依赖、编测试代码**｜未复核
   - `kit/lib/onboard.js:406` 给的启动命令是 `mvn spring-boot:run -pl 模块 -am`，没有 `-o`，也没跳过测试编译。
   - war 项目没给启动命令（`:408`），模型每次自己打包、重新部署。
4. **命令跑完后算整个壳子的指纹**｜未复核，估算
   - curl、node、java、python 这类命令也算（`session.js:1219`、`kit/lib/evidence.js:32,40`）。
   - 壳子下挂 6 个子项目时约起 40 个 git 进程，每条命令多花 4—12 秒。

## 四、可以直接去掉或合并的确认

按去掉后的风险从低到高排。

1. **审查意见一次列全**：放在一个提问框里逐条选。`decisions.md:11` 定的"逐条选择"不变，问的次数从 N 次变成 1 次。
2. **本轮已经说过审查、自测的，收工时不再出提示**（`flow-policy.js:216-226`）。
3. **答"不改"不再作废审查许可**：`session.js:280` 的 ANSWER_NO 只用在"要不要审"这一类问题上。O-流程实测：题目里带"审查"二字、用户答"不改"，审查许可就作废了。
4. **选了"审查→改"，就算准了这一点的复验**：改 `flow-policy.js:281-288`，或者在 `SKILL.md:48` 写明。
5. **归档不再被同步提问打断**：`10-openspec.md:28` 加一句"用户已经说了归档，OpenSpec 问要不要同步时就选同步"。
6. **`/opsx:propose` 不装**，或者装完改成"只写 proposal 就停"（`openspec.js:24`）。
7. **收窄"报问题"的判断**：以"新增""加个""做一个""实现"开头的不算报问题；"用户""客户"后面跟"说""反馈"的那一支，要后面再有问题词才算。
8. **补全认的说法，配上语料测试**：补"都要""测一下""看看页面""推吧""可以提交了""可以归档了"；问句一律不算许可。
9. **能确定的规矩提前送**：串 cd 的写法、起服务走 devserver、新文件要 add、审查带 `--point`，在会话进入流程时由钩子提前告诉模型一次，不放进全局约定（见 M02）。
10. **tasks 那一问和 apply 那一问合成一次**：选项写"定稿并开工 / 只定稿 / 再审 / 我要改"。10-10、10-14 定的"分开确认"靠这几个选项保住。交仓库主人定。
11. **提交、推送、归档改认"本轮最后一次明确表态"**，不被无关的提问框回答顶掉。这和 10-07、10-21 定的"只看最后一句"冲突，交仓库主人定。
12. **push 只留一道确认**（交仓库主人定），两种做法：
    - 去掉 settings 里的 `Bash(git push:*)` ask 规则，全靠钩子。这样钩子一出错就直接放行，风险最高，所以要先修好 P08 再去。
    - 保留这条规则，提示和规范统一写 `git push`，删掉"不再问确认"的说法。

## 五、devserver 和命令为什么慢

来源 O-耗时。秒数按代码路径估算，没实测；标"已复核"的是主审回读过代码。

### 慢在哪（从大到小）

**1. 构建和启动本身：几十秒到几分钟**

- devserver 自己不打包，`--` 后面写什么就跑什么（`devserver.js:435,457`）；重启就是杀掉再全量重跑（`:606,642`）。
- 套件给 Spring Boot 的启动命令是 `mvn spring-boot:run -pl 模块 -am`（`onboard.js:406`、`claude/skills/ttls-see-page/recipes.md:20`），问题在于：
  - 不带 `-o`（只有快检带，`onboard.js:401`），SNAPSHOT 依赖会按更新策略去私服查。
  - spring-boot:run 先跑到 test-compile，测试代码每次都要编一遍。
  - `-am` 把上游模块一起带上。
  - Spring Boot 2.2 起默认 fork，Maven 和应用两个 JVM 同时常驻；IDEA 开着时，这台电脑的内存只剩约 1 GB。
- war 项目没给启动命令（`onboard.js:408`）。模型只能自己打包再部署，每次重打 war，Tomcat 每次全量重新部署。

**2. 多余的重启**｜已复核

- `devserver.js:376-420` 判断"代码改过没有"的方式：
  - 只按目录名排除：`.git`、`.vibe`、`node_modules`、`target`、`build`、`dist`、`out`、`logs`、`.idea`、`.vscode`。
  - git 看得到的改动文件和未跟踪文件，修改时间晚于服务启动就算改过。
  - 服务启动之后有新的提交，也算改过（`:404-405`）。
- 所以下面这些都会触发整轮构建加启动：
  - 在 tasks.md 里打一次勾，改任何 md，改 src/test。
  - 服务自己写出的、没被忽略的 `*.log`、`*.mv.db`。
  - 只是提交了一次。
- 不在 git 里的目录要逐个查修改时间，最多 5 万个（`:410-419`）。

**3. 查进程**｜已复核写法，次数是估算

- `procInfo`、`procTable` 每次都起一个 PowerShell 跑 Get-CimInstance（`:220-238`，超时 15 秒、20 秒），一次约 1—3 秒；每次还跑一遍全表 netstat（`:207`）。
- 次数：首次起服务 2—3 次，重启约 5 次，复用 2 次。
- 合计：首次 3—8 秒，重启 8—20 秒，复用 3—7 秒。
- 输出里的"用了 N 秒"从 startedAt 开始算（`:461,515`）：不含启动前的检查，却含收尾的查询，和用户的体感对不上。

**4. 命令跑完后算指纹**

- `VERIFY_TOOLS` 包括 curl、node、java、python（`session.js:1219`）。命中就算整个壳子的指纹（`evidence.js:32,40`），失败的命令也算（`kit/hooks/after-tool.js:30`）。
- 每个仓库约 6 次 git（`kit/lib/workspace.js:26-39`）。壳子加 6 个子项目，约 42 个 git 进程，每条命令多花 4—12 秒。
- 和 #198 那一批"12 秒预算用完"是同一个根源。
- 反过来，`mvn -f 子项目` 这种写法根本不记证据（`evidence.js:29`）。

**5. 等待粒度**

- 每 2 秒探一轮（`:495`）。
- Windows 上连一个没人监听的本机端口，通常不会马上被拒，`portOpen` 要等满超时，两个地址各等一次（`:174-186`）。端口没通时，一轮实际约 2.8 秒。
- 启动前还要另探 1—2 次端口，每次 1 秒（`:588,613`）。
- 日志里认不出就绪标志的（tomcat7:run 的输出不在 `LOG_UP` 里，`:483`），每 10 秒才发一次 HTTP、每次等 3 秒（`:497,192,538`），部署完之后最多还要再等约 13 秒。

**6. 其余**

- changedSince 的 `git status -uall` 和 `git log`，0.2—3 秒。
- guard-commit 每条命令都要解析 3MB 会话记录（`guard-commit.js:1762`）。
- 几个服务只能串行起：start 要等服务答了 HTTP 才返回（`:464`），`--backend` 要求后端先起好（`:448`）。

### 提速改法（按收益排）

1. **按内容判断"改过"**。
   - 启动时记下 HEAD 和改动文件的哈希，之后比内容，不比修改时间。
   - 只认会进运行的文件：src/main、资源、webapp、pom/gradle；排除 md、openspec/、docs/、src/test/ 和运行时输出。
   - 只是提交了不算改过。
   - 每次能省掉一整轮构建加启动。
2. **改启动命令**（`onboard.js:406,408`）。
   - Spring Boot 改成 `mvn -o spring-boot:run -pl X -am -Dmaven.test.skip=true`。离线编不过就去掉 `-o`；有 test-jar 依赖的不能跳过测试编译。
   - war 给定命令：不 clean，用解开的目录，Tomcat 的上下文直接指过去。
   - 模块多的试 `-T 1C`。
   - 先用第六节采到的分段数据确认哪一项真占时间，再改。
3. **合并进程查询**。
   - 一次 devserver 调用只取一份进程快照（带命令行）和一次 netstat。
   - 看管进程开一个命名管道，名字记进记录；认"是不是自己起的"改成连这个管道，毫秒级完成，PID 被复用也不会认错。
   - 重启省 4—10 秒，复用省 2—5 秒。
4. **after-tool 只算命令针对的那个仓库**（从 `-f`、`--prefix`、`--cwd` 解析），curl 这类探测不算指纹。壳子里每条命令省 3—10 秒，也能消掉"预算用完就放行"的问题。
5. **缩短等待**。
   - 先只探 127.0.0.1，Vite 这类再探 ::1。
   - 日志出现就绪标志后，0.5 秒内发 HTTP 确认。
   - `LOG_UP` 加上 `Starting ProtocolHandler`。
   - 10-28 定的"先看日志，不一直调接口"不动。
6. **其他**：加 `start --no-wait` 和 `wait`，前后端可以并行起；命令里有 push 时才去读会话记录。

## 六、耗时异常自动反思、提议题的机制（M04）

来源 O-耗时的设计，主审整理。对应问题表第 20 条。

**测什么**

- 新建库 `kit/lib/perf.js`，样本追加进 `state/perf.jsonl`，出错一律放行。
- devserver：每一步打点。看管进程逐行看输出，记下 Maven `Downloading from`（同时数条数）、`Compiling N source files`、Spring `Started X in N seconds`、Tomcat `Server startup in`、Gradle `> Task`、Vite `ready in` 第一次出现的时间。据此分出准备、停旧服务、依赖、编译、测试编译、应用启动、等确认、收尾这几段。
- Bash 里的构建和测试：
  - guard-commit 按调用编号记开始时刻，after-tool 算时长。PostToolUse 的输入里有没有 `duration_ms` 没实测过：`evidence.js:44` 读它，取不到就记 0。要先在 `dev/probes` 测清楚。
  - 解析输出里的 `Total time`、Reactor Summary、`Tests run`、`BUILD SUCCESSFUL in`、`built in`。
- 钩子自己：`kit/lib/invocation.js` 记每一段的时间线，超过 2 秒才写一行。
- 看页面：用 `kit/page/scenario-run.js:513` 已经输出的每步毫秒。

**基线和判定**

- 键：项目根目录的哈希 + 种类 + 规整后的命令签名。
  - 签名包括：工具、目标、有没有 clean、有没有 `-o`、跳不跳测试、`-pl`/`-am`；devserver 再分首次、重启、复用。
  - 不含路径和参数值。
- 每个键留最近 10 次成功的样本，取中位数作基线。
- 算异常的条件：
  - 已有至少 3 次样本，总时长到了中位数的 2 倍，并且多出 60 秒以上。
  - 钩子：到了中位数的 3 倍，并且多出 3 秒以上。
  - 套件自己的开销不看基线，直接算异常：devserver 的准备加收尾超过 20 秒，after-tool 超过 8 秒。

**防误报**

- 这几种算"冷"，不进基线：第一次跑、开机不到 10 分钟、当天第一次而且在下依赖。
- 下面几类只记本机、不上报：
  - `Downloading` 有 5 条以上，或者出现连接超时：归为依赖或网络。
  - 空闲内存不到基线时的一半，而且少于 1.5 GB：归为内存。
  - 和别的构建时间重叠，或者 java/node 进程比基线时多 2 个以上：归为并发。
  - 编译的文件数、测试数翻倍：归为工作量。
- 例外：同一个键 5 次里有 3 次是依赖或网络，就记一条"每次都在查远端"。

**反思：事实全部由脚本算出**

- 哪一段多了几秒，占超出部分的几成。
- 空闲内存和总内存、CPU 忙的比例。
- java/node 进程数、IDEA 开没开。这一项在疑似异常时才跑一次 tasklist。
- 下载了多少条、钩子各段的毫秒数、起了几次 PowerShell。
- 重启原因：改动文件按类别计数，不列文件名。
- 只有当没有哪一段能解释一半以上的超出时，才让模型补一句。同一个签名一天最多问一次。这些事实只写进反馈文件，不进模型上下文。

**记成问题反馈**

- 走现成的 `feedback.record`。
- 类型写"耗时"，来源写"耗时自动记录"，避开 `kit/lib/feedback.js:467` 的 isNoise 过滤。
- 标题例：`起服务慢在编译：212 秒，平时 70 秒`。正文写分段对照表、环境、原因。
- 签名按"种类 + 慢的那一段 + 原因"算，不含数字和项目，各台电脑的同类问题并成一条；cwd 传空，照 `kit/lib/toolstats.js:101` 的做法。

**防刷屏**

- 每台电脑每天最多 3 条新记录。同一个键报过之后 24 小时内不再报，除非又慢了 1.5 倍。同一个签名再出现时只补一行"又出现了"。
- devserver 在结果行前面加一行，例如：`耗时：这次 212 秒，平时 70 秒，慢在编译 +140 秒；已记 F…，不用处理`。
- after-tool 只写样本、回一行附加上下文；真正记反馈留到用户开口、收工的时候做。toolstats 现在就是这条路，照搬：`toolstats.js:74-116`、`task-anchor.js:440`、`verify-gate.js:732`。
- 使用情况只加次数：`perf.slow.<种类>`、`perf.env.<原因>`。`kit/lib/usage.js:142-143` 会过滤名字带 ms、duration 的键，键名要避开这些词。

**落在哪些文件**

- 新建 `lib/perf.js`，加进 `dev/pack.js` 的必备清单。
- 要改的地方：devserver 和看管进程打点；guard-commit 记开始时刻；after-tool 判定和提示；invocation 加时间线；hook-host 记慢调用；task-anchor、verify-gate 调汇总。

- 新开关 `perfReport`，三档：on 上报 / local 只记本机 / off。按硬规矩 10 同时改五处。

**测试**（`dev/test-perf.js`，用假用户目录）

- 解析 Maven、Gradle、Vite 的样例输出；覆盖判定的每个分支。

## 七、缺陷清单

### A. 安装、自动更新、发布

**P02 [高｜确认｜已复核] 自检不看路由，路由坏了不回滚；发版前也没有真发一次请求的冒烟**（S-路由、Opus）

- `publish.js:99-103` 发布前跑的也是同一个 selfCheck。
- 结果：1834 那种把请求改坏的版本能照样发出去，同事那边自动更新也判成功。再叠加 P36，路由起不来时钩子一直放行。

**P03 [中｜确认｜已复核] 版本号不是最后写；settings.json、CLAUDE.md 直接覆盖写**（S-路由）

- `install.js:926-927` 先写 VERSION，后面还有 `finishInstall`：写全局约定、重新登记、撤回 IDEA MCP、停了路由再起（`:991`）。中途被打断的话，VERSION 已经是新版，自动更新就不再重装。

- 改法：VERSION 挪到最后写，或者装之前写一个"正在安装"的标记；先写临时文件再改名；`--sync` 加锁。

**P04 [中｜确认｜子代理复核] 回滚也失败时，提示不够**（S-路由，O-路由复核：部分成立）

**P05 [低｜确认｜子代理复核] 更新锁没有租期**（O-路由复核成立）

`dev/pack.js:37-42`。改法：改成扫描 `kit/hooks/*.js` 和 `kit/lib/*.js`。

`install.js:383` 那个空数组被 `:388` 覆盖了，注释写的意图不成立。

**P37 [中｜确认｜未复核] 路由没起来也照样登记 HTTP 钩子**（O-路由）

### B. 钩子与流程

**P08 [高｜确认｜已复核] push 漏检**（S-钩子）

- `guard-commit.js:98-133` 的 splitCommand 遇到引号整段原样收，也不认反引号；`:391-396` 的兜底 pushAnywhere 先把引号里的内容换成占位词，git push 后面紧跟反引号时也匹配不上。
- 场景：`echo "r $(git push)"`、`` x=`git push` `` 都会放行；PowerShell 里的 push 没有第二道确认。
- 改法：
  - 递归检查 `$(…)` 和反引号里的子命令。
  - 有展不开的替换就 ask。
  - 补上 `PowerShell(git push:*)`。

**P09 [中高｜确认｜已复核（实测）] 认许可的说法认不全，还把问句当许可**

和 R5 是同一件事。改法见第四节第 7、8 条和 M12。

**P10 [中｜确认｜子代理复核] HTTP 钩子共用 3 个线程，超时就放行**（O-钩子复核成立）

- 三个线程都忙时，新调用排到最闲的线程后面，从排队起就开始计时（`kit/lib/hook-host.js:91-97,144`）。
- 一次超时之后，`:152` 把同一个线程上排着队的调用全部按放行回掉，只给超时的那一次记反馈。
- 失败的调用也算进"钩子到了"（`:128-129`、`kit/lib/hook-health.js:107-108`）。第一版说"钩子全坏了也没人知道"说重了：`hook-worker.js:27` 会记反馈，只是会话里不提醒，也不切换方式。
- Bash 读令牌只有 guard-commit 这一道（`settings.fragment.json:3` 放行了全部 Bash，`install.js:220` 的 deny 只管 Read）。guard-commit 一放行，令牌就读得到。
- 改法：
  - 令牌、改套件、push 的检查固定走命令方式。
  - 超时时 ask，不放行。
  - 其余排队的调用转到新线程重跑。

**P11 [中｜确认｜已复核] hook-health 切回命令方式时可能清空 config.json**（Opus）

- `hook-health.js:131-137`：读 config.json 失败时用空对象，写回去只剩 `hookTransport`。
- 只要有一轮没收到钩子调用，就永久切成命令方式，还在用户开口的钩子里同步跑 `install --sync`。
- 改法：读不出来就不写；连续两次没收到才切换；写的时候加锁。

**P12 [中｜确认｜已复核] HTTP 方式下 guard-commit 用的是路由进程的工作目录**

- `guard-commit.js:1014,1449` 传的是 `process.cwd()`，HTTP 方式下这是路由的数据目录，不是项目目录。
- 改法：换成 `j.cwd`。

**P13 [中｜确认｜子代理复核] 便宜的安全检查排在昂贵的流程检查后面**（O-钩子：部分成立）
