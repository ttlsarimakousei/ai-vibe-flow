## 二、到点替用户做主（ask-timeout）

### A1 到点放行的范围比说明窄（P2，确认）

`kit/hooks/ask-timeout.js:38` 的 `DESTRUCTIVE` 只认这些：带 `-r`、`-f` 的 `rm`；`git checkout -- .`、`git restore .`（只认整目录）；带 `-Recurse` 的 `Remove-Item`；带 `/s` 的 `del`、`rd`。别的命令最后都走到 `ask-timeout.js:188` 按允许。探针（只测这几条正则，不跑钩子）的结果：

| 命令 | 到点 |
|---|---|
| `rm src/main/java/A.java`、`del src\A.java`、`Remove-Item src\A.java` | 放行 |
| `git checkout -- src/A.java`、`git restore src/A.java`（丢掉没提交的改动） | 放行 |
| `mysql -e "DROP TABLE t_order"`、`psql -c "TRUNCATE t_order"`、`redis-cli FLUSHALL` | 放行 |
| `curl -X DELETE http://…/api/users/1`、`truncate -s 0 app.log`、`echo "" > src/A.java` | 放行 |
| `rm -rf`、`git reset --hard`、`git clean -f`、`git push --force`、`db.py`、`redis.js` | 不放 |

- 直连数据库客户端那一类，绕过了查库工具自己的备份和确认（`db.py` 的 `write_policy`）。
- 说明和代码对不上：`vibe-kit/README.md:107`、`kit/ui/ui.html:629` 都写着"还原不了的删……到点也留给你"。按 AGENTS.md"配置页说明和行为双向"，这算缺陷。
- 现有测试只测了正则里已经有的写法（`test-feedback1118`）。
- 改法要先定方向，见第七节 Q1。

### A2 不是 Bash 的确认框到点也按允许（P2，确认，要定）

`decide()` 只对 Bash、PowerShell 做了分类（`ask-timeout.js:146-188`），别的工具的确认框到点一律按允许：

- MCP 工具：发消息、建议题、操作浏览器这类往外发的。
- WebFetch 访问新的域名。
- Edit、Write 改 `~/.claude/settings.json`、`~/.claude/CLAUDE.md`。2026-11-04 起套件不拦改套件。加上 `install.js:459` 的"你删掉的不再补"，令牌的 deny 规则一旦被改掉，下次安装也不会补回来。

仓库主人 2026-11-18 定过"什么时候都按允许"。这里列出来，是因为外发和改权限规则这两类还原不了，和"还原不了的删留给你"是一个道理。见 Q1。

### B4 用户点了允许、命令还在跑，到点照样记一条（P3，可能）

- `settled()`（`ask-timeout.js:68`）只认两样：这次调用有了结果，或者后面有用户说的话。
- 用户点了允许以后，命令要跑完才有结果。用户 1 分钟后点了允许、命令又跑了 9 分钟以上，到第 10 分钟 `decide()` 照样会跑。`review.js run` 被 guard-commit 改成 600 秒超时，正好落在这个区间。

## 四、健壮性

### B1 坏掉的锁文件永远收不回（P2，确认）

- `lib/state-store.js:63` 判断锁过期，前提是读得出 `pid`。锁文件是空的、全是 0 时，`owner()` 返回 null，`stale(null)` 为假。于是每次 `acquire` 等满 2 秒后返回 null，`update` / `write` 写失败。
- 探针（scratchpad 里的临时文件）：空锁、全 0 锁都"没写，等了 2012 ms"；进程号不在的旧锁 24 ms 就收回了。
- 怎么会出现：`claim()`（`state-store.js:34`）先写临时文件再建硬链接，没有落盘。断电时目录项落了盘、内容没落盘，留下的就是这种锁。第 80 条专门处理过断电留下的坏状态文件，锁文件没处理。
- 影响：
  - 如果是 `review-points`、`<会话>-flow` 这类要紧的状态，每次钩子调用写它都白等 2 秒，12 秒的预算很快用完。
  - 状态一直写不进去，表现是"审过了不认""开工了不认"。
  - 要等 `cleanState` 按天数删掉锁文件才恢复（`lib/session-state.js` 的 `cleanState`）。
- 改法：锁文件读不懂、修改时间超过几秒，就按过期处理。照 `state-store.js` 里 `broken()` 对状态文件的做法。

### B2 guard-ask 吞掉异常（P3，确认）

`kit/hooks/guard-ask.js:68` 的 `catch (e) { out = null; }` 包住了整个调技能的分支，包括 `/opsx:apply` 的开工门槛、进流程的判断、交接许可。出错时放行，这符合硬规矩 2；但没有调 `recordHookError`，内网出了问题，问题反馈里看不到。

### B3 自动更新时原地覆盖钩子（P3，可能）

- `install.js:925` 用 `copyDir` 加 `copyFileSync`（`install.js:93-110`）原地覆盖 `kit/hooks`、`kit/lib`。别的会话的钩子正好在这一刻载入，可能读到半截文件，或者新旧版本混着用。
- 一般后果是这一次钩子出错放行，问题不大。
- 例外是 push：`pushFailOut`（`lib/session-out.js:60`）只在 `cli()` 的 catch 里生效。如果 guard-commit 在顶层 `require` 时就崩了，进程直接退出，push 不经确认就跑了。
- 窗口不到一秒，概率低。改法有两种：拷到临时目录再逐个改名；或者 guard-commit 的入口先用 try 包住 `require`，载入失败时命令里像推送的按 `askOut` 回。

## 五、查库工具

### A4 有副作用的函数调用被当成安全的查询（P3，确认，要定）

探针调 `sqlguard.analyze` / `classify` / `readonly_problem`（不连库）：

| SQL | 分类 / 风险 / 只读模式 | 实际 |
|---|---|---|
| `SELECT pg_terminate_backend(123)` | SELECT / SAFE / 放 | 立刻断掉别人的连接，回滚不了 |
| `SELECT setval('seq_order', 1)` | SELECT / SAFE / 放 | PostgreSQL 的序列不跟着事务回滚；只读事务里会报错，非只读模式下照样生效 |
| `SELECT lo_unlink(1)` | SELECT / SAFE / 放 | 删大对象（跟着回滚） |
| `SELECT * INTO t_bak FROM t_order` | SELECT / SAFE / 拦 | 非只读模式下按查询跑；执行器最后回滚，影响小 |

- 别的难认的写法都判对了：`WITH … DELETE`、`CALL`、`EXEC`、`MERGE`、`REPLACE`、`LOCK TABLES`、`SET GLOBAL`、`COPY`、MySQL 可执行注释 `/*! */`、多语句。
- 执行器读的时候先 `readOnlyHint`，最后一律回滚（`DbRunner.java:62`、`:370`），所以只剩"回滚撤不掉的那几个函数"这个口子。见 Q3。
