## 主要问题

### R1-001：同一数据库确认串可被两个进程同时消费

- **优先级：P1。状态：已复现。** 主代理在假 HOME 中让两个 Python 进程先共同读取，再依次保存；同一确认串两次 `pending_take` 都返回成功。
- **位置：** `vibe-kit/claude/skills/ttls-db-crud/scripts/journal.py:119`，读取位于 124 行，删除及保存位于 130—135 行；原子替换位于 101—109 行。调用方为 `db.py:1630` 和 `db.py:2003`。
- **触发场景：** 两个终端、重复的后台调用或工具重试同时携带相同 `--ack` 执行。例如 `UPDATE ... SET counter=counter+1 WHERE id=1`：两次操作的确认指纹和行数相同，均可继续执行。
- **根因：** 单次消费是“读登记表 → 判断存在 → 删除 → 替换文件”，没有覆盖整个过程的跨进程锁。`os.replace` 只保证读不到半个 JSON，不保证只有一个消费者。
- **影响：** “一个确认串只能执行一次”的约束失效；重复 UPDATE、INSERT 或 undo 可能被执行两次。后台执行器串行处理数据库请求也不能补救，因为确认串已经分别消费成功。
- **修复方向：** 将确认串登记、校验和消费放入同一跨进程临界区，或改为每个 token 一个文件并以排他原子操作认领。不能仅在 `_pending_save` 外加锁；必须锁住读取到删除的整个过程。并发登记不同 token 也应保留两条。
- **验证办法：** 保留双进程屏障反例，断言同 token 恰好一个成功；再测两个不同 token 同时登记、消费互不丢失，以及持锁进程退出后的恢复。使用假 HOME，不需要 JDBC。

### R1-002：提交确认丢失时仍向用户保证“已经回滚，数据没有变”

- **优先级：P1。状态：代码确认；Python 展示分支已注入验证，JDBC 故障未验证。**
- **位置：** `vibe-kit/claude/skills/ttls-db-crud/scripts/runner/DbRunner.java:1404`、`DbRunner.java:1406`，批量执行同类路径位于 1472—1476 行；`vibe-kit/claude/skills/ttls-db-crud/scripts/db.py:1821`—1827 行。
- **触发场景：** 数据库完成 COMMIT 后连接中断，驱动的 `commit()` 抛出 `SQLException`；或者提交后的确认包丢失。此时服务端可能已经提交，客户端无法凭异常证明未提交。
- **根因：** 执行和提交共用同一 `catch (SQLException)`，统一返回 `SQL_ERROR`。后续 `rollbackQuietly` 没有成功证明；即便它成功返回，也不能撤销已经完成的提交。Python 只对 `UNKNOWN_OUTCOME/TIMEOUT` 提示结果不明，普通 `SQL_ERROR` 一律宣称数据未变。
- **影响：** 用户可能依据错误提示重跑，造成重复写入；留痕和真实库状态矛盾。批量 undo 也存在同类误报。
- **修复方向：** 明确区分“执行未提交”“正在提交”“提交已确认”。在提交阶段抛错时返回结果不明，保留快照和操作记录，提示先核对数据库；回滚失败同样不能保证数据未变。不得自动重试结果不明的写操作。
- **验证办法：** 用假 JDBC 驱动让 `commit()` 先记录已提交事实，再抛异常；断言返回结果不明且 Python 不打印“数据没有变”。另测执行阶段错误、确认回滚成功、回滚失败。当前机器没有 Java/JDK，主代理仅注入了 Python 的 `SQL_ERROR` 返回，已确认会打印错误保证；这不能冒充真实 JDBC 复现。

### R1-003：同一事务取快照不足以保证快照对应实际被修改的数据

- **优先级：P1。状态：待验证。** 已确认缺少并发保护的代码路径，具体触发依赖数据库隔离级别和驱动行为。
- **位置：** `vibe-kit/claude/skills/ttls-db-crud/scripts/runner/DbRunner.java:233` 仅关闭自动提交；`DbRunner.java:436` 普通 SELECT 取快照；`DbRunner.java:1359` 后执行原始 DML；1387—1394 行只比较影响数量。`journal.py:284`—301 行依据快照生成 UPDATE 还原语句。
- **触发场景：** 会话 A 取快照后，会话 B 修改同一行并提交，A 再执行原 DML；或者原条件匹配的主键集合变化但行数相同。A 最终影响行数仍不超过 `expect`。
- **根因：** 代码没有锁定快照行、没有指定可证明一致的隔离策略，也没有将写入对象绑定到快照主键及旧值。数量一致不能证明行集合和旧值一致。
- **影响：** 留下的 `before.json` 可能不是写操作紧邻之前的值，生成的 `undo.sql` 可能覆盖另一事务已经提交的修改，或针对错误的行集合。执行前后数量检查本身有效，但它解决不了这一类变化。
- **修复方向：** 为各数据库定义写入与快照的一致性策略：在事务内锁定目标行、使用主键集合约束后续 DML，并对旧值或版本做冲突检查；必要时采用可串行化及冲突重试。仅增加一次 COUNT 仍不够。明确暂不支持的语句和数据库组合。
- **验证办法：** 在假目录中的测试数据库建立双连接屏障：A 快照后暂停，B 修改相同行或替换条件集合，再继续 A；核对 before、最终数据、affected 和 undo。至少覆盖 H2 与一个正式支持数据库的默认隔离级别。本轮没有 JDBC 环境，未把该推演标成已复现。

### R1-004：发布分支与标签可能只成功一个，重跑也不补齐

- **优先级：P1。状态：已复现。** 主代理用临时裸仓库真实推送：标签冲突时 push 非零退出，但 main 已前进；重跑不补核对标签的行为由代码确认。
- **位置：** `vibe-kit/publish.js:182`—187 行；相同树直接返回位于 `publish.js:157`。自动回退依赖标签的位置为 `vibe-kit/kit/lib/updater.js:268`—274 行。
- **触发场景：** 远端已经存在同名版本标签但指向其他提交，或服务端允许更新发布分支、拒绝对应标签。普通多 ref push 可以部分成功。
- **根因：** 同一次 `git push` 携带分支和标签，没有 `--atomic`，也没有后置核对两个远端引用。退出非零被统一当发布失败；再次运行时只要分支树已相同就立即返回，不检查版本标签。
- **影响：** 维护者看到发布失败，但同事的自动更新已经能看到新分支；以后依赖该版本标签的回退可能失败或取到错误内容。重新发布不能自动恢复这一状态。
- **修复方向：** 远端支持时使用原子推送，并在发布前后核对标签、分支与包内容的一致性。相同树的幂等分支也必须检查标签。远端不支持原子推送时，应明确失败并保留可恢复状态，不自动退化为部分发布。
- **验证办法：** 只用临时裸仓库：预建冲突标签，发布新树，断言分支、标签全部不变；再以服务端钩子仅拒绝标签进行验证。覆盖重跑和已有内容一致但标签缺失的情况。本轮没有向任何真实远端执行 push。

### R1-005：服务全机登记表的并发更新会相互覆盖

- **优先级：P2。状态：已复现。** 主代理提取原 `writeReg` 函数，在假 KIT 下以两个进程受控重叠读写，最终丢失一条登记。
- **位置：** `vibe-kit/kit/tools/devserver.js:71`—80 行，真实启动写入入口为 461—463 行；跨目录认领读取入口为 105—109 行。
- **触发场景：** 两个项目、两个会话或前后端同时启动不同端口服务；两个进程先读到同一登记表，分别加入自己的服务，后写入者覆盖先写入者。
- **根因：** `readReg → fn(o) → renameSync` 没有跨进程锁。独立临时文件名不能保护读改写。
- **影响：** 项目本地记录仍可能存在，但另一个目录的 start/status/stop 依赖全机表，可能再度认不出已经由套件启动的服务，重复启动、挑选其他端口或漏停。不能将此项夸大成服务进程必然丢失。
- **修复方向：** 使用现有 `state-store.update` 包住全机表的读改写；写失败保持项目记录兜底。认领时涉及两个本地文件的搬迁，应定义顺序和可恢复状态。
- **验证办法：** 保留受控双进程反例，再用假服务检查并发启动两个端口后，两项都可从第三个目录发现和停止；并发 unregister 不得删除另一项。

### R1-006：驱动登记表也存在独立项目间的覆盖更新

- **优先级：P2。状态：代码确认。**
- **位置：** `vibe-kit/kit/lib/drivers.js:153`—159 行，`use` 的读改写位于 181—187 行，`remove` 位于 193—209 行。后台入口为 `vibe-kit/kit/lib/onboard.js:879`，项目锁位于 893—908 行。
- **触发场景：** 项目 A 自动登记达梦驱动，项目 B 同时登记 MySQL 驱动；或配置页去掉一种驱动时，后台正在登记另一种驱动。不同项目的 onboard 锁不能互相排斥。

- **影响：** 已复制的 jar 仍在，但对应登记、默认版本或“用户去掉过”标记可能丢失；查库重新报缺驱动，或用户删除决定被旧表恢复。该路径与未找到神通驱动的既有反馈不能直接画等号，本轮未拿到那些电脑的现场。

- **验证办法：** 假目录中构造两个最小驱动 jar，双进程在读取后设置屏障，断言两类都保留；再测 remove 与 use、同类不同版本并发。不得使用真实用户驱动目录做写入。

### R1-007：Redis 保留 TTL 的实现会延长过期时间，极短 TTL 会变成永久

- **优先级：P2。状态：已复现。** 主代理用假 RESP 服务返回 `PTTL=0`，真实 Redis CLI 随后发送 SET，不带 PX 或 KEEPTTL；正 TTL 延长及其他客户端竞态仍为代码推演。
- **位置：** `vibe-kit/claude/skills/ttls-redis/scripts/redis.js:383`—392 行。
- **触发场景：** `PTTL` 返回 0 时，`left > 0` 不成立，接下来的 SET 没有过期选项；TTL 为正时，查询和 SET 之间经过网络等待或服务端阻塞，SET 又从旧的剩余时长重新计时。原 key 也可能在两条命令之间已过期或被其他客户端更新。
- **根因：** 读取 TTL 和设置值是两条独立命令，且“0 毫秒剩余”被当成无过期时间。
- **影响：** 本应到期的缓存可能变为永久，或被延长、复活；输出仍称 `kept_ttl_ms`，与实际绝对过期时刻不符。
- **修复方向：** 在支持的 Redis 版本上使用原子保留 TTL 的设置方式；兼容旧版本时用原子脚本定义现存、已过期和永久 key 的行为，并单独处理 0。不要仅把条件改为 `>=0`，因为 PX 0 仍不是正确修复。
- **验证办法：** 假 Redis 分别返回 PTTL 为 -2、-1、0、正值，记录客户端后续命令；对正值人为延迟响应，核对绝对到期时刻。另验证查询后 key 过期和被另一客户端替换的竞态，不连接真实缓存。

### R1-008：环境就绪检查读取了错误的 Maven 目录字段

- **优先级：P2。状态：已复现。** 主代理在假目录中配置 Maven `home`、不将其加入 PATH，检查结果仍报告 Maven 缺失。
- **位置：** `vibe-kit/kit/lib/readiness.js:14`、23—24 行；配置清洗的实际字段定义为 `vibe-kit/router/kit-api.js:35`。
- **触发场景：** 用户通过配置页登记 Maven 安装目录，系统 PATH 没有 Maven。
- **根因：** JDK 使用 `path`，Maven 使用 `home`，但就绪检查将两者都按 `path` 拼接 `bin`。缓存指纹采集也使用同一个错误字段。
- **影响：** 已正确配置的 Maven 被误报缺失，配置页和会话开始注入的就绪摘要不可信。Maven 文件在原 home 下变化也不能按预期参与工具指纹。

- **验证办法：** PATH 中没有 Maven、local.json 仅有 Maven home，假 home/bin/mvn.cmd 存在时应报告文件存在；删除后应失效并报告缺失。另测只登记 settings/repo、未登记安装目录时不能误认工具存在。

### R1-009：反馈编号分配无锁，可发生记录覆盖或同号多记录

- **优先级：P2。状态：代码确认。**
- **位置：** `vibe-kit/kit/lib/feedback.js:150`—160 行，记录创建位于 208—222 行，按编号修改位于 175—177 行。
- **触发场景：** 不同会话钩子或 HTTP 工作线程同时首次记录问题。两者读取相同 seq 并扫描相同已有目录，各得到相同的下一个编号。
- **根因：** 编号读取、目录扫描、编号递增和最终文件创建不在同一个排他区域；`writeFileSync` 创建反馈文件也没有排他标志。同签名记录的次数更新同样是整文件读改写。
- **影响：** 同标题时会落到相同文件名并覆盖一条；不同标题时会出现同 id 的多个文件，按 id 的 `markRecord`、放行回写和上报关联可能指向错误记录。次数并发增加也可能丢失。
- **修复方向：** 用全机反馈锁覆盖编号分配和文件创建；记录更新按文件或 id 串行执行。也可使用真正唯一的内部标识，展示序号单独分配，但不能破坏旧 id 的关联契约。
- **验证办法：** 假 KIT 中让两个进程在 nextId 读取后同步继续，分别测试相同、不同标题；断言 id 唯一、记录数准确；同签名并发重复时次数不丢。然后检查清空、上报和通行证仍引用原记录。

### R1-010：清理只扫描部分条目，却据此删除整个目录

- **优先级：P2。状态：已复现。** 主代理在假项目建立 2001 个文件，把唯一最新文件放在扫描上限之后，运行真实 `cleanTmp`，目录被删除。
- **位置：** `vibe-kit/kit/lib/tidy.js:217`—231 行；删除判定与执行位于 275—280 行。
- **触发场景：** `.vibe/tmp/<事由>/` 有超过 2000 个条目，或最近修改的文件位于扫描深度之外。已扫描文件及各级目录的 mtime 都旧，但未扫描的已有文件刚被改过。
- **根因：** `newestMtime` 达到数量和深度上限后仍返回普通时间值，没有“不完整”标志；读取目录失败也被视为可继续判断。调用方据此认定整目录超过保留时间，直接递归删除。修改已有文件内容不会保证所有祖先目录 mtime 同步变化。
- **影响：** 最近仍在使用的临时脚本、解包样本或验证结果可能被自动删除，与“一个文件都没动过才清理”的说明不符。匹配活动变更名的目录会被保留，因此影响主要落在独立事由、已归档后继续工作的目录。
- **修复方向：** 返回 `{ newest, complete }`；达到上限、读失败、无法判断时跳过自动删除。可另存活动标记辅助性能，但仍需保证不完整扫描不触发删除。
- **验证办法：** 保留已复现的 2001 文件反例：将目录和前 2000 个时间设为 8 天前、最后一个设为现在；修复后运行七天清理，目录必须保留。另测超过深度上限及子目录不可读；后两类边界尚未动态验证。

### R1-011：审查技能和架构文档仍包含已取消的行为

- **优先级：P3。状态：代码确认。**
- **位置：** `vibe-kit/claude/skills/ttls-cross-review/SKILL.md:24`、26 行仍写每轮独立预算、累计默认 300 秒、剩余秒数；同文件 34 行又明确不限时。`docs/architecture.md:25`、56 行仍写开工前自动拉代码；实际 `vibe-kit/kit/lib/pull.js:3` 标注该入口已不用，源码搜索不到 `beforeWork` 调用方。
- **触发场景：** 模型读取独立审查技能，或维护者依据架构文档判断开工前是否已更新代码。
- **根因：** 行为调整只追加新说明，没有移除同一文档中的旧指令；协作文档未同步清理失效入口。
- **影响：** 模型可能仍按“300 秒预算”取消审查或向用户解释不存在的剩余预算；维护者可能误以为会自动拉代码。不能把“不再自动拉代码”或“不按预算截断”本身当缺陷，它们是用户决定。
- **修复方向：** 统一为实际行为：秒数只代表预期耗时，超时记录反馈；代码拉取由用户负责。旧流程放历史文档，不与当前指令并存。
- **验证办法：** 定向检索技能、用户手册、配置页、架构及约定中的相关说法；核对已移除旧预算、自动拉代码承诺，保留历史变更说明。将这些已取消行为加入文档新鲜度检查。

## 改进路线：不作为确定缺陷计数

### 第一阶段：给共享状态定义真正的事务边界

现有 `state-store.js` 已解决部分跨进程读改写问题，不宜再新增另一套 Node 锁。先修 R1-001、R1-005、R1-006、R1-009，再清点其余“read → 修改对象 → write”的共享状态。按更新语义分类：计数用 update、整份替换限定单写者、一次性许可用排他消费。Python 确认串需要等价的跨进程方案，不能因为语言不同而降低一次性保证。

登记表应有少量统一契约测试：并发加入不同项、同项冲突、消费一次、进程中断、文件损坏和存储失败。不要只测试 JSON 可解析、文件存在或单进程累计。

### 第二阶段：统一外部写操作的结果状态

数据库和发布都需要区分“未发生”“已发生且确认”“结果不明”“部分发生”。先修结果表达，再讨论自动恢复。数据库本地留痕宜在执行前保存操作标识和 pending 状态，成功后更新结果；本地写盘失败时应保留足够的恢复线索。暂不要求自动撤回真实数据库数据。

对支持的每类数据库列一张能力表：默认隔离、DDL 隐式提交、生成主键、计数语义、锁语句、二进制和大字段、连接池/后台连接状态。不能用 H2 成功推导五个厂商驱动都满足同一事务语义。

### 第三阶段：明确验证证据能证明什么

`evidence` 已绑定输入和环境指纹，这是合理基础。但“某条验证命令成功”与“某项验收用例被覆盖”是两件事。后续可让场景、构建、自测输出用例标识与结果，保留命令成功、覆盖范围和适用版本三项事实，不把一次普通脚本运行扩大成所有任务通过。无需增加全局提示词。

### 第四阶段：降低跨模块字段和文档漂移

本机环境字段、默认开关、阶段名称和用户可见说明已有多处镜像。可先统一纯数据与解析函数，再拆分大文件。`session.js`、`guard-commit.js`、`ui.html` 的体量增加维护成本，但不能仅为缩短文件而拆分；应优先按稳定职责和输入输出拆分，并保留兼容导出。

将行为文案检查从“旧片段是否已不存在”扩展到少量显式契约：审查不截断、自动拉代码已取消、IDEA 不再自动登记、默认开关两处一致、安装与卸载归属一致。检查业务结论，不要求文案逐字一致。

### 第五阶段：补足离线包的可追溯性

自带 OpenSpec 和 Playwright 的离线交付符合内网限制。建议每版包附机器可读的依赖版本与哈希清单，并明确核心 Node、页面执行器、OpenSpec 各自的最低运行版本。Java 源码和 class 的对应关系宜用构建时来源摘要验证；文件 mtime 和 class major 只能证明部分事实，无法在重新检出后证明二者内容对应。本轮未验证存在实际错配，不按缺陷计数。

## 测试覆盖评价与补测顺序

当前测试对历史反馈、默认值、许可、材料、安装升级、HTTP 钩子、假网关和页面入口覆盖较多。已有数据库测试核对了快照完整、实际影响行数超出后的回滚；驱动测试验证多个版本顺序登记；清理测试验证活动变更保留。这些检查有业务价值。

## 本轮自我反驳

1. **“原子改名已经避免并发损坏。”** 它能避免半文件，不能避免两个进程读到同一个旧值。R1-001、R1-005 已用受控双进程证明；驱动与反馈仍保留代码确认层级。
2. **“数据库发生异常后调用了 rollback，所以没改。”** 只有尚未提交且回滚确认成功时才能这样保证；COMMIT 响应丢失必须保留不明结果。本轮不把 Python 分支注入说成 JDBC 复现。
3. **“快照在同一事务就一定一致。”** 事务并不自动保证普通 SELECT 与后续 DML 使用相同旧值或目标集合；但具体驱动隔离行为需要实验，因此 R1-003 单独列待验证。
4. **“服务登记丢失意味着服务必然无法停止。”** 项目本地记录仍是兜底，所以将影响限定为跨目录发现、认领和停止，不夸大为全部管理能力失效。
5. **“配置页工作线程单一，驱动不会并发。”** 它只能约束该入口；不同项目的后台探索和 CLI 是其他进程。修复也必须覆盖所有调用方。
6. **“临时文件可删，所以扫描上限无关紧要。”** 当前契约明确保留最近修改文件；扫描不完整时无法证明已过期。活动变更名豁免已经计入触发范围。
7. **“审查与快照的成本越小越好。”** 用户已决定审查不按预算截断；本报告不建议恢复累计预算。改进方向是状态正确性和材料边界，不是取消用户决定。
8. **“所有潜在风险都要列成缺陷。”** 未确认 class 错配、未验证厂商兼容、统计近似性和大文件体量只列改进或边界，没有为了数量升格为确定缺陷。取消合并推送、取消 IDEA 自动接入、fail-open 均按既定取舍审核。
