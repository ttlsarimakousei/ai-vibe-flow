三轮合并后保留 **21 项确认问题：P1 7 项、P2 13 项、P3 1 项**；另保留 **1 项待真实数据库验证的潜在 P1 风险**。确认指代码与契约不一致已有依据，不表示在生产环境发生过。19 条动态观察支撑其中 18 项，其余 3 项以代码和调用链确认。动态观察包含函数级并发、假服务、输入注入和错误分支注入，证据强度不同。

基础回归 **64 套、3498 项、0 失败**；177 个 JavaScript 文件语法检查通过，13 个 Python 文件语法检查及 3 套离线自测通过，其中 SQL 分类器 83 项。回归通过没有覆盖本次发现的跨进程消费、提交确认丢失、部分发布和扫描截断等边界。

## 单列的待验证风险

**V01：数据库快照与实际写入的并发一致性，潜在 P1。** `DbRunner.java` 只关闭自动提交，普通 SELECT 取快照后再运行原 DML，影响行数相同不证明主键集合和旧值相同。另一连接在中间修改数据时，before 和 undo 可能不再对应紧邻写入之前的状态。

代码存在缺少显式行锁、版本校验或同一主键集合约束的路径，但具体行为取决于厂商数据库、隔离级别和 SQL。没有 Java/JDK，未做双连接实验，**不计入 21 项确认问题**。验证方法及修复候选见第一轮 R1-003；先在隔离环境用双连接屏障验证，再决定支持矩阵和实现，不能直接把一种数据库的锁语法推广给所有厂商。

## 主要分歧如何裁定

1. **整套提案 resolve：恢复为 P2。** 第二轮依据逐点命令示例认为无 point 属于非支持入口；第三轮找到技能中明确保留的人工整套 agent 兼容方式。该方式不会建立 review-points，而提案记入 reviewed-proposal；resolve 固定读 code 确实无法配对。修复时同时说明逐点与整套两类入口，不能只改示例掩盖支持能力。
2. **重复迁移：由第二轮 P1 降为 P2。** 会覆盖用户选择并打断自动工作，但当前迁移把自动模式关闭，不会自行扩大写入许可。仍需修正永久标记及已丢标记的兼容恢复。
3. **半截 SSE：保留 P2，限制影响表述。** 普通 HTTP 客户端确实得到正常结束，路由却记传输失败；这与路由自己的完整性契约冲突。没有验证真实 Claude SDK，不写成“Claude 必然把半截回复当成功”。
4. **数据库错误：保留 P1，严格区分证据。** Python 分支的错误保证已证实；真实 COMMIT 后确认丢失尚未注入。不把错误分支模拟扩展成厂商数据库事故已复现。
5. **共享状态：不把原子改名当事务。** F09、F11 使用受控交错执行原函数，证明存在可达丢更新／双消费路径，不是自然压力测试的发生频率。驱动和反馈同类路径仍只标代码确认。

## 整套设计评价

本机确定性检查、命令与 HTTP 共用 handle、假用户目录测试、受审输入指纹、令牌保护和离线交付依赖都值得保留。问题主要发生在这些机制的接缝：某模块把原子落盘当原子消费，某入口没有沿用另一入口的输入指纹，安装成功与服务可用使用不同判据，清理上限被当成完整扫描。

不建议新增一套更重的工作流。先把现有契约做实：一次性资格、共享状态、外部写入结果、输入版本、进程归属和完整性检查。大文件拆分、文案统一和性能调整排在这些正确性问题之后。

具体方案、取舍与验收条件见 [改进路线](20261030-vibe-kit-改进路线.md)。优先新增以下修复批次：

- 数据库确认串排他消费、提交结果不明分类、发布分支与标签一致性。
- 路由停止前验证本安装归属；安装及更新自检核对必装路由实际可用，`--no-router` 保持原语义。
- 兼容审查在启动和完成时绑定材料版本，不得在旧结论到达后为它补上当前输入哈希；补齐整套提案意见处理。
- 纠正验证证据分类、迁移状态生命周期、服务／驱动／反馈的并发更新。
- 修清理、TTL、源码删除、请求总期限、运行版本提示和 HTTP 故障反馈，再清理旧文案。

本次没有实施这些修复，不应把报告提交当成套件已修复版本。
