### F04 的最终裁定：人工整套兼容入口有效

第二轮“帮助要求 point，所以不计常规入口缺陷”的排除理由不完整。`ttls-cross-review/SKILL.md:12` 明确保留人工整套 agent 审查，`:38` 规定调用现有审查代理；`session.js:1951` 至 `:1959` 将它记进 `reviewed-proposal` 或 `reviewed`，没有生成逐点 `review-points` 记录。

因此该模式真实存在，没有可以自然传给 resolve 的当前 point。即使照统一说明随意加 point，`flow-policy.record` 返回空记录，也不能处理该整套结果。`review-runner.js:405` 固定读取 code、`:421` 固定写 code 是有效缺陷，详见 R3-001。应同时修实现和兼容模式的用法说明，不能只补一个“无 point 不支持”的参数检查后宣布问题消失。

### F07 的最终裁定：保留协议问题，不推断客户端结果

普通 HTTP 客户端观察到 `end` 只证明 HTTP 传输正常收尾，不证明 Anthropic 消息完整。路由自身已经把该事件序列判断为失败，这一点有源码和受控结果。

本轮确认的范围是：**路由识别消息截断，却没有在下游传输或协议中新增明确失败信号。** 如果真实客户端严格验证 `message_stop`，它可能仍正确报错；如果客户端只凭 HTTP EOF，可能误认完成。后者未验证，不作为已发生影响写入报告。下一步先测支持的真实客户端，再决定统一断连接或发送协议错误；不要伪造成功结束事件。

## 本轮新增正式条目

### R3-001：整套兼容提案审查无法正确登记意见处理

**P2；代码确认，F04 及本轮 G03 受控复现。**

- 位置：`vibe-kit/kit/lib/review-runner.js:405`、`:421`；生产记录入口 `kit/lib/session.js:1958`、`:1959`；支持范围 `claude/skills/ttls-cross-review/SKILL.md:12`、`:38`、`:50`。
- 条件：用户选择人工整套 agent 审查提案，返回完整结果，随后执行 `resolve --change <变更> --mode proposal --decisions <文件>`。
- 结果：仅有提案记录时，固定读取 code 导致“没有可配对的完整审查报告”。如果同时存在代码记录，则可能先配对到错误模式，再因意见数或指纹不一致报其他错误；本轮只复现前者。固定写 `reviewed` 也说明并非只改一处读取就能修完。
- 自我反驳：默认逐点直接请求不受这条影响；但兼容整套模式是明示支持的入口，不能据此驳回。兼容模式的旧多轮逻辑有其他收尾路径，也不能把它说成所有流程绝对无法继续。
- 改法：按实际 mode 查写对应记录，为整套 agent 结果提供不带 point 的明确处理命令；保留逐点逻辑。报告、意见数和模式必须来自同一份记录。
- 验收：只存在提案记录时能够处理；同时有提案和代码记录时只更新提案；不存在对应记录时明确拒绝；逐点直接审查不退化。

### R3-002：路由服务仅凭 version 字段认归属，能停止其他程序

**P1；本轮 G01 受控复现。**

- 位置：`vibe-kit/router/service.js:47` 将任意非空 `version` 视为 ours；`:159` 至 `:168` 在没有本安装 pid/token 时，仍可取得端口 PID 并结束；安装入口 `vibe-kit/install.js:991` 直接调用 `svc.stop()`。
- 条件：本安装配置的回环端口已被另一份安装或另一个提供 `/version` JSON 的本机服务占用；用户安装、重装、重启或运行 stop。
- 结果：该进程可能被当作本安装路由结束。`start():134` 也可能将它直接认成“已经在运行”。卸载入口的 `stopOwnRouter()` 另有 configPath 检查，但安装的 `setupRouter()` 和直接服务命令不经过它。
- 动态证据：harness 假目录里创建普通 HTTP 子进程，随机端口返回 `{"version":"other-app-1"}`；本安装没有 `router.pid`。执行停止前核对 `pidOnPort` 等于本次创建的子进程 PID，随后真实 `service.stop()` 返回 stopped，结束的正是该假服务。父进程等待其 exit。没有操作真实路由。
- 改法：将“像路由”与“属于这份安装”分开。停止前必须核对配置实际路径、进程启动身份或本安装有效 token；归属不足只报告端口占用。start、stop、restart、安装和卸载复用同一归属函数。不能把服务探测失败作为杀端口 PID 的理由。
- 验收：另一假安装、仅有 version 的普通假服务均不被停；自己的正常路由可以优雅退出；自己的卡死进程只有在进程身份可核对时才结束；旧 pid 被重用时不误停。

### R3-003：兼容代理审查没有可靠绑定审查时的输入版本

**P1；本轮 G02、G03 受控复现。两个模式归为一项根因，不重复计数。**

- 位置：`vibe-kit/kit/lib/session.js:1938`、`:1939` 重建审查记录并清除旧指纹；`:1959` 对兼容代码记录不写 fingerprint，提案则在同步时取当前 planHash；`:2057` 只对审查后新打勾任务继续查文件 mtime；`:2067` 至 `:2072`、`:1992` 消费这些记录。
- 代码模式条件：完整兼容审查已经记账，任务早已勾完，之后修改该任务的源码但不重新打勾。
- 代码模式结果：记录没有 fingerprint，`codeReviewed()` 退回任务打勾时间检查；已勾任务的文件再改不会使这条记录失效。G02 中真实工作区指纹改变，但 `codeReviewed=true`、`codeReviewIssue` 为空。
- 提案模式条件：审查针对旧提案完成，结果到达或 sync 补记之前提案已变化。可能来自后台审查期间修改、另一会话编辑，或延迟同步旧会话结果。
- 提案模式结果：同步旧结果时把当前 planHash 写入记录，G03 中提案 hash 已变，但 `proposalReviewed=true`。本轮用构造的合法审查工具调用/结果记录运行真实 `syncReviews`，没有启动真实模型代理；没有声称已走通所有后续门槛。
- 改法：兼容启动时记录目标、模式、输入及必要材料指纹，结果到达时核对；所有消费者使用该指纹。没有启动指纹的旧兼容记录不能在结果同步时补写“当前输入已审”的证明。保留现有代理模式，不恢复已经取消的时间预算。
- 验收：审查运行期间修改、结果到达前修改、记账后修改已勾任务源码、仅修改任务勾选、同名变更重建分别测试。仅勾选进度变化可以继续复用，真实内容变化必须失效。

### R3-004：路由启动失败仍返回安装成功，更新自检无法触发回退

**P1；本轮 G04 受控复现安装器与自检，完整自动更新链由代码确认。**

- 位置：`vibe-kit/install.js:993` 对 start 失败只打印后返回；`:997` 配置页打不开只打印；`:1038` setupRouter 抛错也只打印。`kit/lib/updater.js:236`、`:240` 用退出码判断安装结果；`:247` 至 `:258` 自检只加载库、钩子、行为检查和状态栏；`:295` 至 `:304` 据此登记更新成功。
- 条件：新版本路由本身启动即失败，例如合法 JavaScript 在运行时异常，而套件其余库、钩子和状态栏仍正常。
- 结果：安装器已打印失败，但退出码为 0，更新器自检又不验证路由能否运行，因而可能把不可用的新版本记作成功，跳过已有的回退分支。该路径不需要修改全局权限或真实配置。
- 动态证据：`H.makePackage` 假包中的 `router.js` 注入启动异常，使用 `H.freshHome`、随机回环端口运行真实 `install.js --no-open`；观察到 `installerExit=0`、`routerFailureReported=true`、随后真实 `updater.selfCheck().ok=true`。没有调用远端检查、仓库拉取或完整 `apply()`；“自动更新会如何决策”依据上面的实际代码分支。
- 自我反驳：安装包的语法检查有用，但该样本是语法正确的运行时异常；自动更新自检也确实能发现库和钩子加载失败，缺口仅在路由的运行结果。未安装路由或显式 `--no-router` 的情况不应因此判失败。
- 改法：安装了路由时，将启动失败与配置页验证失败反映到结构化结果和退出码；更新器按安装清单核对本安装路由的归属、实际版本及就绪。运行失败才走既有回退；不能仅检查端口通，避免重现 R3-002。
- 验收：新路由启动异常触发失败并回退上一版；自己的路由恢复后重新核对就绪；被其他程序占端口不能误判成功，也不能误停；明确不安装路由时其他组件仍可独立安装。
