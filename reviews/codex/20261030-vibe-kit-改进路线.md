# 改进路线

本文件给出后续改法，不代表已经修复。优先级以最终综合报告为准。改进应保留现有用户决定：钩子 fail-open、需求与 Apply 分开、人工动作按已有许可执行、审查不按预期时间截断、取消 IDEA 自动接入和套件合并推送、不增加每个请求携带的全局文字。

## 1. 先补“只能发生一次”的保证

确认串、许可消费、服务登记、驱动登记、反馈编号都包含共享状态。现在一部分用 `state-store.update`，另一部分只用临时文件改名。改名能避免半个文件，不能避免丢更新，也不能保证一次性消费。

| 对象 | 需要保证的事实 | 改法 | 验收依据 |
|---|---|---|---|
| 数据库确认串 | 同一串最多一个执行者获得执行资格 | Python 跨进程临界区覆盖读、核对、消费；或每串单独文件原子认领 | 两进程同时消费，恰好一次成功；不同串不互相覆盖 |
| 全机服务登记 | 同时启动的前后端都能找回 | 复用 Node `state-store.update`，在锁内读取最新表、应用本次增删 | 两进程登记两个端口，两个记录都在；并发删除不影响另一项 |
| 驱动登记 | 项目 A、B 的选择和用户删除决定互不覆盖 | jar 可在锁外准备，默认版本及删除标记在同一登记事务中更新 | 不同库、同库不同版本、删除与登记三种并发各有反例 |
| 反馈编号和次数 | 编号唯一，关联稳定，重复次数不丢 | 编号分配与文件创建同一临界区；更新按记录串行 | 多进程新建、同签名递增、失败恢复和旧编号兼容 |

这批改动适合独立提交，先加失败反例，再复用已有状态库。不要为每个模块各写一套 Node 锁。统计失败可按现有设计降级，但一次性资格和破坏性操作不能把“写状态失败”说成“已经成功记住”。

## 2. 外部写操作要区分结果，不只看退出码

数据库提交、发布到 GitLab、安装更新都会跨越两个不同系统。请求返回失败不等于外部系统没发生变化。

建议统一使用下列结果语义，内部字段可以按各模块现有格式实现：

| 结果 | 可以对用户说什么 | 后续动作 |
|---|---|---|
| 明确未执行 | 数据或远端未变，给出拒绝原因 | 修正输入后重新申请或执行 |
| 已执行并确认 | 记录实际影响和版本 | 正常交付 |
| 结果不明 | 已发出，但无法确认是否提交 | 保留执行标识和留痕，先查询核对，禁止自动重试写入 |
| 部分完成 | 指明哪个部分成功、哪个失败 | 按恢复步骤核对，不重复已经完成的部分 |

数据库执行前先保存本机操作记录，包含随机操作标识、目标的脱敏标识、输入指纹和阶段。进入 commit 后抛错应保留“不明”，不能凭一次静默 rollback 就保证“数据没有变”。成功后更新记录；本机结果写不进去也要明确提示已经存在的外部变更。

发布分支与标签应一起成功或一起失败。远端支持时使用原子 push；不支持时明确停下，不能静默退化。内容相同的重跑路径也要核对版本标签，不能仅比较 tree 就结束。以上只改套件发布器；本开发仓库正常推送报告不需要套件发布流程。

### 路由归属与安装成功条件

停止路由必须先证明端口上的进程属于本安装，不能仅凭 `/version` 返回非空字符串认领。结合本安装的 pid 文件、进程身份、启动路径和可核对的配置归属；判定不了就报告端口被占，不结束另一个配置目录或用户程序的进程。保留用户已经决定的服务归属保护。

安装器发现必装路由启动失败或配置页不可用时，应把失败传给调用者；更新自检应核对本次安装承诺的组件。用户明确使用 `--no-router` 的路径单独处理，不能因为增加健康检查而要求所有用户安装路由。路由失败后需要恢复上一版的，连同 HTTP 钩子的可用性一起验证，不能只载入 lib/hooks 和跑状态栏就声明升级成功。

## 3. 为数据库快照建立可证明的并发条件

“同一个事务”和“行数相同”都不足以证明快照与最终修改的是同一批旧值。应先做双连接实验，再选实现，避免直接照搬一种数据库的锁语法到所有厂商。

需要按支持的数据库整理能力表：默认隔离级别、快照读和写读的关系、行锁、DDL 隐式提交、生成主键、影响行数语义、驱动超时和连接断开语义。

可比较三种方式：

1. 在快照时锁住目标行，后续按同一主键集合执行。
2. 将主键和版本／旧值带入写入条件，冲突时回滚并重新给出影响面。
3. 对无法可靠绑定的语句限制自动写入，保留人工确认和明确的能力说明。

验收不能只用一条 UPDATE 成功。至少模拟快照后另一连接改同一行、匹配行集合变但数量不变、删除后重建、回滚失败，以及 undo 遇到新的并发修改。没有厂商环境的组合应列出限制，不用 H2 的通过代替正式驱动结论。

## 4. 清理、迁移和备份采用保守的生命周期

一次性迁移标记应作为跨会话状态保留；它不能和会话缓存一起按天清理。清理扫描达到数量或深度上限、目录不可读时，应返回“不完整”，自动删除据此跳过。最近文件藏在扫描上限后面仍是最近文件。

建议为状态建立一份机器可检查的目录说明：

| 类别 | 例子 | 清理条件 |
|---|---|---|
| 会话缓存 | 提示去重、当前阶段提示 | 会话过期 |
| 跨会话状态 | 审查记录、全机服务、设备标识 | 按条目及业务规则清理 |
| 一次性迁移标记 | 默认值迁移 | 不按会话时间删除 |
| 外部操作留痕 | 数据库操作、结果不明记录 | 由明确留痕政策处理，不能当缓存删 |
| 恢复材料 | 可校验的上一版程序包 | 仅在新的可靠恢复点建立后替换 |

该说明可用于测试，不必进入全局约定。新增状态名时自动检查是否声明生命周期，替代人工记忆“加进 GLOBAL_STATE”。

## 5. 验证证据记录“证明了什么”

目前指纹绑定解决了“旧输入的结果是否还有效”，还需解决“这条命令是不是验证，以及覆盖了什么”。`node --version` 成功只能说明运行时存在，不能作为修改后代码的成功复验。

建议将证据至少分成运行环境查询、编译／静态检查、测试、页面／接口断言、运行配置检查。优先识别项目说明中明确的快检命令，以及场景执行器产生的结构化结果。命令里出现 node、java、curl 不能直接推断测试通过。

每条记录保留仓库、当前输入指纹、环境指纹、命令类别、成功事实和覆盖范围。未知类别仍可记录为“已执行命令”，但不能用于关闭“成立问题已修复并复验”的检查。

首批反例应包含：版本查询、仅打印文字、HTTP 错误但 curl 退出 0、后台未结束、复合命令前段失败后段成功，以及对一个文件执行的检查不能自动扩大到整组验收。不要为了分类完美而阻塞正常命令；应收紧证据用途。

### 兼容审查绑定受审时的输入

默认有限请求执行器已经核对输入指纹，人工整套 agent 兼容方式也必须采用同一契约。启动时保存范围和材料指纹，结果到达时核对；无法还原受审版本的旧结果可以显示为历史记录，但不能为它补上当前代码或提案的哈希并批准新版。

代码审查后再修改已勾任务的源码、提案在结论同步前变化，都应使旧结论失效。整套提案的意见处理按 mode 读取和写回 proposal 记录，不能只要求用户带 point；兼容整套方式并没有逐点记录。保留原有人工兼容能力，不因此恢复默认开子代理。

## 6. 路由的请求期限和协议完成独立核对

候选模型每次获得完整首字节等待，多个候选累计就会超过客户端可等待时间。每个请求应记录开始时间和绝对截止时间，切换、限流等待和下一次首字节等待共用剩余时间；剩余时间不足时及时返回可重试的错误。配置页的审查预期耗时仍只做提示和反馈，不能借此恢复已经取消的审查总预算。

流式 HTTP 正常结束与 Anthropic 消息完整结束是两个事实。路由已经识别缺少 `message_stop` 并记失败，后续要验证 Claude Code 使用的客户端是否可靠拒绝这种半截消息。确认后再决定由路由断连接、发送错误事件还是保留现有客户端处理，不能仅凭普通 HTTP 客户端的 EOF 就声称真实会话误判成功。

另外建议为请求体、缓冲队列、并发请求和慢消费者设定明确上限，并使用流的背压。上限应来自本机内存和真实请求分布，配置保存失败与正在转发的请求隔离。这个方向属于性能改进，当前没有做内存压力测试，不作为已复现故障计数。

## 7. 让服务重用反映当前文件集合

服务是否陈旧不能只看仍然存在的文件 mtime。删除源码、重命名、切换分支、替换构建产物都可能改变服务行为。

先修删除漏报，再比较是否需要保存启动时的输入摘要。对于非热更新服务，使用项目范围内的 Git 变更状态及文件集合；对于热更新服务，保留现有策略，但实际页面或接口断言仍是独立证据。不能因为端口通了就说功能正确，也不能因为服务旧就结束用户自己启动的进程。

全机服务登记丢失时，本地记录仍可兜底。恢复路径应显示“从本地记录找回”或“登记不完整”，避免把无法判定的服务说成用户自己起的或套件自己起的。

## 8. 一份字段定义服务多个入口

Maven 的 `home` 与 JDK 的 `path` 已经产生真实错配。默认开关、清洗、配置页、安装器、状态栏和文档也有同一字段的多份解释。

可先引入只读解析函数，统一产生 JDK、Maven、Tomcat 的标准工具路径，再逐步减少镜像。默认值继续以 `session.js` 的 `DEFAULT_CONFIG` 为准，`kit-api.js` 的镜像由生成或一致性检查维持，不另外建立第三套默认值。

配置字段的类型、允许值、迁移别名和说明适合由纯数据描述；页面可以消费它，文档可以从中生成短表。复杂业务判断仍保留在策略代码，不把所有逻辑塞进一个巨大的配置框架。

## 9. 文档清理要删除旧指令，不能只追加新段落

审查技能同文既写累计 300 秒预算，又写不限时；README 和架构既写自动拉代码，又写取消。模型会同时接收到两种要求。应保留一个当前行为入口，历史决定注明被谁替代，当前技能只留下现行指令。

建议维护少量行为契约检查：自动拉代码已取消、审查秒数只是预期时间、IDEA 不再自动接入、没有套件合并推送、任务只列实现、人工操作已有授权不重复询问。检查行为含义，不要求所有页面复制同一句文案，也不向全局约定继续堆说明。

## 10. 回归从日期文件补向故障契约

已有历史反馈用例应保留，它们记录了真实使用方式。新增测试应能从业务契约找到，而不必先知道某次反馈发生在哪一天。

| 契约 | 最小反例 | 运行环境 |
|---|---|---|
| 一次性消费 | 两个真实进程使用同一 token | 假 HOME、文件系统 |
| 不丢更新 | 两个写者读取同一旧登记表 | 假 KIT、受控屏障 |
| 结果不明不能报回滚 | commit 已发生但确认丢失 | 假 JDBC 驱动，再到隔离数据库 |
| 发布完整 | 分支成功、标签拒绝 | 临时裸仓库 |
| 清理必须有完整证据 | 最新文件位于扫描上限外 | 假项目 |
| 证据不扩大 | 版本查询成功 | 假项目、真实 after-tool 入口 |
| 升级不重置选择 | 迁移标记经过会话清理后再升级 | 假安装包、假 HOME |
| 支持运行时真实可用 | 最低 Node 版本加载随包依赖 | 独立旧版本运行时，不替换系统 Node |

修复时先让反例在本次基线上失败，再验证新版。发布时按仓库规程跑完整矩阵；日常修改仍只跑受影响套，避免把本次审核的广泛核验变成以后每次小改都要执行的额外流程。

## 11. 离线依赖和交付包可追溯

保留依赖离线随包的方案，补充每版依赖名称、版本、引擎要求、来源及哈希清单。安装器应明确区分核心 Node、Playwright 和 OpenSpec 的最低版本与降级行为；当前核心允许 Node 18，但随包 Playwright 明确要求 20，不能只提示 OpenSpec 降级。

Java 源码与随包 class 可以在构建时写来源哈希；重新检出后的 mtime 不能证明二者内容一致。打包前核对输出确实来自当前源码。第三方漏洞核对需要独立记录检查时间和来源；本次没有检查在线漏洞库，因此不下“依赖安全”或“依赖已过时”的结论。

## 12. 记录少量能帮助定位的指标

建议本机记录：钩子在哪个阶段降级、状态锁争用、审查尝试／回复／覆盖、取消发生在哪一步、路由排队／限流等待／首字节／流持续时间、发布哪个引用已核对、恢复包是否可用。保留现有脱敏原则，不记录提示词、源码、业务数据、口令和模型 key。

上报仍只按用户既定政策发送次数和版本。诊断详情留在本机。新增指标应回答一个具体排查问题；不能为了“可观测”再造一套后台服务。

## 实施分批建议

| 批次 | 目标 | 相对工作量 | 交付条件 |
|---|---|---|---|
| A | 确认串原子消费、提交结果分类、发布完整性、清理截断保护 | 中，数据库提交需专门环境 | 对应反例和失败恢复均验证；不自动发布 |
| B | 迁移标记、Maven 字段、删除源码陈旧检查、错误验证证据、提案 resolve | 小到中 | 单入口修复覆盖同类入口；文档同步 |
| C | 全机登记并发、反馈编号、Redis TTL、路由期限 | 中 | 多进程／假服务契约验证，不只跑顺序调用 |
| D | 数据库快照一致性、运行时矩阵、依赖与 class 来源 | 中到大，依赖正式环境 | 明确支持组合与限制；缺环境的项不声称解决 |
| E | 字段共用、文档行为检查、测试索引和本机诊断 | 分步做 | 减少重复定义和定位成本，不增加日常确认或全局提示负担 |

工作量是审核后的粗分，不是排期承诺。应按最终三轮裁定结果调整；一次提交只承载一个可核对的问题或独立功能，相关反例随实现提交，发版生成物单独提交。
