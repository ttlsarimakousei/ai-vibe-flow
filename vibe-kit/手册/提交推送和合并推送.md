# 提交、推送和合并推送

开工前拉代码、提交时查什么、什么时候自动提交、push 怎么确认。回到[用户手册](../README.md)。

## 开工前拉代码（默认开）

同事推了新代码，这边照着旧的分析、写，到提交时才发现对不上。所以会话进 OpenSpec 流程的那一句话先拉一次。

| 你说的 | 拉不拉 |
|---|---|
| 提了一条需求（接下来要探索现有代码） | 拉 |
| 敲了 `/opsx:…`（explore、propose、apply、archive） | 拉 |
| 已经在流程里，说"继续""好""不要停"，或者中间插了一句问话再说"继续" | 不拉，做到一半不换底下的代码 |
| 问问题、让它检索、跑别的技能 | 不拉 |

- 同一个仓库 2 小时里只拉一次（拉没拉成都算）。
- 拉哪些：会话启动目录所在的仓库；启动目录是壳子的，加上它下面的子项目仓库，一次最多 12 个，多出来的先拉最久没拉过的。不是壳子的上级目录不带下面的仓库。
- 只快进：`git fetch` 再 `git merge --ff-only` 跟踪的远端分支。不做合并提交、不变基、不动你没提交的改动（配了 `merge.autoStash` 也不藏改动）。

| 情况 | 结果 |
|---|---|
| 远端有新提交、本地没有没推的 | 拉下来，告诉 Claude 读过的代码可能变了 |
| 本来就是最新的 | 不说 |
| 本地有没推的提交、远端也有新的（分叉了）；没提交的改动和远端改的是同一些文件 | 不拉，告诉 Claude 要合并先问你。自动模式生效时照本地的做，写进收工报告"留给你做的" |
| 连不上、没权限、连远端 15 秒没下完 | 没拉成，照本地的做；自动模式生效时写进报告 |
| 合并要很久（文件多、杀毒软件逐个扫） | 等它做完，不中途结束，免得留下 `.git/index.lock` 和改了一半的工作区 |
| 合完了，仓库自己的 post-merge 钩子还在跑 | 等 20 秒，还没完就结束钩子；代码照样算拉到了 |

- git 一律不交互：不弹登录框、不问口令。用的是这台电脑上 git 自己的登录（SSH 密钥或凭据管理器），和套件的 GitLab 令牌无关。
- 一般多等一两秒。安装器给"用户开口"这个钩子写明等 300 秒（Claude Code 默认只等 30 秒）。
- 关掉：配置页"拉代码和提交"里的"开工前拉代码"。

## 提交时查什么（开关"提交检查"，默认开）

- 提交信息要写成 `类型: 内容`，例 `feat: 新增修改页面`。
- `git add -A`、`git add .`、`git add -u`、`git commit -a` 一律拦：会把你工作区里原来就有的改动一起带进去。壳子里 add 子项目目录也拦（会提交成 gitlink）。新建的仓库第一次入仓不拦。
- 它这个会话新建的文件还没 `git add` 就提交，点名拦一次：属于这次提交的一起 add，测试用的不提交。用临时 index（`GIT_INDEX_FILE=…`）提交的看那份 index。`for r in a b; do git -C "$r" …` 这类循环按每个取值各查一遍。
- 查这次新加的内容里有没有密码、key、token、私钥：`password=`、`secret`、`api-key`、jdbc 连接串里的密码、`用户:密码@`、私钥、`AKIA…`、`sk-…`、`ghp_…`、中文"密码：…"。写成占位符的（`${DB_PASSWORD}`、`<密码>`、`******`）不算；仓库里原来就有、这次没动的不查。查到了弹框，写清哪个文件第几行（值遮掉），你点同意才提交。自动模式生效时提交放行，记进收工报告。

## 什么时候提交

| 场合 | 怎么提交 |
|---|---|
| 需求文档 | proposal、specs、design、tasks 写、审、改到定稿，整套提交一次。人工模式先交代定稿内容，问你提不提交。提交不等于开工许可 |
| Apply 自动生效时的实施 | 按配置页"自动提交档位"：每完成一件事（默认）、一个阶段（tasks.md 里同一个大编号 1.x 全勾上）、一个变更整个做完、我说了才提交。审查修复全部收尾后提交一次，不逐轮提交 |
| 人工模式的实施 | 按进度提醒你提交；你说提交才提交。提醒本身不算许可 |
| 不走 OpenSpec 的改动（修 bug、改配置、改文案） | 默认先交代改了什么、怎么验的，问你，你说提交才提交，没点头的 `git commit` 会被拦下。配置页"不走 OpenSpec 的改动"可以改成直接提交 |
| 经验规则文件 | 单独一笔 `docs: 更新经验规则` |

- 自动提交只 add 它这一轮改的和新建的文件，工作区里原来就有的改动先核对归属，不整文件混进去。
- 你选了"先不提交"，同一份改动可以照常收工；之后的新改动再按上面的规矩问。
- 修的是某个 OpenSpec 变更做出来的东西，提交信息末尾加"（源自 <变更名> <任务号>）"。

## push

push 要你当场明确说（"push""推送"）。权限规则按前缀匹配挡不住 `git -C 子项目 push`，所以套件自己认：写在 if、try、循环、子 shell、函数、脚本文件里的 push 也认得出。否定、询问、后台通知、旧的确认都不算授权。自动模式也一样。

- **只有一笔、目标明确、工作区干净**：你说了就普通推送。空远端的第一次推送、推到远端的新分支也行。
- **多笔**：先给你看合并预览，你另说一次才执行：

1. 它运行 `node "%USERPROFILE%\.claude\vibe-kit\tools\merge-push.js" plan --dir <仓库>`，把原来的提交、建议的分组、合并后的标题、提交数、分支和远端完整列给你看。
2. 你看过之后另说一次"确认推送"，或者在提问框里选"照计划推送"。第一次说的 push 不能当成确认。以前的口令"合并push"也是先出预览。
3. 它运行 `merge-push.js apply --dir <仓库> --plan <文件> --confirmed <完整计划编号> --push`。

归组和安全的规矩：

- 按具体的 OpenSpec 任务号（提交信息里的"源自 add-order 1.1"）或独立修复的"事件: <编号>"归组，不按整个变更或标题相似合并。需求定稿、验收、归档这几个节点保留各自的提交；交错的提交文件不相交才调到一起。没有明确归属的原样保留。
- 含 merge 提交、签名或版本标签的，整段保留原历史，普通推送。版本标签不会自动推。
- 有没提交的改动、远端分叉了、拉取和推送地址不同，都停下；不 stash、不 force。合并后最终文件和原来完全一致才换分支，旧提交留备份。
- 计划放在项目的 `.vibe/tmp/merge-push/`，30 分钟有效；本地提交、目标、分支或远端变了要重新预览、重新确认。失败的保留本地结果和备份，重新预览再试。
- 套件版本升级后，旧的推送预览要重新生成、重新确认。
- 内网发布安装包（`publish.js`）和 push 一样要你点头，push 的授权不能拿来发布。
