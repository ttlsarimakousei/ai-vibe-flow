# 提交、推送和合并推送

提交时查什么、什么时候提交、push 怎么确认。回到[用户手册](../README.md)。

开工前不再自动拉代码（2026-10-17 起）：要拉最新代码你自己拉。

## 提交时查什么（开关"提交检查"，默认开）

- 提交信息要写成 `类型: 内容`，例 `feat: 新增修改页面`。
- `git add -A`、`git add .`、`git add -u`、`git commit -a` 一律拦：会把你工作区里原来就有的改动一起带进去。壳子里 add 子项目目录也拦（会提交成 gitlink）。新建的仓库第一次入仓不拦。
- 它这个会话新建的文件还没 `git add` 就提交，点名拦一次：属于这次提交的一起 add，测试用的不提交。用临时 index（`GIT_INDEX_FILE=…`）提交的看那份 index。`for r in a b; do git -C "$r" …` 这类循环按每个取值各查一遍。
- 不查提交内容里像密码的东西（2026-10-17 起）。套件自己的令牌文件（GitLab 令牌、模型的 key）一直不许提交，不受这个开关管。

## 什么时候提交（配置页"提交"卡片里的"提交方式"）

人工和自动模式都用这一个设置，不走 OpenSpec 的改动也按它。到了提交时机：

| 提交方式 | 做什么 |
|---|---|
| 关（默认） | 什么都不做，不问也不提交；你说"提交"它才提交 |
| 询问 | 交代改了什么、怎么验的，用提问框问你"提交 / 还要改"，你选了提交才提交。Apply 自动时你不在，先不提交，把要提交的列进全自动报告，等你回来说 |
| 自动 | 直接提交，一件事一笔 |

提交时机参照 Claude 桌面版，"做完一件完整的事"才算，做到一半不算：

| 场合 | 什么时候算做完一件事 |
|---|---|
| 需求文档 | proposal、specs、design、tasks 四份都写完、定稿（需求自动时四份都审过）。提交不等于开工许可 |
| OpenSpec 实施 | 上次提交之后又勾完了一项任务；审查修复全部收尾。审查还没收尾不提交，不逐轮提交 |
| 不走 OpenSpec 的改动（修 bug、改配置、改文案） | 改完、跑过快检 |
| 经验规则文件 | 单独一笔 `docs: 更新经验规则`，询问、自动都不再问 |

- 只 add 它这一轮改的和新建的文件，工作区里原来就有的改动先核对归属，不整文件混进去。
- 你选了"先不提交"，同一份改动可以照常收工；之后的新改动再按上面的规矩问。
- 修的是某个 OpenSpec 变更做出来的东西，提交信息末尾加"（源自 <变更名> <任务号>）"。

## push

push 要你当场明确说。权限规则按前缀匹配挡不住 `git -C 子项目 push`，所以套件自己认：写在 if、try、循环、子 shell、函数、脚本文件里的 push 也认得出。否定、询问、后台通知、旧的确认都不算授权。自动模式也一样。2026-10-25 起按你怎么说来：

| 你说 | 它怎么做 |
|---|---|
| "推送""push" | 直接 `git push`，几笔提交都一样，不给推送计划、不再问；壳子里几个子项目都有没推的，各推一次 |
| "合并推送""合并 push" | 先给你看推送计划（下面 1—3），你确认后按计划推 |
| "合并成1条推送""合并成一条 push" | 不问，把这个分支所有没推的提交合成一条直接推：`merge-push.js squash --dir <仓库> --push`。文件内容和原来完全一样，原来每条的说明都写进新提交，旧提交留备份；远端还没有这个分支（第一次推）的不合成，先普通推送 |

强推（`--force`）、删远端分支、推到不是当前分支跟踪的那个远端分支，照旧弹确认框问你。

合并推送的计划：

1. 它运行 `node "%USERPROFILE%\.claude\vibe-kit\tools\merge-push.js" plan --dir <仓库>`，把原来的提交、建议的分组、合并后的标题、提交数、分支和远端完整列给你看。
2. 你看过之后另说一次"确认推送"，或者在提问框里选"照计划推送"。第一次说的"合并推送"不能当成确认。给你看过计划、还没推的，它要照计划推，不能改成直接 `git push`。
3. 它运行 `merge-push.js apply --dir <仓库> --plan <文件> --confirmed <完整计划编号> --push`。

归组和安全的规矩：

- 按具体的 OpenSpec 任务号（提交信息里的"源自 add-order 1.1"）或独立修复的"事件: <编号>"归组，不按整个变更或标题相似合并。需求定稿、验收、归档这几个节点保留各自的提交；交错的提交文件不相交才调到一起。没有明确归属的原样保留。
- 含 merge 提交、签名或版本标签的，整段保留原历史，普通推送。版本标签不会自动推。
- 有没提交的改动、远端分叉了、拉取和推送地址不同，都停下；不 stash、不 force。合并后最终文件和原来完全一致才换分支，旧提交留备份。
- 计划放在项目的 `.vibe/tmp/merge-push/`，30 分钟有效；本地提交、目标、分支或远端变了要重新预览、重新确认。失败的保留本地结果和备份，重新预览再试。
- 套件版本升级后，旧的推送预览要重新生成、重新确认。
- 内网发布安装包（`publish.js`）和 push 一样要你点头，push 的授权不能拿来发布。
