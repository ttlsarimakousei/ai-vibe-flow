## OpenSpec

OpenSpec 管需求、设计和任务；vibe-kit 管本机检查与执行安排。需求文档只有这一套，不另建一份平行清单。

- 探索结果边谈边写进 `openspec/explore/<大任务>.md`（`plan.js new` 建），`openspec/plan.md` 只当索引。含糊的目标、范围、业务规则和验收标准先用 Ask 沟通，不猜。探索完才写需求，每个 change 开始时才建变更、写四份文档，写之前读探索记录的公共几节、这个 change 那一节和前面 change 的落地偏差。
- openspec 命令照常写，套件换成自带的 OpenSpec 执行；项目还没有 openspec/ 时套件在项目根初始化，不用自己 init。Node 版本不够时用项目自己装的；指令不支持时核对 openspec --version 和 --help。
- 逐个生成 proposal → specs → design → tasks，不一次性生成全部。按已安装 CLI 的 status 和 instructions 读取单个产物说明；低版本不能用该指令时提示升级。
- 自动模式（会话里用户敲 /vk-auto 开的）：探索记录的"还没定的"清空、"范围"写好才开始自动；没到这一步即使开关开着也继续沟通。
- 人工模式 proposal、specs、design 写完一份，提醒用户看一看，用 Ask 引导写下一份，不问审查；tasks 写完问要不要审整套。这个 change 的任务全部做完，用一个提问框分两个问题问是否审查、是否自测；这一轮用户已经要求过的，改完的复审、复验直接做，没要求过的先问；编译、类型检查、静态检查不算自测。用户已经明确要求的直接执行。选择放弃就继续，不留未审查、未测试或待办，也不宣称通过。
- 自动模式核验、修改、复验：第一轮全量，后面只审修改点，没有 P1、P2 就算过，照结果里的 next 做。需求文档写到 tasks 审一次整套（--point tasks），中间不审、不停；这个 change 的任务全部做完审一次（--point change），组之间不审。{{REVIEW_MODE}}
- 实现任务做完就打勾，提交按提交方式。打勾不查验法，一个 change 做完只审修，不自测；一个大任务的自测和核验放到最后：所有 change 的任务做完后全面自测（所有 design 的验收用例和探索记录的整体用例），`workflow.js selftest --task <大任务> --results <文件>` 登记，再交给用户人工核验。审查、自测执行、服务起停等本机安排不塞进 tasks，真实要求交付的测试代码可以列为任务。
- 同一套文档定稿后按提交方式提交一次：自动才提交，关、询问在全自动下不提交也不问；开着自动且没限定只写需求时，定稿后直接 apply。人工写完 tasks 时定稿和开工一起问（"审一下 / 定稿并开工 / 只定稿 / 我要改"），选过的不再另问开工；其他情况用提问框问能不能开工（"开工 / 还要改 / 先不做"）。归档等用户明确要求，不能用提交许可代替。
- 多个变更按 openspec/plan.md 表的顺序做：做完一个先在探索记录"落地偏差"写下和计划不一样的地方，开着自动直接接下一个，没开自动用提问框问。表外的新需求用户说要加才加（plan.md 加一行、探索记录加一节）。探索完之后，需求、apply、自测都不加探索记录里没有的东西（用户没说的新场景、新校验、新按钮），想到的用 `workflow.js suggest --task <大任务> --text <建议>` 记下，人工核验时列给用户；做法上的取舍自己定。归档后的问题先用 tools/trace.js 溯源，历史归档只读。归档前先跑 `workflow.js archive-check --task <大任务>`，按表的顺序归档。

### 产物与验收

- proposal 每个能力对应 specs/<能力>/spec.md；规格增量使用 ADDED/MODIFIED/REMOVED Requirements，Requirement 下用 Scenario、WHEN、THEN 写可核对行为。正常、异常、空数据、权限边界按实际需求覆盖，不适用的说明原因。
- 验收用例写在 design.md 的"## 验收用例"一节，需求和设计阶段写完给用户看：每条写对应场景、前置数据和环境、步骤、预期、谁来测（Claude 自动跑的写清命令、接口或页面场景；要人看的写"人工"）、对应第几组任务。自测和用户验收都照它做，结束后把执行结果交给用户。{{SEE_PAGE_SPEC}}
- design 的 Context 写实际读过的路径，新文件注明“新建”。复杂交互、状态或依赖用图辅助，产物不设 250 行上限。
- 需求文档一份一份写：proposal → specs → design → tasks，每份用 `openspec instructions <产物> --change <名字>` 拿模板，用 `/opsx:propose` 也一样。人工模式写完一份停下提醒用户看一看，用户说写下一份再写；自动模式接着写到 tasks。
- tasks 只写要做的实现任务，按依赖分组。一项形如：- [ ] 1.1 订单查询为空时返回空列表：src/order.js。不写"验："，不写测试、审查、用户验收任务。
- 不留模板占位或“待定、视情况、开发阶段再”。不确定的业务问题先沟通；本次不做的写清范围和原因。

### 修订与需求回归

任何阶段发现变更，核对需求、规格、设计、任务、代码、验收用例和流程图的受影响部分，同步修改，不能只改后面一环。改动处加简短批注，例如“修订 2026-10-14：空列表仍返回 200，关联用例 AC-03”。在 revisions.md 追加起因、改了、关联影响及不改的理由。修订会使相关旧审查与验证结果失效，按所属模式决定复验。全面自测、人工核验发现问题也一样。

大任务里回改前面的 change：它没归档就直接改它的文档，不在后面的 change 里写 MODIFIED；同步探索记录的"定了的""跨 change 约定"；补的任务按表的顺序先做完，再回原来的 change；revisions.md 的"影响"写影响哪些 change（`影响 change：c2-api` 或 `影响 change：无`），列出来的审修改点，改过代码的重跑受影响 change 的用例和整体用例。

团队产物只写业务事实、决定和交付内容；套件命令、钩子拦截、请求预算、审查批次失败和诊断留在 .vibe/ 或套件问题反馈。流程或机制改变时同步对应流程图和说明。归档要同步主规格，不使用 --skip-specs；用户已经说了归档，OpenSpec 问要不要同步时直接选同步，不再问用户。
