## OpenSpec

公司要求用 OpenSpec 开发。"做什么、做到哪一步"都归它管，不要另外发明需求文档、任务清单或者状态文件。

- **要走提案的**：新功能、改变现有行为、改接口、改表结构。先 /opsx:propose，再 /opsx:apply，验收后 /opsx:archive。
- **不用提案的**：修 bug（把行为恢复成规格里写的样子）、改文案和样式、改配置、升级依赖、补测试。直接改，改完验证。拿不准算哪一种，问我一句。
- **一个模块一个提案**。我给你整份 PRD、整套原型的时候，先列出模块清单和建议的先后顺序给我看，我点了哪个就只为那一个出提案；其余材料只在和当前模块有关时才读。
- **拆成几个变更的，清单写进 `openspec/plan.md`**（`| 模块 | 变更名 | 状态 | 说明 |`，按先后排；状态列钩子自动刷新，做下一个之前先读它；没有表的用 `node "$HOME/.claude/vibe-kit/tools/plan.js"` 生成骨架）；中途加的功能加一行，写清起因。
- **openspec 在哪**：当前目录有就用它；没有就用所在 git 仓库根目录的（在壳子的子项目里干活，提案、任务写在壳子那一层，代码到子项目里改）；都没有才在仓库根目录 `openspec init`。不要到仓库外面的上级目录去找、去建。
- apply 时每做完一项任务，先跑这项任务写的验法（"验：…"），过了才把 `- [ ]` 打成 `- [x]`；验证不过就不打勾，说明卡在哪。验法里有现在验不了的部分，把那一部分写成"……本次不做（原因）"，能验的照样跑。
- 要我动手才能做的任务（要账号密码、没有技能能做的操作）：在任务后面加上"（留给用户：原因）"，不打勾，先做别的。改库、改 redis 里的数据有技能，照技能说的先问我，我同意了你来做。
- 规格增量（`openspec/changes/<名字>/specs/<能力>/spec.md`）里的需求要放在 `## ADDED Requirements`、`## MODIFIED Requirements`、`## REMOVED Requirements` 这几种标题下面，不然归档时 OpenSpec 认不出来（报 no deltas found）。归档不要加 `--skip-specs`；加了、或者手工挪目录归档的，要自己把需求并进 `openspec/specs/<能力>/spec.md`。

- **所有产出都要审**，换一个模型审：提案写好、apply 之前审提案（/ttls-cross-review 的提案模式）；最后一项任务打勾之后、归档之前审代码（代码模式，后端前端都在内）。交给 ttls-reviewer 的提示，第一行固定写"模式：提案"或"模式：代码"（复审写"模式：复审提案""模式：复审代码"），并写上变更名。{{REVIEW_MODE}} 没审过代码、没做完的变更不让归档。

### 先探索再提案

- 我提出需求时（哪怕只有一句话），不要直接写提案，也不要直接改代码。先用 /opsx:explore 的方式在项目里探索：读会碰到的代码、表结构（有查库的技能就用它）、接口、配置。把现状写下来给我看：读了什么、发现什么、和需求对不上的地方、还不知道什么；要产出代码之外的文件（DDL 脚本、说明文档）的，放哪也在这时一起问清。我确认了范围再 /opsx:propose。
- 没读过的东西不能出现在提案和设计里；探索和写提案不在同一轮（我自己敲 /opsx:propose 的除外）；设计 Context 里说读过的文件，会话里得真的读过。

### 提案的门槛（写进产物时钩子会查，不过就拦回来并给出写法）

- 四个产物里不许有"待定、后续完善、开发阶段再、视情况、暂不考虑、TBD"这类话。拿不准的写成决策项：未定什么、默认按哪种做、理由（同一行写明"默认按…做"就算）；我不接受会改。本次不做的写成"本次不做：X（原因）"。模板的占位注释不能留着。
- proposal.md 的每个能力都要有 specs/<能力>/spec.md；specs 每条 Requirement 至少一个 `#### Scenario`，WHEN 写具体的输入和状态，THEN 写能核对的结果，正常、异常、空数据、无权限各写一条（不适用的写明为什么）；design.md 的 Context 列出探索时读过的真实路径，提到的路径要真实存在（要新建的写明"新建"）。
- tasks.md 一项任务 = 一次提交的量：`- [ ] 2.1 <做什么>：<文件路径>；验：{{PAGE_VERIFY}}`。不许有"联调、完善、收尾、优化细节"这种任务。按依赖排序。
- 每个产物控制在 250 行以内。超了说明拆得不够细，回到"一个模块一个提案"。

### 链路要对齐，改了要有记录

需求 → 探索 → 提案 → 规格 → 设计 → 任务 → 代码，是一条链。后面任何一环发现问题（我要求改、需求变了、代码里的事实和设计假设不符、你觉得原方案不好、审查提出的），改那一环的同时，上面每一环都看一遍要不要跟着改，颗粒度保持一致；不改的要说得出理由。每次改都在 `openspec/changes/<名字>/revisions.md` 末尾追加一条：标题 `## <日期 时间> · <在哪一步发现的>`，下面三行"起因、改了、上层"（例：`- 起因：客观。order 表没有 status 字段，设计里假设有`）。起因写这六种之一再加一句具体的：主观、客观、用户要求、需求变化、审查（审查意见，成立的改了、不成立的写明理由）、自动模式决定。apply 中途发现问题：先停下改产物和记录，再继续做任务；不要一边写代码一边默默偏离设计。

### 归档之后发现的问题（人工测试、用户反馈）

先用 `node "$HOME/.claude/vibe-kit/tools/trace.js" <出问题的文件>[:行号]` 溯源，再按它给的做法分类处理；归档目录不要改，那是历史记录。
