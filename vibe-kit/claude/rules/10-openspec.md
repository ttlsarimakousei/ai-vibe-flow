## OpenSpec

OpenSpec 管需求、设计和任务；vibe-kit 管本机检查与执行安排。需求文档只有这一套，不另建一份平行清单。

- 先根据对话探索代码，判断是直接修改还是需要变更。恢复既定行为、文案、配置等简单修改可以直接做；新增业务行为、接口或复杂改动用 OpenSpec。含糊的目标、范围、业务规则和验收标准先用 Ask 沟通，不猜。
- 使用当前项目或所在壳子的 openspec。没有才在项目根目录初始化。套件不内置、不安装、不升级 OpenSpec；指令不支持时核对 openspec --version 和 --help，提示使用者按原安装方式自行升级。
- 逐个生成 proposal → specs → design → tasks，当前产物审修结束再继续；不用一次性生成全部的方式跳过中间审查。按已安装 CLI 的 status 和 instructions 读取单个产物说明；低版本不能用该指令时提示升级。
- 需求自动先要有描述、读过实际代码并沟通未决问题；用本轮提醒里的 workflow.js qualify 登记评估，unresolved 为空才自动。没有这些条件，即使开关开着也继续沟通。
- 人工模式每个产物完成后，用 Ask 问是否审查；代码完成后分别问是否审查、是否自测，复验另问。用户已经明确要求的直接执行。选择放弃就继续，不留未审查、未测试或待办，也不宣称通过。
- 自动模式逐点核验、修改、复验。需求的每个产物与 Apply 的每整组 1.x 分别计数，不共用次数；整组做完并审修后再进入下一组。{{REVIEW_MODE}}
- 实现任务做完就打勾，提交按档位。人工放弃自测不阻止完成任务；自动阶段按验法验证后打勾。审查、自测执行、服务起停等本机安排不塞进 tasks，真实要求交付的测试代码可以列为任务。
- 同一套文档定稿后提交一次；两种自动都开且未限定只写需求时，定稿提交后自动 apply。其他情况用 Ask 给出“执行 apply / 继续修改 / 暂不执行”。归档等用户明确要求，不能用提交许可代替。
- 多个变更的顺序写 openspec/plan.md，不自行启动下一个变更。归档后的问题先用 tools/trace.js 溯源，历史归档只读。

### 产物与验收

- proposal 每个能力对应 specs/<能力>/spec.md；规格增量使用 ADDED/MODIFIED/REMOVED Requirements，Requirement 下用 Scenario、WHEN、THEN 写可核对行为。正常、异常、空数据、权限边界按实际需求覆盖，不适用的说明原因。
- 需求阶段准备验收用例，设计阶段补齐环境、数据、步骤与预期。自己的自测围绕这些用例，结束后把测试清单、用例和实际执行结果交给用户测试。{{SEE_PAGE_SPEC}}
- design 的 Context 写实际读过的路径，新文件注明“新建”。复杂交互、状态或依赖用图辅助，产物不设 250 行上限。
- tasks 只列项目交付内容，按依赖分组。一项形如：- [ ] 1.1 实现已确认行为：src/order.js；验：订单为空时返回空列表。验法描述通过条件，不代表人工模式已批准运行。
- 不留模板占位或“待定、视情况、开发阶段再”。不确定的业务问题先沟通；本次不做的写清范围和原因。

### 修订与需求回归

任何阶段发现变更，核对需求、规格、设计、任务、代码、验收用例和流程图的受影响部分，同步修改，不能只改后面一环。改动处加简短批注，例如“修订 2026-10-14：空列表仍返回 200，关联用例 AC-03”。在 revisions.md 追加起因、改了、关联影响及不改的理由。修订会使相关旧审查与验证结果失效，按所属模式决定复验。

团队产物只写业务事实、决定和交付内容；套件命令、钩子拦截、请求预算、审查批次失败和诊断留在 .vibe/ 或套件问题反馈。流程或机制改变时同步对应流程图和说明。归档要同步主规格，不使用 --skip-specs。
