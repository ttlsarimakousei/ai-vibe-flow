## OpenSpec

OpenSpec 管需求、设计和任务；vibe-kit 管本机检查与执行安排。需求文档只有这一套，不另建一份平行清单。

- 探索结果边谈边写进 `openspec/explore/<大任务>.md`（`plan.js new` 建），`openspec/plan.md` 只当索引。含糊的目标、范围、业务规则和验收标准先用 Ask 沟通，不猜。探索完才写需求，每个 change 开始时才建变更、写四份文档，写之前读探索记录的公共几节、这个 change 那一节和前面 change 的落地偏差。
- openspec 命令照常写，套件换成自带的 OpenSpec 执行；项目还没有 openspec/ 时套件在项目根初始化，不用自己 init。Node 版本不够时用项目自己装的；指令不支持时核对 openspec --version 和 --help。
- 需求阶段没有自动模式，两种模式一样：探索记录"还没定的"清空了才写需求；proposal → specs → design → tasks 一次写完，中间不停、不问审查，每份用 `openspec instructions <产物> --change <名字>` 拿模板（`/opsx:propose` 也一样）。写的时候有任何疑问用提问框问用户；探索记录、用户的话、读过的代码和材料里没有的，不写进需求，不猜。低版本不能用该指令时提示升级。
- 四份写完强制审一次整套（`review.js run --change <名字> --mode proposal --point tasks`），不问用户：审出的 P1、P2 成立的直接改，要用户拿主意的（范围、业务规则、验收标准）用提问框问，不成立的写依据；改完复审，第二轮起只审改过的地方，没有 P1、P2 就算过。中间单份文档不审。
- 需求审过：按提交方式提交一次，再用提问框问怎么实施，选项写"自动实施""实施（每步问我）""先不实施"。每个 change 的需求审完都问，开着自动也问。用户自己说开工、说过停又让接着做的，改代码前也先问一次（"自动实施""实施（每步问我）"；说过停的写"自动接着做""人工接着做"），钩子会提醒。
- 自动实施（用户在提问框里选的）：做完这个 change 的任务 → 审查（`--point change`，组之间不审）→ 改 → 复审，没有 P1、P2 就算过，照结果里的 next 做；还有下一个 change 就接着写它的需求（照上面，审过再问）；最后一个 change 审过之后全面自测 → 改 → 再测再审，全部通过后套件自动关，停下等用户核验，用户核验时报的问题照旧自动改、审、测。审查、自测不问用户。用户插话、提问回应完接着做；用户说"停""别自动了"自动就关，停在那里。{{REVIEW_MODE}}
- 实现任务做完就打勾，提交按提交方式。打勾不查验法，一个 change 做完只审修，不自测；一个大任务的自测和核验放到最后：所有 change 的任务做完后全面自测（所有 design 的验收用例和探索记录的整体用例），`workflow.js selftest --task <大任务> --results <文件>` 登记（不归哪个大任务的 change 用 `--change <名字>`），再交给用户人工核验。审查、自测执行、服务起停等本机安排不塞进 tasks，真实要求交付的测试代码可以列为任务。
- 人工实施（选了"实施（每步问我）"）：这个 change 的任务全部做完，用一个提问框分两个问题问是否审查、是否自测；这一轮用户已经要求过的，改完的复审、复验直接做，没要求过的先问；编译、类型检查、静态检查不算自测。选择放弃就继续，不留未审查、未测试或待办，也不宣称通过。提交按提交方式；归档等用户明确要求，不能用提交许可代替。
- 多个变更按 openspec/plan.md 表的顺序做：做完一个先在探索记录"落地偏差"写下和计划不一样的地方，开着自动直接接下一个，没开自动用提问框问。表外的新需求用户说要加才加（plan.md 加一行、探索记录加一节）；在做的大任务里开的新 change 套件自动补进表，别的情况套件提示时用提问框问用户归到哪，选了再跑 `plan.js link`。探索完之后，需求、apply、自测都不加探索记录里没有的东西（用户没说的新场景、新校验、新按钮），想到的用 `workflow.js suggest --task <大任务> --text <建议>` 记下，人工核验时列给用户；做法上的取舍自己定。归档后的问题先用 tools/trace.js 溯源，历史归档只读。归档前先跑 `workflow.js archive-check --task <大任务>`，按表的顺序归档。

### 产物与验收

- proposal 每个能力对应 specs/<能力>/spec.md；规格增量使用 ADDED/MODIFIED/REMOVED Requirements，Requirement 下用 Scenario、WHEN、THEN 写可核对行为。正常、异常、空数据、权限边界按实际需求覆盖，不适用的说明原因。
- 验收用例写在 design.md 的"## 验收用例"一节，需求和设计阶段写完给用户看：每条写对应场景、前置数据和环境、步骤、预期、谁来测（Claude 自动跑的写清命令、接口或页面场景；要人看的写"人工"）、对应第几组任务。自测和用户验收都照它做，结束后把执行结果交给用户。{{SEE_PAGE_SPEC}}
- design 的 Context 写实际读过的路径，新文件注明“新建”。复杂交互、状态或依赖用图辅助，产物不设 250 行上限。
- 需求文档一次写完：proposal → specs → design → tasks，每份用 `openspec instructions <产物> --change <名字>` 拿模板，写到 tasks 再停。
- tasks 只写要做的实现任务，按依赖分组。一项形如：- [ ] 1.1 订单查询为空时返回空列表：src/order.js。不写"验："，不写测试、审查、用户验收任务。
- 不留模板占位或“待定、视情况、开发阶段再”。不确定的业务问题先沟通；本次不做的写清范围和原因。

### 修订与需求回归

任何阶段发现变更，核对需求、规格、设计、任务、代码、验收用例和流程图的受影响部分，同步修改，不能只改后面一环。改动处加简短批注，例如“修订 2026-10-14：空列表仍返回 200，关联用例 AC-03”。在 revisions.md 追加起因、改了、关联影响及不改的理由。修订会使相关旧审查与验证结果失效，按所属模式决定复验。全面自测、人工核验发现问题也一样。

大任务里回改前面的 change：它没归档就直接改它的文档，不在后面的 change 里写 MODIFIED；同步探索记录的"定了的""跨 change 约定"；当前 change 不变（状态栏写"回改"），补的任务和当前 change 的任务一起做，回改的代码在当前 change 的审查里一起审，不单独重审前面的 change；revisions.md 的"影响"写影响哪些 change（`影响 change：c2-api` 或 `影响 change：无`），列出来的审修改点，改过代码的重跑受影响 change 的用例和整体用例。

团队产物只写业务事实、决定和交付内容；套件命令、钩子拦截、请求预算、审查批次失败和诊断留在 .vibe/ 或套件问题反馈。流程或机制改变时同步对应流程图和说明。归档要同步主规格，不使用 --skip-specs；用户已经说了归档，OpenSpec 问要不要同步时直接选同步，不再问用户。
