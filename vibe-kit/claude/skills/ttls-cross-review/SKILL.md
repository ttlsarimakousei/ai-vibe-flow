# 换个模型审一遍

自己写的东西自己审，容易顺着原来的思路再错一遍。这里把产出交给 `ttls-reviewer` 子代理，它跑在另一个模型上，看不到你的思考过程，只看结果。**所有产出都要过这一道**：提案一次（apply 之前），代码一次（归档之前，前端后端都在内）。钩子会催，没审不让归档。

**交给它的提示，第一行固定写模式，第二行写变更**，钩子靠这两行认出"这个变更的提案 / 代码审过了"：

```
模式：提案            （或：模式：代码 / 模式：复审提案 / 模式：复审代码）
变更：openspec/changes/<名字>/
```

不走提案的小改动审代码，第二行写"变更：无"，再用一两句写清目的。

**等它审完再往下做**：调 Agent 时 `run_in_background` 传 `false`（工具有这个参数的话），下一步（改产物、开工、归档）要看它的结论。已经在后台跑了的，就等它的通知回来（通知会自动接着一轮），这期间不要打勾开工、不要归档，也不要再开一个审查。

## 提案模式（提案写好、apply 之前）

1. **材料**，只给事实：变更目录 `openspec/changes/<名字>/`，让它自己读 proposal、specs、design、tasks、revisions；项目在哪（壳子目录和各子项目目录，或者就是当前目录）；怎么验证（`.vibe/project.md`）。不要附你的解释和"我觉得这里没问题"。
2. **用 Agent 工具调 `ttls-reviewer`**，提示第一行写"模式：提案"，第二行写变更目录，让它按提案模式检查：
   - 想当然：设计里说读过的、说存在的（文件、表、字段、接口），和代码对不对得上；
   - 没说清：含糊词、决策项没写默认怎么做、需求边界没圈；
   - 场景漏了：异常、空数据、无权限、并发、超长输入；
   - 任务：能不能验证、是不是一次提交的量、顺序对不对、有没有任务落不到设计上；
   - 四个产物对不对齐：提案的能力都有规格，规格的场景都有任务覆盖，设计的决策都有任务落地。
3. **逐条核实**它的发现：成立的改产物，在 `revisions.md` 记一条（起因写"审查"）；不成立的也在 `revisions.md` 记一句为什么（起因写"审查"）；拿不准的问用户（全自动模式开着时不问：按影响面最小的处理，记进 `revisions.md`，起因写"自动模式决定"）。
4. **交代结果**：提了几条、改了几条、驳回几条及理由。审过之后再 apply。

## 代码模式（全部任务打勾、归档之前）

1. **圈定范围**：在壳子目录里干活时，代码在下面的各个子项目里，每个子项目是独立的 git 仓库，在壳子这一层跑 git 看不到它们的改动。先确定这次动过哪几个子项目（前端子项目也算，.vue / .js / .ts 的改动一样审），下面的命令**对每个动过的子项目各跑一次**（`git -C <子项目目录> …`）。先跑 `git status --porcelain -uall` 列出全部改动，`??` 开头的是还没纳入 git 的新文件，同样要审。改动内容用 `git diff HEAD` 看。如果这次变更中途提交过（按规范每项任务提交一次，一般都提交过），改用 `git diff <开工前的那个提交>`（不是三个点的写法），这样已提交和未提交的都在里面；开工前是哪个提交用 `git log --oneline` 找，找不准就问用户。超过二十个文件就按模块分几批审。
2. **准备交给它的材料**，只给事实，不给你的解释：
   - 这次要做什么：OpenSpec 变更的 proposal 和规格（`openspec/changes/<名字>/`）；不走提案的小改动，用一两句话写清目的。
   - 改了哪些文件（含 `??` 的新文件）、在哪个仓库目录、基线是哪个提交（让它自己去读，不要贴进提示里）。
   - 项目里怎么验证（`.vibe/project.md` 里的快检命令），让它能自己跑。
   - 页面改动：/ttls-see-page 的场景文件（`.vibe/scenarios/`）和跑出来的结果（`.vibe/out/<名字>/` 里的 RESULT 行、layout 文本），让它对照规格的场景看。
3. **用 Agent 工具调 `ttls-reviewer`**，提示第一行写"模式：代码"，第二行写变更目录，再附上面的材料。不要告诉它"我觉得这里没问题"之类的话。
4. **逐条核实它的发现**，再决定改不改：
   - 能复现或者看代码能确认的：改，改完验证。提交等全部轮次审完（报"问题 0 条"）再一起提交一次（类型 fix）：审查过程不进提交，审一轮提交一轮不行。
   - 它说错了的：不改，在这个变更的 `revisions.md` 记一句为什么（起因写"审查"；不走提案的小改动在交代里说）。
   - 拿不准的：告诉用户，让用户定（全自动模式开着时不等：按影响面最小的处理，记进 `revisions.md`，起因写"自动模式决定"）。
   不要因为审查者这么说了就照改，它也会看错。
5. **交代结果**：它提了几条，确认了几条、改了哪些，驳回了几条及理由。

## 审完之后：经验

审查报的问题套件自动收，**你不用另外记**：报了之后那个文件你确实改过的才收，规则的文字用审查者写的"以后怎么避免"那一句。同样的问题在另一个变更里又被审出来，自动变成项目的规则（`.claude/rules/ttls-lessons-*.md`，读到那类文件时自动带上）。

规则文件更新了，收工钩子会让你提交：照它说的只 `git add` 那个文件，提交信息写 `docs: 更新经验规则`，和修复分开提交。

下面两种情况才自己记：收工钩子催你"各记一条经验"（说明自动收关着）；审查没报、你自己踩到的坑，换个任务还会再犯。各记一句话：

```
node "$HOME/.claude/vibe-kit/tools/lesson.js" add --file <出问题的文件> --when "<什么情况下>" --do "<要怎么做>" --from "<变更名> <任务号>"
```

- 值得记的：这个项目特有的坑（某张表没有某个字段、某个公共方法传空会报错）、这类技术的坑。换一个人、换一个任务来做还会踩进去的。
- 不记的：笔误、漏看一个字段这类一次性的疏忽；约定里已经写着的；"注意边界"这种照着做不了的话。
- 能用脚本查出来的（某种写法不许出现、命名、格式）：加 `--checkable "<怎么查>"`，会转给改套件的人做成检查，不写规则。
- 工具说"已有相近的"：说的是同一件事，就原样再执行一次、末尾加 `--same <编号>`；不是就加 `--new`。
- 工具说升成规则了，就照它给的命令把规则文件提交。规则文件不要直接改。
- 被催了、一条值得记的都没有：交代里说一句"没有需要沉淀的经验"。

## 审几轮

- 默认每个变更提案审一次、代码审一次：子代理要花额度，公司不许随意开。改完之后不再审第二遍；这次修改本身很大的，告诉用户，让用户决定要不要再审。
- 配置页开了"多轮审查"时（全局约定里会写明）：一轮审出问题、你改了之后，再让 `ttls-reviewer` 审**改动点**：提示第一行写"模式：复审提案"或"模式：复审代码"，第二行写变更目录，材料只给它上一轮的问题清单（原文）和这次改过的文件（`git diff` 或整个文件），让它确认每条改对了没有、改动有没有引出新问题。直到它报"结论：问题 0 条"。上一轮的问题核实下来全都不成立、一处都没改的，不用复审：在 `revisions.md` 逐条记下理由就算这一轮处理完了。最多几轮看约定里写的数；轮数用完还有问题，按约定：问用户，或者全自动模式下按原则自己定。收工钩子会按这个规则催，你不用自己数。
- 审查者每次回复最后一行都是"结论：问题 N 条"，那是给钩子看的，不要删。
