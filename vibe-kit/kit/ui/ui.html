vibe-kit

套件开关

这个页面只有这台电脑打得开。

套件说明

vibe-kit 是什么、由哪几块组成、流程怎么走、人工和自动有什么不同，以及哪些规矩是固定的、不做开关。

核心思路

能用本机脚本确定判断的事，不交给模型：编号、阶段、git 状态、编译、起停服务、截图比对、该不该问你。模型只做要理解的事：读需求、写文档和代码、核对审查意见。所以套件钩子多、给模型的提示少。

流程

探索 → [需求 → apply] × N → 全面自测 → 人工核验 → 按顺序归档。中途打断不影响。

探索记录

接着写新 change 时靠它理解之前的讨论。

接回和插话

敲 /vk-resume 列出没归档的 change，用提问框问你切哪个；敲 /vk-resume <变更名> 直接切到这个 change，状态栏跟着它，做完了回到表的顺序；只要没归档都能切，任务都勾完的切过去等你说下一步。任务已经写好的，接回就算开工。在做的大任务里开的新 change 套件自己补进表；流程改版前留下的、全部归档后开的，找出线索用提问框问你，确认了才写。死机前开着自动就接着开。任何时候插话都不退出流程。

发现要改时

做到一半、全面自测、人工核验发现要改，都走这张图。

不自己加

探索完之后，需求、apply、自测都对着探索记录核对。

审查

审查由脚本调 claude -p 做（2026-11-05 起，不开子代理），用你默认的模型（2026-11-09 起不再指定 Sonnet），不带工具，材料和脚本查好的事实一次送完。

人工和自动怎么走

自动模式按会话开：在要自动的会话里敲 /vk-auto（或者说"这个需求自动做"），只对那个会话有效，/vk-auto off 关；没开就是人工模式。中间横跨两栏的是两种模式一样的步骤。

固定的规矩（不做开关）

这些一直生效，配置页上没有开关。

  • 过程文件放 .vibe/tmp：备份（.bak、.orig、"xx - 副本"、backup 目录）、日志、临时脚本不许落在项目里，也不许 git add；放 .vibe/tmp/<事由>/。变更没归档前它的过程文件留着，归档之后套件清掉；多少天没动就清，在"套件开关"里设。
  • 代码之外的产出先问位置：新建 DDL、说明文档、报告这类文件，放哪要你定过；没定过就拦下让它先问你，定了记进项目说明的"产出位置"，以后同类不再问。自动模式下你不在，先放 .vibe/pending/，报告里列出来等你定。
  • 起服务走 devserver：直接敲 mvn spring-boot:run、npm run dev 会被拦下，要经过套件的 devserver.js。同一个服务在跑就不重复起；端口在 30000 到 39999 里挑，离项目配置的端口至少 1000，不和你在 IDE 里跑着的冲突。你在 IDEA、终端里起的服务不动。换了目录、换了名字也认得自己起过的，要重启在原来的端口先停再起；vite 这类会热更新的改了代码不重启。等它起来时每 2 秒看一次日志：日志说起好了再发一次请求确认，日志里报了起不来的错马上停掉、把日志给模型看，不干等。不用 IDEA 的运行配置起（2026-10-28 起）。
  • 推送、发内网要你亲口说：git push、把安装包发到内网 GitLab，都要你当场明确说；同意推送不代表同意发内网。自动模式也不能代替。说"推送"直接推，不出推送计划，也不再弹 Claude Code 的确认框；套件的合并推送工具 2026-10-28 起去掉了，你说"合并推送"的照你说的自己合并再推，不拦。
  • 令牌和口令模型读不到：GitLab 令牌、模型的 key、数据库和 redis 的口令，模型读不到、不进命令行、不进日志，也不许提交。项目里别的口令不再遮。
  • 不接任何 MCP：套件不登记 MCP。你自己接的 MCP 工具只查读令牌，别的不查（终端命令不按 Bash 的规矩查，运行配置不算自测）。
  • 需求文档一份一份写：人工模式上一份你看过、说了写下一份才写下一份；自动模式接着写。四份写完才审。
  • 任务只写实现：tasks.md 不写"验："，不写测试、审查、用户验收任务；测试和验收写在 design.md 的"验收用例"里。打勾不查验法。
  • 人工模式先问：跑测试、起服务、看页面、审查、复验先问你，同一个要求只问一次；这一轮你说过要审、要测的，改完再审、再测不再问（"提交"也一样，分几笔提交不再问）。编译、类型检查、静态检查直接跑。你放弃就继续，不记待办。
  • 开工前不拉代码：要拉最新代码你自己拉。
  • 后台自动探索：进到一个没探索过的项目，套件在后台查工程类型、构建和启动命令、端口、编码，还有开发环境的数据库和 redis 连接，写进项目的 .vibe/。不用模型，不花额度，不占你的对话。只读项目里的文件，不跑构建命令，不连数据库；测试、生产环境的连接不配；你和 Claude 改过的行它不动。命令是照工程结构推出来的，项目说明里标着"没跑过"，Claude 第一次用的时候跑一遍。脚本查不了的（登录账号、代码之外的产出放哪），用到的时候 Claude 会问你。
  • 提案、打勾、归档有门槛：过不去就拦下，提示里写着怎么改；只查这次新加、改过的行，老内容不追究。写提案：没在项目里读过代码不让写；不许写"待定、后续完善、视情况"，拿不准的写成决策项；设计里提到的文件要真的存在。写设计：要有"## 验收用例"一节。写任务：只写要做的实现，每项写改哪个文件。打勾：还没说开工不能打勾；自动模式时后面一组要等前面一组做完、审修过。改产物：要在 revisions.md 记原因。归档：任务全部打勾，你说了归档才归档；人工模式不要求先审查，提示照实说审过没有；归档之后主规格里没有这个变更的需求会提醒。

大需求怎么写

  • 文档写多长都行，套件不限行数；审查材料放不下时分批送，不截断。
  • 按能力拆规格：一个能力一份 specs/<能力>/spec.md，不要全堆在一份里。
  • 关系复杂的地方画图：状态流转、调用链、数据流在 design.md 里用 mermaid 图。
  • 真的太大就拆成几个变更：每个能单独开工、单独验收的部分各建一个。

自带的 OpenSpec

安装包里带一份 OpenSpec（打包时的最新版），/opsx:* 命令装成用户级，所有项目都能用；模型敲 openspec 命令时，套件改成调用自带的这份，项目没初始化的第一次用时自动建 openspec/。写出来的变更，同事用自己的 OpenSpec 1.2 也能看、校验、归档。

  • Node 低于它要求的版本（1.14.3 要 20.19）时，不用自带的，照旧用你自己装的、项目里初始化好的 OpenSpec。
  • 不往外发使用统计（OPENSPEC_TELEMETRY=0）。
  • 装的命令：/opsx:explore、/opsx:propose、/opsx:new、/opsx:continue、/opsx:apply、/opsx:verify、/opsx:archive。一份一份写用 /opsx:new 加 /opsx:continue，用 /opsx:propose 也一样会一份一份停下。

    需求阶段准备验收用例，设计阶段补输入、环境、步骤和预期。文档写多长都行，复杂的关系画图。只要求写需求时不会自行开工。没开自动的会话，审查、自测和复验都先用提问框问你；放弃就继续，不记待办。
    
    
    

    
    
      
    提交
    
      
    只提交，不自己 push。push 要你当场明确说：说"推送"直接推，不出推送计划；说"合并推送"的照你说的自己合并再推（套件的合并推送工具 2026-10-28 起去掉了）；自动模式也一样。不走 OpenSpec 的改动也按下面的"提交方式"。
    

      
    
        
    提交方式
    人工、自动都用。做完一件完整的事时：询问交代改了什么、怎么验的，问你"提交 / 还要改"；自动直接提交；关不问也不提交，你说"提交"才提交。
    
          
    细节
    • 提交时机参照 Claude 桌面版：做完一件完整的事才算。OpenSpec 实施里，上次提交之后又勾完了一项任务；审查修复全部收尾（连续没拿到结论停了的不挡）；任务都勾完以后，改完你报的一处问题；需求文档四份定稿；不走 OpenSpec 的改动做完、跑过快检。做到一半不算。
    • 只 add 它这一轮改的和新建的文件，你工作区里原来就有的改动不会被带上。
    • 自动模式时选"询问"：你不在，它先不提交，把要提交的列进全自动报告，等你回来说。
    • push 和发内网不归这里管，一律要你亲口说。
    
        
    
      
    
      
    
        
    提交检查
    开着：提交信息要写成"类型: 内容"；不许 git add -A、git add .、git commit -a。
    
          
    细节
    • 提交信息的例子：feat: 新增修改页面。
    • 壳子里 add 子项目目录也拦，那样会提交成 gitlink。
    • 它新建的文件漏了 add 就提交，会点名拦一次。
    • 它用 tools/commit.js（只提交这个会话改过的文件）提交的，和 git commit 一样查。
    • 不查提交内容里像密码的东西；套件自己的令牌文件（GitLab 令牌、模型的 key）一直不许提交，不受这个开关管。

    Claude Code 自带的自动模式
    新版 Claude Code 没配权限模式时默认进它：有风险的命令先发给一个分类模型审。内网的模型当不了这个分类器，默认关掉。
    
          
    细节
      
            
    • 它是 Claude Code 的 auto mode，和套件的自动模式（/vk-auto）是两回事。2.1.284 起默认进，2.1.259 和更早的版本没有这回事。
      • 
            
    • 实测（2.1.289，经网关）：node -e、curl 这类命令每条多发一次请求给审查用的那个模型，系统提示有 14 万字符；它答得不合格式就重试，最多十次，然后把命令拦下。
      • 
            
    • 关掉：套件在 settings.json 里写 permissions.disableAutoMode，会话照以前的普通模式起（底下显示 manual mode），放行的还是套件装的那几条权限。
      • 
            
    • 不管它：套件把自己写的那一项去掉，照 Claude Code 的默认。
      • 
            
    • 你启动时带 --dangerously-skip-permissions，或者自己在 settings.json 里配了 defaultMode，不受这一项影响。改了要重新打开 Claude Code 才生效。

    更新和上报
    套件从团队的 GitLab 仓库拿新版，问题反馈建成那个仓库的 issue。
    
    
    这台电脑上装着的套件还没有自动更新和问题上报，版本太老。装一次新版的安装包就有了。

    和 GitLab 换过 SSH 密钥的电脑，令牌不用填：拿新版走 SSH，要建 issue 时用 SSH 向 GitLab 申请一个令牌存在本机。

    只对 https 地址有用。默认关：内网常见的自签证书也能连上。
    
        
    
      
    
      
    
      
    
    
    
    
    
      
    自动更新
    
      
    用 Claude Code 的时候，隔一阵在后台问一次仓库，没有窗口。有新版就下载；勾了"先装新版"的马上装，没勾的等这一版发布满 24 小时、尝鲜组没报问题再装。装完自检，自检不过自动装回上一版。装着的版本跟着仓库走：仓库退回旧版，这台电脑也马上跟着退，不等。
    
      
    
        
    发现新版之后
    "只提醒"：状态栏和这一页说有新版，你点了才装。
    
        
    
      
    
      
    
        
    先装新版（尝鲜）
    勾上：一发现新版就装，替大家先试。不勾：等这一版发布满 24 小时、尝鲜组没报问题再装。
    
          
    细节
    • 24 小时按仓库里那次发布的时间算；那个时间比现在还晚（维护的电脑钟不准）的，按这台电脑第一次看到它的时间算。
    • 尝鲜组报问题：在仓库里记一条"[有问题的版本] 版本号"。
    • 这一条开着，没勾的电脑就不自动装那一版。维护的人确认是误报、关掉它以后，最晚两小时照常装。
    • 查不到有没有人报（没有建 issue 的令牌、接口不通）按没问题算，满 24 小时照装。
    • 点"立即更新"不用等；仓库退回旧版也不等，马上跟着退。
    
        
    
      
    
      
    
        
    多久检查一次
    1 到 24。

    固定、跳过
    固定在这一版：什么版本都不自动装，直到取消。跳过这一版：仓库里是这一版时不自动装，出了别的版本照常。
    
          
    细节
    • 固定着照常检查，这一页看得到仓库里有什么。
    • 固定以后这些都不做：装新版、跟着仓库退回旧版、装坏后再试着装回。"立即更新"是灰的，要先取消固定。
    • 没装好的版本不能固定。
    • 跳过的版本点"立即更新"照样能装；出了别的版本，跳过自动不起作用，不用去取消。
